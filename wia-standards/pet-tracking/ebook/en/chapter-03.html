3.1 Real-time Tracking Architecture

Real-time pet tracking requires a distributed system architecture that balances responsiveness, reliability, scalability, and battery efficiency. The WIA-PET-TRACKING standard defines a three-tier architecture optimized for these requirements.

System Components

================================

+------------------+
|   Pet Tracker    |  (Tier 1: Edge Device)
|   - GPS Module   |
|   - Cellular     |
|   - Battery      |
+--------+---------+
         |
         | HTTPS/MQTT/CoAP
         ↓
+------------------+
|  Cloud Gateway   |  (Tier 2: Backend Services)
|  - Load Balancer |
|  - API Servers   |
|  - Message Queue |
|  - Database      |
+--------+---------+
         |
         | WebSocket/SSE/Push
         ↓
+------------------+
|  Client Apps     |  (Tier 3: User Interface)
|  - Mobile Apps   |
|  - Web Portal    |
|  - Watch Apps    |
+------------------+

Data Flow Patterns

Pattern Protocol Latency Power Use Case
Streaming WebSocket <100ms High Active tracking, live following
Polling HTTPS 500ms-5s Medium Periodic updates, background refresh
Push FCM/APNS 1-5s Low Alerts, geofence violations
Event-Driven MQTT <200ms Low IoT devices, telemetry
Batch HTTPS Minutes Very Low Historical data, analytics

Update Frequency Modes

The WIA-PET-TRACKING standard defines five update frequency modes that balance real-time responsiveness with battery life:

Mode Interval Battery Life Use Case Data Usage
High Performance 10 seconds 12-18 hours Active search, lost pet ~50 MB/month
Real-time 30 seconds 24-36 hours Live tracking, walks ~25 MB/month
Normal 2 minutes 48-60 hours Daily monitoring ~10 MB/month
Eco 5 minutes 60-72 hours Home monitoring ~5 MB/month
Sleep 30 minutes 5-7 days Low activity, indoor ~1 MB/month

3.2 Location Update Protocol

The location update protocol defines how trackers communicate position data to backend servers and how clients receive real-time updates.

Tracker-to-Server Communication

Trackers SHALL support at least one of the following protocols for sending location updates:

PROTOCOL 1: HTTPS POST (Required for Basic conformance)
========================================================

Endpoint: POST /api/v1/tracking/update
Headers:
  Authorization: Bearer {tracker_jwt_token}
  Content-Type: application/json

Request Body:
{
  "trackerId": "TRK-ABC123",
  "timestamp": "2025-12-25T10:30:45.123Z",
  "location": {
    "latitude": 37.774929,
    "longitude": -122.419418,
    "accuracy": 8.5,
    "altitude": 52.3,
    "heading": 275.5,
    "speed": 1.2
  },
  "positioning": {
    "method": "multi-gnss",
    "satellites": 12,
    "hdop": 0.9
  },
  "battery": {
    "level": 78,
    "voltage": 3.87,
    "estimatedHours": 36
  }
}

Response (200 OK):
{
  "status": "accepted",
  "sequenceNumber": 12847,
  "nextUpdate": "2025-12-25T10:31:15.000Z",
  "config": {
    "updateInterval": 30,
    "mode": "real-time"
  }
}

PROTOCOL 2: MQTT (Recommended for Standard conformance)
========================================================

Topic: wia/tracking/{trackerId}/location
QoS: 1 (at least once delivery)
Retain: false

Message Payload (JSON):
{
  "timestamp": "2025-12-25T10:30:45.123Z",
  "location": { ... },
  "positioning": { ... },
  "battery": { ... }
}

PROTOCOL 3: CoAP (Optional for Advanced conformance)
=====================================================

Endpoint: coap://api.example.com/tracking/update
Method: POST
Content-Format: application/json

(Same JSON payload as HTTPS)

Server-to-Client Communication

Clients SHALL support at least one of the following protocols for receiving real-time updates:

METHOD 1: WebSocket (Recommended)
=================================

Connection: wss://api.example.com/ws/tracking
Protocol: wia-tracking-v1

Client Subscribe Message:
{
  "action": "subscribe",
  "trackerIds": ["TRK-ABC123", "TRK-DEF456"],

===========================================

Endpoint: GET /api/v1/tracking/stream?trackers=TRK-ABC123,TRK-DEF456

  Authorization: Bearer {user_jwt_token}

Event Stream:

data: {"trackerId":"TRK-ABC123","timestamp":"2025-12-25T10:30:45.123Z",...}

event: geofence
data: {"trackerId":"TRK-ABC123","geofenceId":"GEO-HOME","event":"exit",...}

METHOD 3: Push Notifications (Alerts only)
===========================================

For critical alerts (geofence violations, low battery, lost pet)
Platform: FCM (Android) / APNS (iOS)

3.3 Motion Detection and Smart Updates

Battery-powered pet trackers benefit greatly from motion-aware update strategies that reduce GPS sampling when pets are stationary.

Accelerometer-Based Motion Detection

Modern pet trackers include accelerometers to detect movement without activating GPS:

State Detection Criteria GPS Sampling Update Frequency
Stationary Acceleration <0.1g for >2 min Every 30 minutes Only on movement
Resting Minor movement <0.3g Every 10 minutes Every 30 minutes
Walking Regular pattern 0.3-1.0g Every 2 minutes Every 2 minutes
Running High activity >1.0g Every 30 seconds Every 30 seconds
Alert Sudden spike or shake Immediate Immediate + frequent

Smart Update Algorithm

ADAPTIVE UPDATE FREQUENCY
=========================

1. Initialize:
   - Default mode: "Normal" (2-minute updates)
   - Motion threshold: 0.3g
   - Stationary timeout: 5 minutes

2. Continuous Monitoring:
   - Sample accelerometer every 1 second
   - Calculate movement magnitude
   - Detect activity state

3. State Machine:

   IF stationary for >5 minutes:
     - Reduce GPS sampling to every 30 minutes
     - Report "Last known location" with staleness
     - Monitor for movement via accelerometer only
     - Battery savings: ~80%

   ELSE IF movement detected:
     - Increase GPS sampling to every 30 seconds
     - Report actual location updates
     - Continue for duration of movement + 2 minutes

   ELSE IF geofence boundary nearby (<50m):
     - Increase GPS sampling to every 10 seconds
     - Monitor for boundary crossing
     - Return to normal after crossing or moving away

   ELSE IF battery <20%:
     - Reduce to "Eco" mode regardless of movement
     - GPS every 5 minutes minimum
     - Alert user about low battery

4. Override Conditions:
   - User activates "Live Tracking": 10-second updates
   - Lost Pet Mode: 10-second updates, ignore battery
   - Sleep Schedule: Minimum updates during night hours

Example State Transition:
10:00 - Pet resting at home (stationary)
        → GPS every 30 min, battery saver ON
10:15 - Movement detected (walking)
        → GPS every 30 sec, normal tracking
10:45 - Stationary again (sleeping)
        → GPS every 30 min after 5-min timeout
11:30 - Movement + near geofence boundary
        → GPS every 10 sec, high-frequency mode
11:35 - Crossed boundary, alert sent
        → Return to movement-based updates

3.4 Network Connectivity and Failover

Pet trackers must handle variable network conditions gracefully, including areas with poor or no cellular coverage.

Connectivity States

State Condition Behavior
Online Active cellular connection Normal operation, real-time updates
Degraded Weak signal (<2 bars) Reduce update frequency, queue data
Offline No cellular coverage Store locations locally, sync when online
Roaming Outside home network Continue tracking (may incur roaming fees)
Wi-Fi Available Known Wi-Fi network in range Use Wi-Fi for data, save cellular

Offline Buffering Strategy

OFFLINE DATA MANAGEMENT
=======================

Local Storage Capacity: Minimum 7 days of location history
Buffer Format: Circular buffer (FIFO)
Storage Medium: Flash memory

When Offline:
1. Continue GPS positioning (if needed)
2. Store location updates locally with timestamps
3. Compress older data to extend buffer
4. Monitor for network connectivity

When Connection Restored:
1. Authenticate with server
2. Upload buffered locations in chronological order
3. Use batch API for efficiency:

   POST /api/v1/tracking/batch
   {
     "trackerId": "TRK-ABC123",
     "locations": [
       {
         "timestamp": "2025-12-25T10:00:00Z",
         "location": {...}
       },
       {
         "timestamp": "2025-12-25T10:02:00Z",
         "location": {...}
       },
       ...
     ]
   }

5. Delete uploaded data from local buffer
6. Resume normal operation

Buffer Overflow Handling:
- If buffer fills before connectivity restored:
  - Keep most recent locations (last 24 hours)
  - Keep locations at geofence crossings (critical)
  - Compress older data by reducing frequency
  - Discard oldest non-critical locations

Priority Levels:
  CRITICAL:   Geofence violations, alerts
  HIGH:       Movement periods, boundary approaches
  NORMAL:     Regular updates during activity
  LOW:        Stationary periods, redundant data

3.6 Battery Life Optimization

Battery life is the most critical constraint in pet tracking devices. The WIA-PET-TRACKING standard defines optimization strategies.

Power Consumption Profile

Component Active Power Sleep Power % of Total
GPS Module 30-50 mA 0.5 mA 40-60%
Cellular Modem (4G) 200-400 mA (tx) 2-5 mA 30-40%
Accelerometer 0.15 mA 0.01 mA 1-2%
MCU (Microcontroller) 10-20 mA 0.05 mA 5-10%
Other (LED, sensors) 5-10 mA 0.01 mA 2-5%

Battery Life Calculation

BATTERY LIFE ESTIMATION
=======================

Given:
  Battery capacity: 1000 mAh (typical for small tracker)
  Update interval: 30 seconds
  GPS fix time: 5 seconds per update
  Cellular transmission: 2 seconds per update

Calculation:
  Per 30-second cycle:
    - GPS active: 5 sec × 40 mA = 0.055 mAh
    - Cellular tx: 2 sec × 300 mA = 0.167 mAh
    - Sleep: 23 sec × 3 mA = 0.019 mAh
    - Total per cycle: 0.241 mAh

  Cycles per hour: 120
  Consumption per hour: 120 × 0.241 = 28.9 mAh

  Battery life: 1000 mAh / 28.9 mAh = 34.6 hours

Optimization Strategies:
1. Reduce update frequency → 72+ hours at 5-min intervals
2. Use accelerometer wake → 60+ hours with motion detection
3. Implement A-GPS → Reduce GPS fix time to 1-2 seconds
4. Use NB-IoT instead of 4G → Reduce cellular power by 50%
5. Optimize antenna → Improve GPS sensitivity, faster fixes

Mode Comparisons:
  High Performance (10s):  ~15 hours
  Real-time (30s):         ~35 hours
  Normal (2min):           ~55 hours
  Eco (5min):              ~72 hours
  Sleep (30min):           ~140 hours (5-6 days)

Chapter Summary

Key Takeaways:

  1. Three-Tier Architecture: Real-time tracking requires edge devices (trackers), backend services (cloud), and client applications working together seamlessly.
  2. Adaptive Updates: Smart update algorithms using motion detection can extend battery life by 80% while maintaining tracking quality during active periods.
  3. Protocol Flexibility: The standard supports multiple protocols (HTTPS, MQTT, WebSocket) to accommodate different implementation needs and constraints.
  4. Offline Resilience: Buffering location data locally ensures no data loss during connectivity gaps, with automatic sync when connection is restored.
  5. Battery Optimization: GPS and cellular transmission are the largest power consumers; optimizing their usage through motion detection and update frequency adjustment is essential for multi-day battery life.

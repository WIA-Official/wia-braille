From APIs to On-Chain Protocols

Phase 2 established standardized APIs for token management and compliance checks. But to achieve true decentralization, transparency, and programmability, we need to move these capabilities on-chain through smart contract protocols.

Phase 3 transforms WIA-FIN-008 from a centralized API system into a decentralized protocol where token issuance, transfers, compliance enforcement, and dividend distribution happen directly on the blockchain—trustlessly, transparently, and immutably.

🎯 Phase 3 Goal

Implement production-ready smart contract protocols that enable:

  • ERC-1400 compliant security token deployment
  • Automated transfer restrictions and compliance enforcement
  • On-chain dividend/rental income distribution
  • Token holder governance and voting
  • Multi-chain deployment (Ethereum, Polygon, Avalanche)
  • Upgradability and emergency controls

ERC-1400: The Security Token Standard

While ERC-20 powers utility tokens and DeFi, ERC-1400 is the industry standard for compliant security tokens. Developed by Polymath and adopted by major platforms (Securitize, Harbor, TokenSoft), ERC-1400 provides:

Core Features

Feature Purpose Implementation
Transfer Restrictions Enforce KYC/AML, lockups, jurisdiction limits canTransfer() validation hooks
Partition Management Multiple token classes (common, preferred) transferByPartition()
Document Management On-chain legal documents and disclosures setDocument(), getDocument()
Forced Transfers Legal/regulatory seizure or recovery controllerTransfer()
Issuance Control Controlled token minting for offerings issue(), redeem()

ERC-1400 Contract Architecture

// Simplified ERC-1400 Interface pragma solidity ^0.8.0; interface IERC1400 { // Transfer Validation function canTransfer( address from, address to, uint256 value, bytes calldata data ) external view returns (bool, bytes32, bytes32); // Partition-Based Transfers function transferByPartition( bytes32 partition, address to, uint256 value, bytes calldata data ) external returns (bytes32); // Document Management function setDocument( bytes32 name, string calldata uri, bytes32 documentHash ) external; function getDocument(bytes32 name) external view returns ( string memory, bytes32, uint256 ); // Controller Operations function controllerTransfer( address from, address to, uint256 value, bytes calldata data, bytes calldata operatorData ) external; // Issuance function issue( address tokenHolder, uint256 value, bytes calldata data ) external; function redeem( uint256 value, bytes calldata data ) external; }

Compliance Module: Transfer Restrictions

The heart of WIA-FIN-008 Phase 3 is the Compliance Module—a modular smart contract that enforces regulatory requirements before allowing token transfers.

Compliance Rules Engine

// WIA-FIN-008 Compliance Module pragma solidity ^0.8.0; contract AssetTokenCompliance { struct InvestorProfile { bool kycVerified; bool accredited; uint256 kycExpiry; string jurisdiction; // ISO 3166-1 alpha-3 uint256 lockupExpiry; uint256 lastTransferTime; } mapping(address => InvestorProfile) public investors; mapping(string => bool) public allowedJurisdictions; uint256 public maxOwnershipPercent = 500; // 5.00% (basis points) uint256 public minHoldingPeriod = 30 days; uint256 public totalSupply; // Transfer Validation function canTransfer( address from, address to, uint256 amount ) public view returns ( bool allowed, string memory reason ) { InvestorProfile memory sender = investors[from]; InvestorProfile memory recipient = investors[to]; // Rule 1: Recipient must be KYC verified if (!recipient.kycVerified) { return (false, "Recipient not KYC verified"); } // Rule 2: KYC must not be expired if (block.timestamp > recipient.kycExpiry) { return (false, "Recipient KYC expired"); } // Rule 3: Accreditation required (for Reg D) if (!recipient.accredited) { return (false, "Recipient not accredited investor"); } // Rule 4: Jurisdiction whitelist if (!allowedJurisdictions[recipient.jurisdiction]) { return (false, "Recipient jurisdiction not allowed"); } // Rule 5: Lockup period enforcement if (block.timestamp < sender.lockupExpiry) { return (false, "Sender lockup period not expired"); } // Rule 6: Maximum ownership limit uint256 recipientBalance = balanceOf(to); uint256 newBalance = recipientBalance + amount; uint256 ownershipPercent = (newBalance * 10000) / totalSupply; if (ownershipPercent > maxOwnershipPercent) { return (false, "Exceeds maximum ownership limit"); } // Rule 7: Minimum holding period if (block.timestamp < sender.lastTransferTime + minHoldingPeriod) { return (false, "Minimum holding period not met"); } return (true, "Transfer allowed"); } // Transfer with Compliance Check function transfer(address to, uint256 amount) external returns (bool) { (bool allowed, string memory reason) = canTransfer(msg.sender, to, amount); require(allowed, reason); _transfer(msg.sender, to, amount); investors[msg.sender].lastTransferTime = block.timestamp; return true; } }

KYC Provider Integration

Rather than storing sensitive KYC data on-chain, WIA-FIN-008 uses an oracle pattern where trusted KYC providers (Onfido, Jumio, Civic) attest to investor verification:

// KYC Oracle Integration contract KYCOracle { mapping(address => bool) public approvedProviders; mapping(address => mapping(address => bool)) public verifications; event KYCVerified( address indexed investor, address indexed provider, uint256 timestamp, uint256 expiryDate ); // KYC Provider submits verification function verifyInvestor( address investor, uint256 expiryDate, bytes calldata signature ) external { require(approvedProviders[msg.sender], "Not approved provider"); // Verify signature from off-chain KYC check bytes32 messageHash = keccak256(abi.encodePacked( investor, expiryDate, block.chainid )); require( recoverSigner(messageHash, signature) == msg.sender, "Invalid signature" ); verifications[msg.sender][investor] = true; emit KYCVerified(investor, msg.sender, block.timestamp, expiryDate); } }

Dividend Distribution Protocol

One of the most powerful features of asset tokenization is automated dividend distribution. For real estate tokens, this means quarterly rental income; for art tokens, resale appreciation; for commodity tokens, storage fee rebates.

Push vs. Pull Distribution

Method Pros Cons Use Case
Push Automatic, no user action High gas costs for many holders Small holder count (<100)
Pull Gas-efficient, scalable Users must claim manually Large holder count (>100)
Merkle Tree Ultra gas-efficient Complex implementation Very large holder count (>1000)

Pull-Based Distribution (Recommended)

// WIA-FIN-008 Dividend Distribution contract DividendDistributor { struct Distribution { uint256 totalAmount; uint256 amountPerToken; uint256 timestamp; uint256 claimedAmount; } Distribution[] public distributions; mapping(address => mapping(uint256 => bool)) public hasClaimed; event DividendDistributed( uint256 indexed distributionId, uint256 totalAmount, uint256 amountPerToken, uint256 timestamp ); event DividendClaimed( address indexed investor, uint256 indexed distributionId, uint256 amount ); // Asset Manager distributes rental income function distributeRentalIncome(uint256 amount) external onlyManager { uint256 totalSupply = token.totalSupply(); uint256 amountPerToken = (amount * 1e18) / totalSupply; distributions.push(Distribution({ totalAmount: amount, amountPerToken: amountPerToken, timestamp: block.timestamp, claimedAmount: 0 })); emit DividendDistributed( distributions.length - 1, amount, amountPerToken, block.timestamp ); } // Token holders claim their share function claimDividend(uint256 distributionId) external { require(distributionId < distributions.length, "Invalid distribution"); require(!hasClaimed[msg.sender][distributionId], "Already claimed"); Distribution storage dist = distributions[distributionId]; uint256 balance = token.balanceOf(msg.sender); uint256 amount = (balance * dist.amountPerToken) / 1e18; require(amount > 0, "No dividends to claim"); hasClaimed[msg.sender][distributionId] = true; dist.claimedAmount += amount; payable(msg.sender).transfer(amount); emit DividendClaimed(msg.sender, distributionId, amount); } // Claim multiple distributions at once function claimMultiple(uint256[] calldata distributionIds) external { for (uint256 i = 0; i < distributionIds.length; i++) { if (!hasClaimed[msg.sender][distributionIds[i]]) { claimDividend(distributionIds[i]); } } } }

Governance & Voting

Token holders should have a say in major decisions: property refinancing, sale, major renovations, asset manager replacement. WIA-FIN-008 implements on-chain governance using a modified Governor Bravo pattern.

Governance Mechanisms

// Asset Token Governance contract AssetGovernance { struct Proposal { uint256 id; address proposer; string description; uint256 forVotes; uint256 againstVotes; uint256 startTime; uint256 endTime; bool executed; mapping(address => bool) hasVoted; } Proposal[] public proposals; uint256 public votingPeriod = 7 days; uint256 public quorumPercent = 5000; // 50% (basis points) uint256 public approvalThreshold = 6667; // 66.67% majority // Create Proposal (requires 1% token ownership) function propose(string calldata description) external returns (uint256) { uint256 proposerBalance = token.balanceOf(msg.sender); uint256 totalSupply = token.totalSupply(); require( (proposerBalance * 10000) / totalSupply >= 100, "Insufficient tokens to propose" ); Proposal storage prop = proposals.push(); prop.id = proposals.length - 1; prop.proposer = msg.sender; prop.description = description; prop.startTime = block.timestamp; prop.endTime = block.timestamp + votingPeriod; return prop.id; } // Vote on Proposal function vote(uint256 proposalId, bool support) external { Proposal storage prop = proposals[proposalId]; require(block.timestamp <= prop.endTime, "Voting ended"); require(!prop.hasVoted[msg.sender], "Already voted"); uint256 votes = token.balanceOf(msg.sender); prop.hasVoted[msg.sender] = true; if (support) { prop.forVotes += votes; } else { prop.againstVotes += votes; } } // Execute Proposal function execute(uint256 proposalId) external { Proposal storage prop = proposals[proposalId]; require(block.timestamp > prop.endTime, "Voting ongoing"); require(!prop.executed, "Already executed"); uint256 totalVotes = prop.forVotes + prop.againstVotes; uint256 totalSupply = token.totalSupply(); // Check quorum require( (totalVotes * 10000) / totalSupply >= quorumPercent, "Quorum not reached" ); // Check approval require( (prop.forVotes * 10000) / totalVotes >= approvalThreshold, "Insufficient approval" ); prop.executed = true; _executeProposal(proposalId); } }

Upgradability & Security

Proxy Pattern for Upgrades

Asset tokens may need bug fixes or feature additions. Use transparent proxy pattern:

// OpenZeppelin Transparent Proxy contract AssetTokenProxy is TransparentUpgradeableProxy { constructor( address _logic, address admin_, bytes memory _data ) TransparentUpgradeableProxy(_logic, admin_, _data) {} } // Upgrade process (admin only) function upgrade(address newImplementation) external onlyAdmin { _upgradeTo(newImplementation); }

Emergency Controls

// Circuit Breaker for Emergencies contract EmergencyControls { bool public paused; address public guardian; modifier whenNotPaused() { require(!paused, "Contract paused"); _; } // Guardian can pause in emergency function pause() external onlyGuardian { paused = true; emit Paused(msg.sender, block.timestamp); } function unpause() external onlyAdmin { paused = false; emit Unpaused(msg.sender, block.timestamp); } }

Gas Optimization

Security tokens involve frequent compliance checks and transfers. Key optimizations:

  • Batch Operations: Transfer to multiple recipients in single transaction
  • Merkle Proofs: For large-scale dividend claims
  • Storage Packing: Pack multiple values into single storage slot
  • EIP-2612 Permits: Gasless approvals via signatures
  • Read Caching: Cache frequently-read values in memory

Security Audit Checklist

Before mainnet deployment, ensure:

  • ✓ Complete audit by reputable firm (OpenZeppelin, Trail of Bits, ConsenSys Diligence)
  • ✓ Formal verification of critical functions (canTransfer, distributeIncome)
  • ✓ Comprehensive test coverage (>95% line coverage, 100% branch coverage)
  • ✓ Testnet deployment for 30+ days with public bug bounty
  • ✓ Multi-sig admin controls (3-of-5 or 5-of-9 Gnosis Safe)
  • ✓ Time-locked upgrades (minimum 48-hour delay)
  • ✓ Emergency pause mechanism with guardian oversight

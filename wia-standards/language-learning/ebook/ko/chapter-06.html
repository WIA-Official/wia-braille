제6장: 보안 및 프라이버시

"학습자 데이터는 신성합니다. 보안과 프라이버시는 선택이 아닌 필수입니다."

6.1 보안 원칙

WIA-EDU-022는 다음 보안 원칙을 준수합니다:

🛡️ CIA 트라이어드

원칙 설명 구현
기밀성
(Confidentiality)		 권한 있는 사용자만 데이터 접근 암호화, 접근 제어
무결성
(Integrity)		 데이터 변조 방지 해시, 디지털 서명
가용성
(Availability)		 필요할 때 시스템 사용 가능 백업, 재해복구

🔒 다층 보안 모델

계층 1: 네트워크 보안
├─ DDoS 방어
├─ 방화벽
└─ IDS/IPS

계층 2: 애플리케이션 보안
├─ 인증/인가
├─ 입력 검증
├─ CSRF/XSS 방어
└─ Rate Limiting

계층 3: 데이터 보안
├─ 암호화 (전송/저장)
├─ 데이터 마스킹
└─ 접근 로그

계층 4: 물리적 보안
├─ 데이터센터 보안
├─ 하드웨어 보안
└─ 재해 복구

6.2 인증 및 인가

🔐 OAuth 2.0 + OIDC

인증 흐름:

1. 사용자 로그인 요청
   → 인증 서버로 리다이렉트

2. 인증 서버에서 자격증명 확인
   → 인증 성공 시 Authorization Code 발급

3. Authorization Code로 Access Token 교환
   POST /oauth/token
   {
     "grant_type": "authorization_code",
     "code": "abc123",
     "redirect_uri": "https://app.wialanguage.com/callback",
     "client_id": "your-client-id",
     "client_secret": "your-client-secret"
   }

4. Access Token 수신
   {
     "access_token": "eyJhbGc...",
     "token_type": "Bearer",
     "expires_in": 3600,
     "refresh_token": "def456",
     "scope": "learner.read learner.write"
   }

5. API 요청 시 Access Token 사용
   Authorization: Bearer eyJhbGc...

👥 역할 기반 접근 제어 (RBAC)

역할 권한 사용 사례
learner 자신의 데이터 읽기/쓰기 일반 학습자
instructor 콘텐츠 생성/관리, 학습자 조회 교사, 강사
admin 시스템 관리, 사용자 관리 플랫폼 관리자
content_creator 콘텐츠 생성/수정 교재 제작자

6.3 데이터 암호화

🔐 전송 중 암호화

  • TLS 1.3 — 모든 API 통신
  • Perfect Forward Secrecy — 세션 키 유출 시에도 과거 통신 보호
  • HSTS — HTTP Strict Transport Security
  • Certificate Pinning — 모바일 앱에서 인증서 고정

💾 저장 시 암호화

데이터 유형별 암호화 전략:

1. 개인 식별 정보 (PII)
   - 알고리즘: AES-256-GCM
   - 키 관리: AWS KMS / Google Cloud KMS
   - 필드: 이름, 이메일, 전화번호

2. 민감 학습 데이터
   - 알고리ズ�: AES-256-GCM
   - 필드: 음성 녹음, 작문 샘플, 평가 결과

3. 인증 정보
   - 비밀번호: bcrypt (cost factor 12)
   - API 키: SHA-256 해시

4. 데이터베이스 전체 암호화
   - PostgreSQL: Transparent Data Encryption (TDE)
   - 백업: 암호화된 스냅샷

예제 코드:
const crypto = require('crypto');

function encryptPII(data, key) {
  const iv = crypto.randomBytes(16);
  const cipher = crypto.createCipheriv('aes-256-gcm', key, iv);

  let encrypted = cipher.update(data, 'utf8', 'hex');
  encrypted += cipher.final('hex');

  const authTag = cipher.getAuthTag();

  return {
    encrypted,
    iv: iv.toString('hex'),
    authTag: authTag.toString('hex')
  };
}

6.4 프라이버시 규정 준수

📜 GDPR 준수

GDPR 요구사항 구현
동의 획득 명시적 동의 UI, 동의 기록 저장
데이터 최소화 필요한 데이터만 수집
정보 접근권 GET /learners/{id}/data-export
삭제권 DELETE /learners/{id} (완전 삭제)
데이터 이동권 JSON/CSV 형식 다운로드
침해 통지 72시간 이내 통지 프로세스

🇺🇸 COPPA 준수 (아동 보호)

13세 미만 아동 데이터 처리 시 특별 조치:

  • 부모 동의 — 계정 생성 전 부모/보호자 확인
  • 데이터 수집 제한 — 교육 목적 외 데이터 수집 금지
  • 제3자 공유 금지 — 광고, 마케팅 목적 데이터 공유 불가
  • 부모 접근권 — 부모가 자녀 데이터 조회/삭제 가능

6.5 취약점 방어

🛡️ OWASP Top 10 대응

취약점 방어 방법
SQL Injection Parameterized queries, ORM 사용
XSS 입력 sanitization, CSP 헤더
CSRF CSRF 토큰, SameSite 쿠키

6.6 감사 로깅

📋 감사 이벤트

다음 이벤트는 모두 로그에 기록되어야 합니다:

  • 인증 이벤트 — 로그인, 로그아웃, 비밀번호 변경
  • 권한 변경 — 역할 할당, 권한 수정
  • 민감 데이터 접근 — PII 조회, 수정, 삭제
  • 시스템 설정 변경 — 구성 수정, 기능 활성화/비활성화

6.7 침해 대응 계획

🚨 단계별 대응

Phase 1: 탐지 및 분석 (0-4시간)
├─ 이상 징후 탐지
├─ 침해 범위 파악
├─ 영향 받은 데이터 식별
└─ 보안팀 소집

Phase 2: 격리 및 차단 (4-8시간)
├─ 공격 벡터 차단
├─ 영향 받은 시스템 격리
├─ 추가 침투 방지
└─ 증거 보존

Phase 3: 제거 및 복구 (8-24시간)
├─ 악성코드 제거
├─ 취약점 패치
├─ 시스템 복원
└─ 보안 강화

Phase 4: 통지 및 보고 (24-72시간)
├─ 영향 받은 사용자 통지
├─ 규제 기관 보고 (GDPR 72시간 규정)
├─ 언론 대응 (필요시)
└─ 사후 분석 보고서

Phase 5: 개선 (72시간+)
├─ 근본 원인 분석
├─ 프로세스 개선
├─ 보안 교육 강화
└─ 모니터링 강화

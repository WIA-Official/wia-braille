Token Standards: ERC-721 & ERC-1155

Token standards are the backbone of the NFT ecosystem, providing a common framework that enables interoperability, composability, and consistent behavior across different platforms and applications. This chapter explores the two primary NFT standards on Ethereum: ERC-721 and ERC-1155, examining their technical specifications, use cases, and implementation considerations.

Understanding ERC-721: The Original NFT Standard

History and Development

ERC-721 emerged from the CryptoKitties project in late 2017. As the game's popularity exploded, the development team, led by Dieter Shirley, recognized the need for a standardized interface for non-fungible tokens. They proposed ERC-721 as an Ethereum Improvement Proposal (EIP), which was finalized in January 2018 after extensive community discussion and refinement.

The standard's name comes from the Ethereum Request for Comments (ERC) process, with 721 being the proposal number. It established the first formal specification for non-fungible tokens on Ethereum, defining the minimum interface that conforming contracts must implement.

Core Concepts and Architecture

At its heart, ERC-721 defines each token as absolutely unique, identified by a uint256 token ID within a specific contract. No two tokens can share the same ID within the same contract, ensuring uniqueness. Each token is indivisible—you cannot own 0.5 of an ERC-721 token; you either own it entirely or not at all.

The standard maintains a mapping of token IDs to owner addresses, creating an immutable record of ownership on the blockchain. It also tracks which addresses are approved to transfer specific tokens, enabling marketplace functionality where you can list a token for sale without transferring ownership until the sale completes.

Required Interface Methods

Every ERC-721 compliant contract must implement specific functions: 

interface IERC721 {
    // Returns the number of tokens owned by an address
    function balanceOf(address owner) external view returns (uint256 balance);

    // Returns the owner of a specific token ID
    function ownerOf(uint256 tokenId) external view returns (address owner);

    // Transfers a token from one address to another
    function safeTransferFrom(
        address from,
        address to,
        uint256 tokenId
    ) external;

    // Transfers a token (unsafe version)
    function transferFrom(
        address from,
        address to,
        uint256 tokenId
    ) external;

    // Approves another address to transfer a specific token
    function approve(address to, uint256 tokenId) external;

    // Approves an operator to manage all tokens for the owner
    function setApprovalForAll(address operator, bool approved) external;

    // Returns the approved address for a specific token
    function getApproved(uint256 tokenId) external view returns (address);

    // Checks if an operator is approved to manage all tokens for an owner
    function isApprovedForAll(
        address owner,
        address operator
    ) external view returns (bool);
}

Metadata Extension

While the core ERC-721 standard handles ownership and transfers, the metadata extension defines how to associate descriptive information with tokens. This optional but widely adopted extension includes: 

interface IERC721Metadata {
    // Returns the token collection name
    function name() external view returns (string memory);

    // Returns the token collection symbol
    function symbol() external view returns (string memory);

    // Returns the URI for a token's metadata
    function tokenURI(uint256 tokenId) external view returns (string memory);
}

The tokenURI function is particularly important, as it returns a URL pointing to a JSON file containing the token's metadata. This metadata typically includes the token's name, description, image URL, and any additional attributes or properties.

Use Cases and Applications

ERC-721 excels in scenarios where each token should be completely unique:

  • Digital Art: One-of-one pieces or limited edition artworks where each piece is distinct and valuable in its own right.
  • Virtual Real Estate: Parcels of land in virtual worlds like Decentraland, where each plot has unique coordinates and characteristics.
  • Domain Names: NFT-based domain systems like ENS (Ethereum Name Service) where each domain is unique and non-fungible.
  • Collectibles: Trading cards, sports memorabilia, or other collectibles where each item has individual value and rarity.
  • Digital Identity: Credentials, certificates, or identity tokens where each represents a unique individual or achievement.

ERC-1155: The Multi-Token Standard

Origins and Motivation

ERC-1155 was developed by Enjin, a blockchain gaming company, and formally proposed by Witek Radomski in June 2018. The standard emerged from practical challenges in blockchain gaming, where games need to manage thousands of different item types—some unique (like legendary weapons) and others fungible (like gold coins or potions).

Before ERC-1155, a game would need separate ERC-721 contracts for unique items and ERC-20 contracts for fungible items, leading to complexity, higher gas costs, and difficult inventory management. ERC-1155 solved this by allowing a single contract to manage multiple token types, both fungible and non-fungible.

Multi-Token Architecture

The key innovation of ERC-1155 is its ability to represent multiple token types in a single contract. Each token type has a unique ID, but unlike ERC-721, multiple addresses can own quantities of the same token type. For non-fungible items, you simply set the supply to 1; for fungible items, you can have any supply amount.

This architecture enables batch operations—you can transfer multiple different token types in a single transaction, significantly reducing gas costs compared to multiple ERC-721 transfers.

Interface and Functions

interface IERC1155 {
    // Returns the amount of tokens of type `id` owned by `account`
    function balanceOf(
        address account,
        uint256 id
    ) external view returns (uint256);

    // Batch version of balanceOf
    function balanceOfBatch(
        address[] calldata accounts,
        uint256[] calldata ids
    ) external view returns (uint256[] memory);

    // Approves or removes operator for the caller
    function setApprovalForAll(address operator, bool approved) external;

    // Checks if operator is approved for owner
    function isApprovedForAll(
        address account,
        address operator
    ) external view returns (bool);

    // Transfers tokens from one address to another
    function safeTransferFrom(
        address from,
        address to,
        uint256 id,
        uint256 amount,
        bytes calldata data
    ) external;

    // Batch transfer multiple token types
    function safeBatchTransferFrom(
        address from,
        address to,
        uint256[] calldata ids,
        uint256[] calldata amounts,
        bytes calldata data
    ) external;
}

Metadata Flexibility

ERC-1155 uses a flexible URI system for metadata. Instead of requiring a separate URI for each token, the standard allows a base URI with a placeholder that gets replaced with the token ID: 

// Base URI might be: https://token-cdn-domain/{id}.json
// For token ID 123, the actual URI becomes: https://token-cdn-domain/123.json

function uri(uint256 tokenId) external view returns (string memory);

This approach dramatically simplifies metadata management for large collections, though individual URIs can still be set for specific tokens when needed.

Gas Efficiency

One of ERC-1155's major advantages is gas efficiency. Batch operations allow you to:

  • Mint multiple token types in a single transaction
  • Transfer an entire inventory in one operation
  • Approve all token types for an operator with one call
  • Query balances for multiple tokens simultaneously

In gaming scenarios where players might acquire dozens of different items, ERC-1155 can reduce gas costs by 80% or more compared to equivalent ERC-721 operations.

Use Cases and Applications

  • Gaming: Perfect for games with diverse inventories mixing unique items (characters, legendary equipment) and consumables (potions, materials).
  • Large Collections: Projects minting thousands or millions of items benefit from the gas efficiency and simplified contract management.
  • Fractional Ownership: Scenarios where you want to represent both whole ownership and fractional shares of assets.
  • Complex Ecosystems: Projects needing multiple interrelated token types managed from a single contract.

Comparing ERC-721 and ERC-1155

Feature ERC-721 ERC-1155
Token Uniqueness Each token is unique Can be unique or have multiple copies
Contract Efficiency One contract per collection Multiple token types in one contract
Gas Costs Higher for batch operations Lower due to batch transfers
Adoption More widely adopted and supported Growing adoption, especially in gaming
Metadata Individual URI per token Flexible URI system with ID substitution

Complexity Simpler to understand and implement More complex but more powerful

Implementation Considerations

Choosing the Right Standard

The choice between ERC-721 and ERC-1155 depends on your specific requirements:

Choose ERC-721 when:

  • Each token should be completely unique
  • You're creating art or collectibles where individual provenance matters
  • You want maximum marketplace compatibility
  • Simplicity and widespread adoption are priorities
  • You don't need batch operations

Choose ERC-1155 when:

  • You're building a game with diverse item types
  • Gas efficiency is crucial due to high transaction volumes
  • You need both unique and fungible tokens in your ecosystem
  • Batch operations would benefit your use case
  • You're managing large collections (10,000+ items)

OpenZeppelin Implementation

For production deployments, using battle-tested implementations is crucial. OpenZeppelin provides secure, community-vetted implementations of both standards: 

// ERC-721 Example
import "@openzeppelin/contracts/token/ERC721/ERC721.sol";

contract MyNFT is ERC721 {
    constructor() ERC721("MyNFT", "MNFT") {
        // Constructor logic
    }

    function mint(address to, uint256 tokenId) public {
        _safeMint(to, tokenId);
    }
}

// ERC-1155 Example
import "@openzeppelin/contracts/token/ERC1155/ERC1155.sol";

contract MyMultiToken is ERC1155 {
    constructor() ERC1155("https://api.mytoken.com/metadata/{id}.json") {
        // Constructor logic
    }

    function mint(
        address to,
        uint256 id,
        uint256 amount,
        bytes memory data
    ) public {
        _mint(to, id, amount, data);
    }
}

Security Considerations

Regardless of which standard you choose, security must be paramount:

  • Reentrancy Protection: Use checks-effects-interactions pattern and consider OpenZeppelin's ReentrancyGuard for functions involving external calls.
  • Access Control: Implement proper authorization for minting, burning, and administrative functions using role-based access control.
  • Integer Overflow: While Solidity 0.8+ has built-in overflow protection, be cautious with older versions and external libraries.
  • Front-running: Consider front-running implications for minting and trading functions, especially in high-demand scenarios.
  • Audits: Professional security audits are essential before deploying contracts managing significant value.

💡 Best Practice

Always use well-audited library implementations like OpenZeppelin rather than writing standards from scratch. These libraries have been tested in production by thousands of projects and have undergone multiple security audits. Custom implementations dramatically increase the risk of bugs and vulnerabilities.

Beyond Ethereum: Cross-Chain Standards

While ERC-721 and ERC-1155 originated on Ethereum, the concepts have been adapted to other blockchains:

  • Polygon: Fully compatible with ERC-721 and ERC-1155, offering lower gas costs while maintaining Ethereum security through its Layer 2 architecture.
  • Binance Smart Chain: Uses BEP-721 and BEP-1155, which are functionally identical to their Ethereum counterparts.
  • Solana: Uses a different technical approach but provides similar NFT functionality with its own standards.
  • Flow: Developed by the CryptoKitties team specifically for NFTs, with resource-oriented programming paradigm.

Cross-chain bridges are emerging to enable NFT transfers between different blockchains, though this technology is still maturing and carries additional risks.

Conclusion

Understanding ERC-721 and ERC-1155 is fundamental to working with NFTs. These standards provide the technical foundation enabling interoperability, marketplace functionality, and consistent user experiences across the NFT ecosystem.

ERC-721's simplicity and universal adoption make it the default choice for unique digital assets, while ERC-1155's flexibility and efficiency make it increasingly popular for gaming and complex applications. As the NFT space evolves, both standards will continue to play crucial roles, and new standards may emerge to address specific use cases and limitations.

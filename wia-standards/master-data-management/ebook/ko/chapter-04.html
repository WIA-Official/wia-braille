4장: 마스터 데이터 통합 아키텍처

마스터 데이터 관리의 성공은 적절한 통합 아키텍처 선택에서 시작됩니다. 이 장에서는 다양한 MDM 아키텍처 패턴을 비교 분석하고, 각 패턴의 장단점과 적용 시나리오를 심층적으로 다룹니다.

1. MDM 아키텍처 스타일 개요

MDM 아키�ecture는 크게 네 가지 주요 스타일로 분류됩니다. 각 스타일은 서로 다른 비즈니스 요구사항과 기술적 제약을 충족하도록 설계되었습니다.

아키텍처 스타일 데이터 저장 방식 데이터 흐름 주요 사용 사례
Registry (레지스트리) 중앙 인덱스만 유지, 원본 데이터는 소스 시스템 양방향 조회 크로스 레퍼런스, 경량 MDM
Consolidation (통합) 중앙 저장소에 골든 레코드 저장 (읽기 전용) 단방향 (소스 → MDM) 분석, 보고, BI
Coexistence (공존) 중앙 저장소 + 소스 시스템 동기화 양방향 동기화 하이브리드 환경, 점진적 마이그레이션
Centralized (중앙집중) MDM 허브가 단일 진실 소스 (SSOT) MDM → 모든 시스템 신규 프로젝트, 전사 표준화

2. Hub-and-Spoke vs Registry 아키텍처

Hub-and-Spoke와 Registry는 MDM 구현에서 가장 일반적으로 사용되는 두 가지 패턴입니다.

Hub-and-Spoke 아키텍처

중앙 허브가 모든 마스터 데이터를 저장하고 관리하며, 스포크(spoke) 시스템들과 데이터를 교환합니다.

Hub-and-Spoke 장점:
  • 단일 진실 소스(SSOT) 확립
  • 데이터 품질 중앙 관리
  • 복잡한 비즈니스 규칙 적용 가능
  • 완전한 데이터 계보(lineage) 추적
Hub-and-Spoke 단점:
  • 높은 초기 구축 비용
  • 복잡한 데이터 동기화
  • 중앙 허브 장애 시 전체 영향
  • 레거시 시스템 통합 어려움

Registry 아키텍처

중앙 레지스트리는 마스터 데이터의 인덱스와 크로스 레퍼런스만 관리하고, 실제 데이터는 소스 시스템에 유지됩니다.

3. 데이터 허브 설계 패턴

효과적인 데이터 허브는 확장성, 성능, 유연성을 모두 고려해야 합니다.

계층별 아키텍처

계층 역할 주요 컴포넌트 기술 스택 예시
프레젠테이션 계층 사용자 인터페이스, API 게이트웨이 웹 UI, REST API, GraphQL React, Vue.js, Kong, Apigee
비즈니스 로직 계층 매칭, 병합, 품질 검증 매칭 엔진, 워크플로우 엔진 Python, Java Spring, Camunda
통합 계층 소스 시스템 연동 ETL/ELT, 메시지 큐 Apache NiFi, Kafka, Talend
데이터 계층 마스터 데이터 저장 RDBMS, NoSQL, 데이터 레이크 PostgreSQL, MongoDB, S3

데이터 허브 구현 예시 (Python)

from typing import List, Dict, Optional
from dataclasses import dataclass
from datetime import datetime
import hashlib

@dataclass
class MasterRecord:
    """마스터 레코드 데이터 모델"""
    master_id: str
    entity_type: str
    golden_record: Dict
    source_records: List[Dict]
    confidence_score: float
    created_at: datetime
    updated_at: datetime
    version: int

class DataHub:
    """중앙 데이터 허브 구현"""

    def __init__(self, storage_backend):
        self.storage = storage_backend
        self.matcher = MatchingEngine()
        self.merger = MergingEngine()

    def ingest_record(self, source_system: str, record: Dict) -> str:
        """
        소스 시스템에서 레코드를 수집하여 처리

        Args:
            source_system: 소스 시스템 식별자
            record: 소스 레코드 데이터

        Returns:
            마스터 ID
        """
        # 1. 기존 마스터 레코드와 매칭
        matches = self.matcher.find_matches(record)

        if matches:
            # 2-A. 매칭되면 병합
            master_id = matches[0]['master_id']
            master_record = self.storage.get(master_id)

            # 소스 레코드 추가
            master_record.source_records.append({
                'system': source_system,
                'data': record,
                'ingested_at': datetime.now()
            })

            # 골든 레코드 재계산
            master_record.golden_record = self.merger.merge(
                master_record.source_records
            )
            master_record.version += 1
            master_record.updated_at = datetime.now()

            self.storage.update(master_id, master_record)
            return master_id
        else:
            # 2-B. 매칭 안되면 새 마스터 레코드 생성
            master_id = self._generate_master_id(record)
            master_record = MasterRecord(
                master_id=master_id,
                entity_type=record.get('entity_type', 'unknown'),
                golden_record=record,
                source_records=[{
                    'system': source_system,
                    'data': record,
                    'ingested_at': datetime.now()
                }],
                confidence_score=1.0,
                created_at=datetime.now(),
                updated_at=datetime.now(),
                version=1
            )

            self.storage.create(master_id, master_record)
            return master_id

    def _generate_master_id(self, record: Dict) -> str:
        """마스터 ID 생성"""
        hash_input = f"{record.get('entity_type', '')}_{datetime.now().isoformat()}"
        return f"M-{hashlib.sha256(hash_input.encode()).hexdigest()[:12]}"

    def get_golden_record(self, master_id: str) -> Optional[Dict]:
        """골든 레코드 조회"""
        master_record = self.storage.get(master_id)
        return master_record.golden_record if master_record else None

    def publish_to_subscribers(self, master_id: str):
        """변경된 마스터 데이터를 구독 시스템에 발행"""
        golden_record = self.get_golden_record(master_id)
        if golden_record:
            # Kafka, RabbitMQ 등으로 발행
            self.message_queue.publish('mdm.updates', {
                'master_id': master_id,
                'golden_record': golden_record,
                'timestamp': datetime.now().isoformat()
            })

4. 실시간 vs 배치 통합

통합 방식 선택은 비즈니스 요구사항과 기술적 제약을 모두 고려해야 합니다.

구분 실시간 통합 배치 통합
데이터 지연시간 밀리초~초 단위 시간~일 단위
복잡도 높음 (이벤트 처리, 오류 처리) 중간 (스케줄링, 재시도)
비용 높음 (인프라, 운영) 낮음
적용 사례 전자상거래, 실시간 개인화, 사기 탐지 분석, 보고, 데이터 웨어하우스
기술 스택 Kafka, Flink, Spark Streaming Airflow, Luigi, Cron
데이터 볼륨 소량, 빈번 대량, 주기적

하이브리드 통합 전략

많은 조직에서 실시간과 배치 통합을 조합하여 사용합니다:

  • Lambda 아키텍처: 실시간 스트림 처리 + 배치 처리를 병렬로 운영
  • Kappa 아키텍처: 모든 데이터를 스트림으로 처리 (배치 제거)
  • 계층화 접근: 중요 데이터는 실시간, 나머지는 배치

5. 클라우드 MDM 아키텍처

클라우드 네이티브 MDM은 확장성, 탄력성, 비용 효율성을 제공합니다.

AWS 기반 MDM 아키텍처 예시

# AWS CloudFormation 템플릿 (YAML)
AWSTemplateFormatVersion: '2010-09-09'
Description: 'Cloud-Native MDM Architecture on AWS'

Resources:
  # 데이터 수집 계층
  IngestionQueue:
    Type: AWS::SQS::Queue
    Properties:
      QueueName: mdm-ingestion-queue
      VisibilityTimeout: 300
      MessageRetentionPeriod: 1209600  # 14일

  IngestionTopic:
    Type: AWS::SNS::Topic
    Properties:
      TopicName: mdm-ingestion-events
      Subscription:
        - Endpoint: !GetAtt IngestionQueue.Arn
          Protocol: sqs

  # 처리 계층
  MatchingFunction:
    Type: AWS::Lambda::Function
    Properties:
      FunctionName: mdm-matching-processor
      Runtime: python3.11
      Handler: matching.lambda_handler
      MemorySize: 1024
      Timeout: 300
      Environment:
        Variables:
          MASTER_DATA_TABLE: !Ref MasterDataTable
          SIMILARITY_THRESHOLD: '0.85'

  MergingFunction:
    Type: AWS::Lambda::Function
    Properties:
      FunctionName: mdm-merging-processor
      Runtime: python3.11
      Handler: merging.lambda_handler
      MemorySize: 2048
      Timeout: 300

  # 저장 계층
  MasterDataTable:
    Type: AWS::DynamoDB::Table
    Properties:
      TableName: master-data-records
      BillingMode: PAY_PER_REQUEST
      AttributeDefinitions:
        - AttributeName: master_id
          AttributeType: S
        - AttributeName: entity_type
          AttributeType: S
      KeySchema:
        - AttributeName: master_id
          KeyType: HASH
      GlobalSecondaryIndexes:
        - IndexName: entity-type-index
          KeySchema:
            - AttributeName: entity_type
              KeyType: HASH
          Projection:
            ProjectionType: ALL

  # API 계층
  MDMApi:
    Type: AWS::ApiGatewayV2::Api
    Properties:
      Name: mdm-api
      ProtocolType: HTTP
      CorsConfiguration:
        AllowOrigins:
          - '*'
        AllowMethods:
          - GET
          - POST
          - PUT
          - DELETE

  # 캐싱 계층
  CacheCluster:
    Type: AWS::ElastiCache::CacheCluster
    Properties:
      CacheNodeType: cache.t3.medium
      Engine: redis
      NumCacheNodes: 2
      ClusterName: mdm-cache

클라우드 MDM 모범 사례

  • 서버리스 우선: Lambda, Step Functions 활용으로 운영 부담 감소
  • 관리형 서비스: DynamoDB, RDS, DocumentDB 등 관리형 DB 사용
  • 멀티 리전 복제: 글로벌 서비스를 위한 데이터 복제
  • 자동 확장: Auto Scaling으로 트래픽 변화 대응
  • 보안 강화: IAM, KMS, VPC 엔드포인트 활용
  • 비용 최적화: Reserved Instances, Savings Plans 활용

6. 마이크로서비스와 MDM

마이크로서비스 아키텍처에서 MDM을 구현할 때는 서비스 경계와 데이터 일관성을 신중히 고려해야 합니다.

마이크로서비스 MDM 패턴

서비스 책임 API 엔드포인트
Ingestion Service 데이터 수집 및 검증 POST /api/v1/ingest
Matching Service 레코드 매칭 및 중복 탐지 POST /api/v1/match
Merging Service 레코드 병합 및 골든 레코드 생성 POST /api/v1/merge
Quality Service 데이터 품질 검증 및 점수 계산 GET /api/v1/quality/{id}
Query Service 마스터 데이터 조회 GET /api/v1/master/{id}
Sync Service 소스 시스템과 동기화 POST /api/v1/sync

7. 데이터 가상화와 MDM

데이터 가상화는 물리적 데이터 이동 없이 여러 소스를 통합하는 기술입니다.

데이터 가상화 장단점

장점 단점
실시간 데이터 접근 소스 시스템 성능 의존
데이터 중복 최소화 복잡한 쿼리 시 성능 저하
빠른 구축 시간 네트워크 지연 영향
항상 최신 데이터 소스 시스템 장애 시 영향

8. 구현 사례 비교

실제 기업들의 MDM 아키텍처 구현 사례를 비교합니다.

기업 산업 아키텍처 스타일 주요 기술 핵심 성과
글로벌 은행 A 금융 Hub-and-Spoke Oracle MDM, IBM InfoSphere 고객 중복 70% 감소

10. 요약 및 핵심 포인트

마스터 데이터 통합 아키텍처 선택은 조직의 전략적 목표, 기술 환경, 비즈니스 요구사항을 종합적으로 고려해야 합니다.

핵심 요약:
  • Registry 스타일은 경량이고 빠르지만, 기능이 제한적
  • Hub-and-Spoke는 강력하지만 복잡하고 비용이 높음
  • 클라우드 네이티브 아키텍처는 확장성과 유연성 제공
  • 마이크로서비스 MDM은 이벤트 기반 통신이 핵심
  • 실시간과 배치 통합을 하이브리드로 조합하는 것이 현실적
  • 데이터 가상화는 특정 사용 사례에서 유용

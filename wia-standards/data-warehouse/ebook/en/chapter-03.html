Chapter 3

Star Schema and Snowflake Schema

3.1 Star Schema

The star schema is the simplest and most widely used dimensional model. It consists of a central fact table surrounded by denormalized dimension tables, resembling a star when visualized.

Star Schema Structure

┌──────────────┐
│ dim_customer │
└──────┬───────┘
       │
┌──────┴───────┐     ┌─────────────┐
│  dim_date    │─────│  fact_sales │─────┐
└──────────────┘     └─────────────┘     │
                            │              │
                     ┌──────┴──────┐ ┌────┴────────┐
                     │ dim_product │ │ dim_store   │
                     └─────────────┘ └─────────────┘

Advantages

  • Simplicity: Easy to understand and query
  • Performance: Fewer joins needed
  • Query speed: Optimized for SELECT operations
  • BI tool friendly: Most tools work well with star schemas

Disadvantages

  • Data redundancy: Denormalized dimensions duplicate data
  • Storage: Requires more disk space
  • Updates: Dimension updates affect multiple rows

3.2 Snowflake Schema

The snowflake schema extends the star schema by normalizing dimension tables into multiple related tables, creating a snowflake-like structure.

When to Use Snowflake

  • Storage is a critical concern
  • Dimension tables are very large
  • Multiple hierarchies exist within dimensions
  • Data integrity is paramount

3.3 Galaxy Schema (Fact Constellation)

A galaxy schema contains multiple fact tables that share dimension tables. This is common in enterprise data warehouses with multiple business processes.

3.4 Schema Comparison

Feature Star Schema Snowflake Schema
Complexity Simple Complex
Query Performance Faster Slower
Storage More space Less space
Maintenance Easier More difficult

3.5 Best Practices

💡 Schema Design Guidelines

  • Start with star schema for simplicity
  • Use snowflake only when storage is critical
  • Keep fact tables narrow (fewer columns)
  • Use surrogate keys for all dimensions
  • Index foreign keys in fact tables

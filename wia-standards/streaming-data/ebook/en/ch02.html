Chapter 2: Streaming Architecture Patterns

2.1 Overview of Streaming Architectures

Streaming architectures define how data flows through a system, from ingestion to processing to storage and serving. The choice of architecture significantly impacts system performance, complexity, and maintainability. This chapter explores the most common and effective patterns for building streaming data systems.

2.2 Lambda Architecture

Introduced by Nathan Marz, Lambda Architecture is a data-processing architecture designed to handle massive quantities of data by taking advantage of both batch and stream processing methods.

2.2.1 Architecture Components

Three-Layer Design:
  1. Batch Layer: Manages the master dataset (immutable, append-only) and pre-computes batch views
  2. Speed Layer: Processes data in real-time, computing real-time views from recent data
  3. Serving Layer: Indexes and serves batch and real-time views for fast querying
// Lambda Architecture Flow
Data Sources
    ↓
    ├─→ Batch Layer (Hadoop/Spark)
    │   ├─→ Master Dataset (HDFS)
    │   └─→ Batch Views (Pre-computed)
    │
    └─→ Speed Layer (Storm/Flink)
        └─→ Real-time Views (Recent data)
            ↓
        Serving Layer (HBase/Cassandra)
            ↓
        Query API

2.2.2 Advantages

  • Accuracy: Batch layer ensures accurate results from complete data
  • Low latency: Speed layer provides immediate results
  • Fault tolerance: Batch layer can recompute from master dataset if speed layer fails
  • Scalability: Each layer can scale independently

2.2.3 Disadvantages

  • Complexity: Maintaining two separate code paths for batch and stream
  • Operational overhead: Running and monitoring two processing systems
  • Resource intensive: Requires infrastructure for both batch and streaming
  • Code duplication: Same logic often written twice
Use Case: Lambda Architecture is ideal when you need both real-time and accurate historical views, such as financial reporting systems that require immediate alerts but also precise monthly reconciliation.

2.3 Kappa Architecture

Proposed by Jay Kreps as a simplification of Lambda Architecture, Kappa Architecture eliminates the batch layer, using only stream processing for both real-time and historical data.

2.3.1 Core Principles

Stream-First Design:
  • Everything is a stream – both real-time and historical data
  • Single code path for all processing
  • Reprocessing handled by replaying event streams
  • Stream storage (Kafka) acts as the source of truth
// Kappa Architecture Flow
Data Sources
    ↓
Event Stream (Kafka)
    ↓
Stream Processing Layer (Flink/Kafka Streams)
    ↓
Materialized Views / State Stores
    ↓
Query API / Applications

2.3.2 Reprocessing Strategy

When logic changes or bugs are fixed, Kappa Architecture handles reprocessing through:

  1. Deploy new version of stream processor alongside old one
  2. New processor reads from beginning of event log
  3. Once caught up, switch queries to new processor
  4. Deprecate old processor

2.3.3 Advantages

  • Simplicity: Single processing framework and codebase
  • Lower operational overhead: One system to maintain
  • Real-time by default: All data processed as streams
  • Flexible reprocessing: Easy to replay and recompute

2.3.4 Disadvantages

  • Stream storage requirements: Must retain all historical data in event log
  • Reprocessing time: Can be slow for large datasets
  • Limited to stream-friendly operations: Some batch operations don't translate well

2.4 Lambda vs Kappa: Comparison

Aspect Lambda Architecture Kappa Architecture
Processing Layers Batch + Speed + Serving Stream + Serving
Code Complexity High (duplicate logic) Low (single codebase)
Latency Mixed (instant + delayed) Consistently low
Accuracy Eventual (batch reconciles) Depends on stream processing
Reprocessing Batch layer reruns Replay event streams
Storage Data lake + stream buffer Event log (Kafka)
Best For Complex analytics, reporting Event-driven systems, real-time apps

2.5 Event-Driven Architecture (EDA)

Event-Driven Architecture is a software design pattern where system components communicate through the production, detection, consumption, and reaction to events.

2.5.1 Core Components

Component Role Example
Event Producers Generate and publish events User service emits "UserRegistered" event
Event Broker Route events to consumers Kafka, Pulsar, RabbitMQ
Event Consumers React to events Email service sends welcome email
Event Store Persist event history Event sourcing database

2.5.2 EDA Patterns

Event Notification

// Producer notifies consumers of state changes
userService.register(user) {
    saveUser(user);
    eventBus.publish('UserRegistered', {
        userId: user.id,
        email: user.email,
        timestamp: new Date()
    });
}

// Consumers react independently
emailService.on('UserRegistered', async (event) => {
    await sendWelcomeEmail(event.email);
});

analyticsService.on('UserRegistered', async (event) => {
    await trackNewUser(event.userId);
});

Event-Carried State Transfer

// Events carry full state, reducing need for queries
orderService.publish('OrderPlaced', {
    orderId: 'order-123',
    userId: 'user-456',
    items: [...],
    totalAmount: 299.99,
    shippingAddress: {...},
    // Full order details included
});

// Consumers don't need to query order service
shippingService.on('OrderPlaced', (event) => {
    // Has all info needed to ship
    createShipment(event.items, event.shippingAddress);
});

Event Sourcing

// Store all state changes as events
const events = [
    { type: 'OrderCreated', data: {...} },
    { type: 'ItemAdded', data: {...} },
    { type: 'ItemRemoved', data: {...} },
    { type: 'OrderPaid', data: {...} }
];

// Rebuild current state by replaying events
function getCurrentState(orderId) {
    const events = eventStore.getEvents(orderId);
    return events.reduce((state, event) => {
        return applyEvent(state, event);
    }, initialState);
}

2.6 Microservices with Event Streaming

Event streaming provides an ideal communication mechanism for microservices architectures, enabling loose coupling and asynchronous processing.

2.6.1 Benefits

  • Loose coupling: Services don't need to know about each other
  • Scalability: Each service scales independently
  • Resilience: Service failures don't propagate
  • Evolution: Easy to add new services and features

2.6.2 Communication Patterns

Choreography: Services react to events autonomously 
Order Service → "OrderPlaced" → Kafka
                          ↓
    ┌──────────────────┼──────────────────┐
    ↓                  ↓                  ↓
Payment Service   Inventory Service   Notification Service
Orchestration: Central coordinator manages workflow 
Order Orchestrator
    ↓ (command)
Payment Service
    ↓ (event: PaymentCompleted)
Order Orchestrator
    ↓ (command)
Inventory Service
    ↓ (event: InventoryReserved)
Order Orchestrator
    ↓ (command)
Shipping Service

2.7 CQRS (Command Query Responsibility Segregation)

CQRS separates read and write operations into different models, often combined with event sourcing for powerful streaming architectures.

2.7.1 Architecture

// Write side (Commands)
Command → Command Handler → Aggregate → Events → Event Store
                                              ↓
                                        Event Bus
                                              ↓
// Read side (Queries)
Event Handlers → Update Read Models → Query API

2.7.2 Implementation Example

// Command side
class OrderService {
    async placeOrder(command: PlaceOrderCommand) {
        const order = new Order(command.items);
        order.validate();

        const event = {
            type: 'OrderPlaced',
            data: order.toJSON(),
            timestamp: new Date()
        };

        await eventStore.append('orders', event);
        await eventBus.publish('OrderPlaced', event);
    }
}

// Query side - Multiple read models
class OrderQueryService {
    // Optimized for order history
    async getOrderHistory(userId) {
        return orderHistoryDb.find({ userId });
    }

    // Optimized for analytics
    async getSalesMetrics() {
        return metricsDb.aggregate([...]);
    }
}

// Event handler keeps read models in sync
eventBus.on('OrderPlaced', async (event) => {
    await orderHistoryDb.insert(event.data);
    await metricsDb.incrementSales(event.data.amount);
});

2.7.3 Advantages

  • Optimized reads and writes: Each side optimized for its purpose
  • Scalability: Scale read and write sides independently
  • Multiple views: Create specialized read models for different use cases
  • Event sourcing synergy: Natural fit with event-driven systems

2.8 Data Mesh Architecture

Data Mesh is a decentralized approach to data architecture, treating data as a product owned by domain teams, with streaming playing a key role in data distribution.

2.8.1 Principles

  1. Domain-oriented decentralization: Each domain owns its data products
  2. Data as a product: Treat data with product thinking
  3. Self-serve data infrastructure: Platform enables autonomous domain teams
  4. Federated computational governance: Balance autonomy with standards

2.8.2 Streaming in Data Mesh

// Each domain publishes data products as streams
User Domain → user-events stream (Kafka topic)
Order Domain → order-events stream
Product Domain → product-events stream

// Domains consume from other domains
Recommendation Domain subscribes to:
    - user-events (behavioral data)
    - order-events (purchase history)
    - product-events (catalog updates)

2.9 Hybrid Architectures

Real-world systems often combine multiple patterns to balance requirements:

2.9.1 Lambda + Event Sourcing

  • Event sourcing for write model
  • Speed layer for real-time aggregations
  • Batch layer for complex analytics

2.9.2 Kappa + CQRS

  • Stream processing for all data flows
  • Separate read/write models
  • Multiple specialized read models from same event stream

2.10 Choosing the Right Architecture

Requirement Recommended Architecture Why
Real-time + complex batch analytics Lambda Leverages strengths of both batch and stream
Pure real-time, event-driven Kappa Simplicity, single codebase
Microservices communication Event-Driven Loose coupling, scalability
Audit trail, temporal queries Event Sourcing Complete history, replayability
Read/write performance optimization CQRS Separate optimization of each side
Large organization, domain autonomy Data Mesh Decentralization, domain ownership

2.11 Summary

Streaming architecture patterns provide proven blueprints for building scalable, maintainable data systems. Key takeaways:

  • Lambda Architecture: Combines batch and stream for accuracy and low latency
  • Kappa Architecture: Stream-only simplification of Lambda
  • Event-Driven Architecture: Enables loose coupling through event communication
  • CQRS: Separates reads and writes for optimization
  • Data Mesh: Decentralizes data ownership across domains

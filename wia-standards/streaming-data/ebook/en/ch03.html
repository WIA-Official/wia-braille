Chapter 3: Apache Kafka Deep Dive

3.1 Kafka Architecture Overview

Apache Kafka is a distributed event streaming platform capable of handling trillions of events per day. Originally developed at LinkedIn, Kafka has become the de facto standard for event streaming.

3.1.1 Core Components

Component Description Role
Broker Kafka server instance Stores and serves data
Topic Logical channel for events Categorizes event streams
Partition Ordered, immutable sequence Enables parallelism
Producer Publishes events to topics Data ingestion
Consumer Reads events from topics Data consumption
ZooKeeper/KRaft Cluster coordination Metadata management

3.2 Topics and Partitions

Topics are the fundamental abstraction in Kafka. Each topic is divided into partitions for scalability.

// Topic structure
Topic: user-events
├── Partition 0: [evt0, evt3, evt6, ...]
├── Partition 1: [evt1, evt4, evt7, ...]
└── Partition 2: [evt2, evt5, evt8, ...]

// Each partition is an ordered log
Partition 0:
Offset: 0    1    2    3    4    5    ...
       [A] [B] [C] [D] [E] [F] ...

3.2.1 Partition Key Selection

// Hash-based partitioning
producer.send({
    topic: 'orders',
    key: userId,  // Same user → same partition
    value: orderData
});

// Custom partitioner
class RegionPartitioner {
    partition(key, numPartitions) {
        const region = extractRegion(key);
        return regionMap[region] % numPartitions;
    }
}

3.3 Producers

3.3.1 Producer Configuration

const producer = kafka.producer({
    // Idempotence ensures exactly-once semantics
    idempotent: true,

    // Batching for throughput
    batch: {
        size: 16384,        // 16KB batch
        lingerMs: 10        // Wait up to 10ms
    },

    // Compression
    compression: CompressionTypes.GZIP,

    // Acks configuration
    acks: -1,  // All in-sync replicas

    // Retry configuration
    retry: {
        retries: 5,
        initialRetryTime: 300
    }
});

3.3.2 Delivery Guarantees

Setting Guarantee Use Case
acks=0 At-most-once Metrics, logs (ok to lose)
acks=1 At-least-once General use
acks=-1 + idempotent Exactly-once Financial transactions

3.4 Consumers and Consumer Groups

// Consumer group enables parallel processing
const consumer = kafka.consumer({
    groupId: 'analytics-group'
});

await consumer.subscribe({
    topics: ['user-events', 'order-events']
});

await consumer.run({
    eachMessage: async ({ topic, partition, message }) => {
        await processEvent(message.value);
        // Auto-commit or manual commit
    }
});

3.4.1 Consumer Group Rebalancing

// Before rebalance
Consumer Group: analytics-group
├── Consumer A: [P0, P1]
└── Consumer B: [P2, P3]

// After Consumer C joins
Consumer Group: analytics-group
├── Consumer A: [P0]

3.5 Replication and Fault Tolerance

// Topic with replication factor 3
Partition 0:
├── Leader: Broker 1 (handles reads/writes)
└── Followers: Broker 2, Broker 3 (replicas)

// If Broker 1 fails:
Partition 0:
├── Leader: Broker 2 (promoted)
└── Follower: Broker 3

3.5.1 In-Sync Replicas (ISR)

  • Replicas that are caught up with leader
  • Only ISR can be elected as leader
  • min.insync.replicas ensures durability

3.7 Performance Optimization

3.7.1 Producer Optimization

  • Batching: Combine multiple messages
  • Compression: Reduce network/disk I/O
  • Pipelining: Multiple in-flight requests
  • Async sending: Don't wait for acknowledgment

3.7.2 Consumer Optimization

  • Fetch size: Larger batches per poll
  • Parallel processing: Multiple consumer instances
  • Offset management: Manual commit for control
  • Deserialization: Efficient formats (Avro, Protobuf)

3.9 Kafka Streams

// Stream processing with Kafka Streams
StreamsBuilder builder = new StreamsBuilder();

KStream orders = builder.stream("orders");

// Stateless transformations
KStream highValueOrders = orders
    .filter((key, order) -> order.getAmount() > 1000)
    .mapValues(order -> enrichOrder(order));

// Stateful aggregation
KTable orderCounts = orders
    .groupByKey()
    .windowedBy(TimeWindows.of(Duration.ofMinutes(5)))
    .count();

// Write to output topic
highValueOrders.to("high-value-orders");
orderCounts.toStream().to("order-counts");

3.10 Monitoring Kafka

3.10.1 Key Metrics

Metric Description Alert Threshold
Consumer Lag Messages behind current offset > 1000 messages
Request Rate Requests per second Near capacity
Under-replicated Partitions Partitions without all replicas > 0
ISR Shrink Rate Replicas falling out of sync > 0
Disk Usage Storage consumption > 80%

3.11 Security

  • SSL/TLS: Encrypt data in transit
  • SASL: Authentication (PLAIN, SCRAM, GSSAPI)
  • ACLs: Authorization for topics and consumer groups
  • Quotas: Rate limiting per client

3.12 Best Practices

  1. Use appropriate replication factor (3 for production)
  2. Monitor consumer lag continuously
  3. Choose partition keys carefully for even distribution
  4. Enable compression for large messages
  5. Use Schema Registry for schema evolution
  6. Implement proper error handling and dead-letter queues
  7. Plan capacity for peak load + 50% headroom
  8. Regular backups and disaster recovery testing

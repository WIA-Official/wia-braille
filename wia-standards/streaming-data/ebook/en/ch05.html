Chapter 5: Event Sourcing and CQRS

5.1 Event Sourcing Fundamentals

Event Sourcing is a pattern where state changes are stored as a sequence of events rather than updating current state directly.

5.1.1 Traditional vs Event Sourcing

AspectTraditional (CRUD)Event Sourcing
StorageCurrent state onlyAll events (history)
UpdatesUPDATE queryAppend event
HistoryLost or separate audit logBuilt-in complete audit trail
DebuggingDifficult to reproduceReplay events to any point in time

5.1.2 Event Sourcing Example

// Traditional approach
UPDATE orders SET status = 'shipped' WHERE id = 123;
// Previous status lost!

// Event Sourcing approach
Event Stream for Order 123:
1. OrderCreated { items: [...], total: 99.99 }
2. PaymentReceived { amount: 99.99, method: 'card' }
3. OrderShipped { carrier: 'UPS', tracking: 'ABC123' }
// Complete history preserved!

5.2 Implementing Event Sourcing

5.2.1 Event Store

class EventStore {
    async append(streamId, event) {
        const record = {
            streamId,
            eventType: event.type,
            eventData: event.data,
            timestamp: new Date(),
            version: await this.getNextVersion(streamId)
        };
        await db.events.insert(record);
        await eventBus.publish(event);
    }

    async getEvents(streamId, fromVersion = 0) {
        return await db.events.find({
            streamId,
            version: { $gte: fromVersion }
        }).sort({ version: 1 });
    }

    async replayTo(streamId, targetVersion) {
        const events = await this.getEvents(streamId);
        return events
            .filter(e => e.version <= targetVersion)
            .reduce((state, event) => applyEvent(state, event), {});
    }
}

5.2.2 Aggregate Pattern

class OrderAggregate {
    constructor(orderId) {
        this.orderId = orderId;
        this.uncommittedEvents = [];
        this.version = 0;
    }

    // Command handlers (business logic)
    createOrder(items, customerId) {
        if (this.version > 0) throw new Error('Order already exists');
        
        this.applyEvent({
            type: 'OrderCreated',
            data: { orderId: this.orderId, items, customerId }
        });
    }

    shipOrder(carrier, trackingNumber) {
        if (this.status !== 'paid') throw new Error('Order not paid');
        
        this.applyEvent({
            type: 'OrderShipped',
            data: { carrier, trackingNumber }
        });
    }

    // Event application (state changes)
    applyEvent(event) {
        switch (event.type) {
            case 'OrderCreated':
                this.status = 'created';
                this.items = event.data.items;
                break;
            case 'OrderShipped':
                this.status = 'shipped';
                this.tracking = event.data.trackingNumber;
                break;
        }
        this.version++;
        this.uncommittedEvents.push(event);
    }

    async save(eventStore) {
        for (const event of this.uncommittedEvents) {
            await eventStore.append(this.orderId, event);
        }
        this.uncommittedEvents = [];
    }
}

5.3 Benefits of Event Sourcing

  • Complete Audit Trail: Every state change is recorded
  • Temporal Queries: View system state at any point in time
  • Event Replay: Reprocess events to fix bugs or add features
  • Event-Driven Architecture: Natural fit for microservices
  • Debugging: Reproduce exact sequence of events
  • Analytics: Rich data for business intelligence

5.4 CQRS (Command Query Responsibility Segregation)

CQRS separates read and write operations into different models, optimizing each for its specific purpose.

5.4.1 CQRS Architecture

// Write side (Commands)
User → Command → Command Handler → Aggregate → Events → Event Store
                                                           ↓
                                                      Event Bus
                                                           ↓
// Read side (Queries)
                                Event Handlers → Projections (Read Models)
                                                           ↓
User ← Query Results ← Query Handlers ← Read Database (optimized views)

5.4.2 Implementation

// Command side
class PlaceOrderCommand {
    constructor(orderId, items, customerId) {
        this.orderId = orderId;
        this.items = items;
        this.customerId = customerId;
    }
}

class OrderCommandHandler {
    async handle(command) {
        const order = new OrderAggregate(command.orderId);
        order.createOrder(command.items, command.customerId);
        await eventStore.save(order);
    }
}

// Query side - Projection 1: Order History
class OrderHistoryProjection {
    async on(event) {
        if (event.type === 'OrderCreated') {
            await orderHistoryDb.insert({
                orderId: event.data.orderId,
                customerId: event.data.customerId,
                items: event.data.items,
                createdAt: event.timestamp,
                status: 'created'
            });
        }
        else if (event.type === 'OrderShipped') {
            await orderHistoryDb.update(
                { orderId: event.data.orderId },
                { $set: { status: 'shipped', shippedAt: event.timestamp } }
            );
        }
    }
}

// Query side - Projection 2: Sales Analytics
class SalesAnalyticsProjection {
    async on(event) {
        if (event.type === 'OrderCreated') {
            const total = calculateTotal(event.data.items);
            await analyticsDb.incrementDailySales(event.timestamp, total);
            await analyticsDb.incrementProductSales(event.data.items);
        }
    }
}

5.6 Event Sourcing + CQRS Pattern

// Combined pattern workflow
1. User submits command (PlaceOrder)
2. Command handler validates and creates events
3. Events appended to event store
4. Events published to event bus
5. Projections consume events and update read models
6. User queries read models (not event store)

Benefits:
- Write model optimized for consistency
- Read models optimized for queries
- Can have multiple specialized read models
- Eventual consistency between write and read sides

5.7 Handling Complexity

5.7.1 Snapshotting

// Problem: Replaying 1 million events is slow
// Solution: Periodic snapshots

class SnapshotStore {
    async createSnapshot(streamId, state, version) {
        await db.snapshots.insert({
            streamId,
            state,
            version,
            timestamp: new Date()
        });
    }

    async getLatestSnapshot(streamId) {
        return await db.snapshots.findOne(
            { streamId },
            { sort: { version: -1 } }
        );
    }
}

async function loadAggregate(streamId) {
    const snapshot = await snapshotStore.getLatestSnapshot(streamId);
    const events = await eventStore.getEvents(streamId, snapshot.version + 1);
    
    let state = snapshot ? snapshot.state : {};
    return events.reduce((state, event) => applyEvent(state, event), state);
}

5.7.2 Event Versioning

// V1 event
{
    type: 'OrderCreated',
    version: 1,
    data: {
        orderId: '123',
        items: [...]
    }
}

// V2 event (added customer info)
{
    type: 'OrderCreated',
    version: 2,
    data: {
        orderId: '123',
        customerId: '456',  // new field
        items: [...]
    }
}

// Upcaster pattern
class EventUpcaster {
    upcast(event) {
        if (event.type === 'OrderCreated' && event.version === 1) {
            return {
                ...event,
                version: 2,
                data: {
                    ...event.data,
                    customerId: 'UNKNOWN'  // default for old events
                }
            };
        }
        return event;
    }
}

5.8 Saga Pattern for Distributed Transactions

// Orchestration-based saga
class OrderSaga {
    async execute(orderId) {
        try {
            // Step 1: Reserve inventory
            await inventoryService.reserve(orderId);
            
            // Step 2: Process payment
            await paymentService.charge(orderId);
            
            // Step 3: Ship order
            await shippingService.ship(orderId);
            
            await this.complete(orderId);
        } catch (error) {
            await this.compensate(orderId, error);
        }
    }

    async compensate(orderId, error) {
        // Rollback in reverse order
        await shippingService.cancelShipment(orderId);
        await paymentService.refund(orderId);
        await inventoryService.release(orderId);
        await this.fail(orderId, error);
    }
}

// Choreography-based saga (event-driven)
inventoryService.on('InventoryReserved', async (event) => {
    await paymentService.processPayment(event.orderId);
});

paymentService.on('PaymentProcessed', async (event) => {
    await shippingService.shipOrder(event.orderId);
});

paymentService.on('PaymentFailed', async (event) => {
    await inventoryService.releaseInventory(event.orderId);
});

5.11 Best Practices

  1. Events should be past tense (OrderCreated, not CreateOrder)
  2. Events are immutable - never modify published events
  3. Use snapshots for aggregates with many events
  4. Version events from day one
  5. Keep events small and focused
  6. Use correlation IDs for tracing
  7. Monitor projection lag
  8. Test event replay scenarios

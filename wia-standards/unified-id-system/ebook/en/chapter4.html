Chapter 4: Phase 1 - Data Format

In this chapter: We dive into the technical details of the unified ID data format, including JSON schema definitions, field mappings, validation rules, and migration strategies for legacy data from both North and South Korean systems.

4.1 Core Data Schema

The WIA-UNI-002 data format uses JSON as the primary serialization format for its human-readability, widespread tooling support, and ease of validation. Here's the core schema for a unified ID record: 

{
  "version": "1.0",
  "standard": "WIA-UNI-002",
  "unifiedId": "UNI-KR-900515-1234",
  "personalInfo": {
    "familyName": "Kim",
    "givenName": "MinJun",
    "fullName": "Kim MinJun",
    "birthDate": "1990-05-15",
    "gender": "M"
  },
  "origin": {
    "region": "south",
    "previousId": "900515-1234567",
    "registrationDate": "2025-01-15T09:00:00Z"
  },
  "biometric": {
    "fingerprintHash": "sha256:a1b2c3d4...",
    "facialHash": "sha256:e5f6g7h8...",
    "irisHash": null
  },
  "issuedAt": "2025-01-15T09:30:00Z",
  "expiresAt": "2035-01-15T00:00:00Z",
  "issuer": "did:wia:unified-korea-authority",
  "status": "active",
  "privacyLevel": "protected"
}

4.2 Field Definitions

Each field in the unified ID record has specific validation rules and privacy implications:

Field Type Required Privacy Level
unifiedId String Yes Public (non-reversible to PII)
personalInfo.familyName String Yes Protected (encrypted at rest)
personalInfo.givenName String Yes Protected
personalInfo.birthDate Date (ISO 8601) Yes Sensitive (ZK proofs only)
origin.region Enum (north/south/unified) Yes Highly Sensitive (encrypted)
origin.previousId String No Highly Sensitive
biometric.*Hash String (hex) At least 1 Hashed (irreversible)

4.3 Unified ID Format

The unified ID itself follows a specific format designed to be both human-readable and privacy-preserving:

Format: UNI-KR-YYMMDD-NNNN

  • UNI: Universal prefix indicating Unified ID
  • KR: Country code (Korea)
  • YYMMDD: Birth date (last 2 digits of year, month, day)
  • NNNN: Random 4-digit serial number (NOT sequential)

Privacy Note: The random serial number prevents enumeration attacks and makes it impossible to determine origin region from the ID alone.

4.4 Biometric Data Handling

Biometric data is never stored in plaintext. Instead, the system stores cryptographic hashes that can be used for matching but not reconstruction:

Fingerprint Processing

  • Capture: High-resolution fingerprint scanner (500+ DPI)
  • Feature Extraction: Minutiae points extracted (30-60 points)
  • Template Generation: Secure biometric template (irreversible)
  • Hashing: SHA-256 hash of template stored in record

Facial Recognition

  • Capture: 2D color photograph + optional 3D scan
  • Embedding: Deep learning model generates 128D embedding
  • Hashing: Embedding hashed with keyed hash function
  • Privacy: Original photo never stored in centralized database

4.5 Legacy Data Migration

Converting existing North and South Korean ID records to the unified format requires careful mapping:

South Korean RRN Migration

RRN Field Unified ID Field Transformation
YYMMDD personalInfo.birthDate Parse and expand to full ISO 8601 date
G (gender) personalInfo.gender Map 1/3→M, 2/4→F
Full RRN origin.previousId Store encrypted for audit trail
Registration DB personalInfo.fullName Lookup in existing database

North Korean Record Migration

North Korean paper records require more extensive processing:

  1. Digitization: OCR scanning of physical registration books
  2. Name Extraction: Parse handwritten Korean names (AI-assisted)
  3. Date Conversion: Convert Juche calendar to Gregorian
  4. Quality Check: Manual verification for low-confidence OCR results
  5. Biometric Capture: In-person enrollment required for biometrics

4.6 Validation Rules

All unified ID records must pass validation before being accepted:

Required Field Validation

function validateUnifiedId(record) {
  // Check required fields
  if (!record.unifiedId || !record.personalInfo || !record.issuer) {
    throw new Error("Missing required fields");
  }

  // Validate ID format
  const idPattern = /^UNI-KR-\d{6}-\d{4}$/;
  if (!idPattern.test(record.unifiedId)) {
    throw new Error("Invalid unified ID format");
  }

  // Validate birth date
  const birthDate = new Date(record.personalInfo.birthDate);
  if (isNaN(birthDate.getTime())) {
    throw new Error("Invalid birth date");
  }

  // Ensure at least one biometric hash
  const biometrics = record.biometric;
  if (!biometrics.fingerprintHash && !biometrics.facialHash && !biometrics.irisHash) {
    throw new Error("At least one biometric hash required");
  }

  return true;
}

4.8 Interoperability Formats

WIA-UNI-002 supports multiple serialization formats for different use cases:

Format Use Case Features
JSON APIs, web applications Human-readable, widely supported
JSON-LD Verifiable Credentials Linked data, semantic web
Protocol Buffers High-performance systems Compact, fast serialization
CBOR IoT, offline devices Binary, minimal overhead
QR Code Physical verification Camera-readable, no internet needed

4.9 Versioning and Evolution

The data format is versioned to support future evolution while maintaining backward compatibility:

  • Version 1.0: Initial release with core fields
  • Version 1.1: (Planned) Additional biometric modalities (voice, gait)
  • Version 2.0: (Future) Quantum-resistant cryptography

All implementations must support the current version plus one previous version to ensure smooth transitions.

Chapter Summary

Key Takeaways:

  • Unified ID uses JSON format with strict validation rules
  • ID format (UNI-KR-YYMMDD-NNNN) balances readability and privacy
  • Biometric data stored as cryptographic hashes, never plaintext
  • Legacy migration tools map RRN and North Korean records to unified format
  • Supports encrypted and zero-knowledge proof variants for high-privacy scenarios
  • Multiple serialization formats for different use cases and devices

WIA-COMM-018 Standard | Low-Power Wide Area Networks

2.1 Introduction to LoRaWAN

LoRaWAN (Long Range Wide Area Network) stands out among LPWAN technologies for its unique combination of long range, low power consumption, and deployment flexibility. Unlike cellular-based solutions (NB-IoT, LTE-M), LoRaWAN operates in unlicensed ISM (Industrial, Scientific, and Medical) bands, enabling both public and private network deployments without ongoing spectrum licensing costs.

Developed by the LoRa Alliance—a global association of over 500 companies—LoRaWAN is an open standard that promotes interoperability between devices and networks from different vendors. This openness has driven rapid adoption: over 171 public LoRaWAN networks operate in 170+ countries, with millions of sensors deployed worldwide.

LoRaWAN vs. LoRa: Understanding the Difference

It's crucial to distinguish between LoRa (the physical layer modulation) and LoRaWAN (the network protocol):

  • LoRa (Physical Layer): Chirp Spread Spectrum (CSS) modulation technique developed by Semtech. Defines how data is encoded into radio waves for transmission.
  • LoRaWAN (MAC Layer & Above): Network protocol that defines device activation, encryption, network management, and message formats. Built on top of LoRa modulation.

Think of it like WiFi: LoRa is analogous to OFDM modulation, while LoRaWAN is like the 802.11 protocol that manages network operations.

2.2 Chirp Spread Spectrum Modulation

LoRa's revolutionary capability comes from Chirp Spread Spectrum (CSS) modulation—a technique originally developed for radar and military communications. CSS offers exceptional resilience to interference and enables reception of signals significantly below the noise floor.

How Chirps Work

A chirp is a sinusoidal signal whose frequency increases (up-chirp) or decreases (down-chirp) linearly over time. Imagine a sound that starts low-pitched and smoothly transitions to high-pitched—that's an audible chirp. LoRa uses radio frequency chirps in the ISM bands.

Key Properties of CSS:

  • Spreading Gain: Signal is spread across the full bandwidth (125/250/500 kHz), making it resistant to narrowband interference
  • Processing Gain: Receiver correlates incoming signal with expected chirp pattern, extracting signal from noise (up to -20 dB below noise floor)
  • Doppler Resilient: Frequency offset from motion has minimal impact, unlike FSK modulation
  • Multipath Resistant: Delayed reflections don't significantly degrade performance

Spreading Factors: The Range-Rate Tradeoff

LoRa's Spreading Factor (SF) is the most critical parameter, controlling the tradeoff between range, data rate, and power consumption. SF determines how many chirps represent each bit of data.

SF Chips/Symbol Data Rate (125kHz BW) Time on Air (10B) Link Budget Range (Urban)
SF7 128 5.5 kbps 41 ms ~126 dB 2 km
SF8 256 3.1 kbps 72 ms ~129 dB 4 km
SF9 512 1.8 kbps 144 ms ~132 dB 6 km
SF10 1024 980 bps 247 ms ~135 dB 8 km
SF11 2048 440 bps 494 ms ~138 dB 11 km
SF12 4096 250 bps 988 ms ~141 dB 14 km

Important Observations:

  • Each SF increase (SF7→SF8) doubles the time on air and halves the data rate
  • Higher SF = longer range but more battery consumption and airtime
  • Different SFs are orthogonal—transmissions don't interfere with each other
  • Gateway can receive multiple SFs simultaneously on the same frequency

2.3 LoRaWAN Network Architecture

LoRaWAN employs a star-of-stars topology, distinct from mesh networks (Zigbee) or cellular point-to-point architectures.

Network Components

1. End Devices (Nodes)

Battery-powered sensors or actuators with LoRa radio modules. Devices transmit data whenever needed (Class A) or at scheduled intervals. They don't know which gateway will receive their transmission—nor do they care.

2. Gateways (Base Stations)

Multi-channel receivers that listen on all spreading factors simultaneously. A single gateway can serve 10,000-50,000 devices. Gateways are essentially transparent bridges—they forward all received packets to the network server via IP backhaul (Ethernet, 4G, fiber) without processing or filtering. Advanced gateways support 8-16 channels and GPS synchronization for Class B operation.

3. Network Server

The brain of the LoRaWAN network. Responsibilities include:

  • Deduplication: When multiple gateways receive the same packet, select the one with best SNR
  • Device authentication and encryption key management
  • Adaptive Data Rate (ADR): Optimize SF and TX power for each device
  • Scheduling downlinks: Determine which gateway and when to send messages to devices
  • Frame counter validation for replay attack prevention

4. Application Server

Implements business logic, processes sensor data, and stores information. Communicates with network server via APIs. End-to-end encryption ensures application server is the only entity that can decrypt payload data.

2.4 Device Classes: Choosing the Right Tradeoff

LoRaWAN defines three device classes, each optimizing for different latency/power tradeoffs:

Class A: Lowest Power, Highest Latency

All LoRaWAN devices must support Class A. After each uplink transmission, the device opens two short receive windows:

Device TX ────┐ ┌RX1 (1s)──┐ ┌RX2 (2s)──┐ └────────┘ └──┘ └───────────▶ 0 1s 2s Time TX: Transmit uplink RX1: First receive window (1s after TX end) RX2: Second receive window (2s after TX end, different freq)
  • Uplink: Anytime, asynchronous (when sensor has data)
  • Downlink: Only in RX windows after uplink (server must wait for device to transmit)
  • Power: Ultra-low (sleep current 1-5 µA, 10-15 year battery)
  • Latency: Depends on uplink interval (could be hours if device transmits once daily)
  • Use Cases: Sensors with infrequent updates (soil moisture, temperature, utility meters)

Class B: Scheduled Downlinks, Medium Power

Class B devices synchronize with network beacons (transmitted by gateways every 128 seconds) and open additional receive windows ("ping slots") at scheduled times:

  • Uplink: Anytime (like Class A)
  • Downlink: After uplink + during scheduled ping slots (every 0.96 to 122.88 seconds)
  • Power: Medium (5-10 year battery, depending on ping slot frequency)
  • Latency: Maximum of ping slot interval (e.g., 30 seconds if ping every 30s)
  • Use Cases: Streetlights, irrigation valves, smart locks requiring timely downlinks

Class C: Continuous RX, Highest Power

Class C devices keep receiver open continuously except when transmitting:

  • Uplink: Anytime
  • Downlink: Anytime (server can send immediately, ~1 second latency)
  • Power: High (RX current 10-15 mA continuously, months on battery or mains-powered)
  • Latency: Minimal (~1 second)
  • Use Cases: Actuators requiring immediate commands (emergency lighting, alarms), mains-powered devices

2.5 Device Activation: OTAA vs ABP

Before a device can communicate, it must join the network and establish session keys. LoRaWAN supports two activation methods:

OTAA (Over-the-Air Activation) - Recommended

Devices perform a join procedure that dynamically generates session keys:

OTAA Join Procedure: 1. Device sends Join Request: DevEUI: 0x0123456789ABCDEF (unique device ID, like MAC address) AppEUI: 0xFEDCBA9876543210 (application ID) DevNonce: 0x1234 (random number, prevents replay) MIC: Message Integrity Code (signed with AppKey) 2. Network Server validates request and responds with Join Accept: AppNonce: 0x5678 (random from server) NetID: Network identifier DevAddr: 0x01AB23CD (32-bit device address, assigned dynamically) DLSettings: RX1 delay, RX2 data rate RxDelay: Delay between TX and RX1 window 3. Device and Server derive session keys: NwkSKey = aes128_encrypt(AppKey, AppNonce | NetID | DevNonce | pad) AppSKey = aes128_encrypt(AppKey, AppNonce | NetID | DevNonce | pad | 0x01) 4. Device can now send encrypted data using session keys Security Benefits: - Session keys change on each join (if device loses power, new keys generated) - AppKey never transmitted over the air - DevNonce prevents replay of join requests - Supports network roaming

ABP (Activation By Personalization) - Less Secure

Session keys are hardcoded into the device during manufacturing or provisioning. No join procedure occurs—device can transmit immediately after power-on.

Disadvantages:

  • Frame counter reset risk: If device loses power and restarts with counter=0, network server rejects packets (sees as replay attack)
  • No key refresh: Compromised keys remain valid indefinitely
  • Manual provisioning: Each device requires unique key injection
  • No roaming support

When to use ABP: Manufacturing test fixtures, controlled environments where power cycling is rare, or when join latency is unacceptable (e.g., emergency sensors that must transmit immediately after power-on).

2.6 LoRaWAN Security Architecture

LoRaWAN implements a two-layer encryption model providing both network-level and application-level security:

Security Layer Key Used Purpose Who Can Decrypt
Network Security NwkSKey MIC validation, MAC commands encryption Network Server
Application Security AppSKey Payload encryption Application Server only

This architecture ensures that even if the network operator is untrusted, they cannot read application payloads. Only the application server (controlled by the device owner) holds AppSKey.

Encryption Process

AES-128 CTR Mode Encryption: Plaintext: "Hello World" (application payload) AppSKey: 0x2B7E151628AED2A6ABF7158809CF4F3C FCnt: 42 (frame counter) DevAddr: 0x01AB23CD Direction: 0x00 (uplink) 1. Build encryption block Ai: Ai = [0x01, 0x00, 0x00, 0x00, 0x00, Direction, DevAddr, FCnt, 0x00, i] 2. Generate keystream Si: Si = AES128_Encrypt(AppSKey, Ai) 3. XOR with plaintext: Ciphertext = Plaintext ⊕ Si Frame Counter (FCnt) Security: - 16-bit counter increments with each uplink (separate counter for downlink) - Network server rejects packets with FCnt ≤ previous FCnt - Prevents replay attacks - Device must re-join if counter reaches 65535 (or implement 32-bit counter)

Key Takeaways

  • LoRaWAN uses Chirp Spread Spectrum (CSS) modulation, enabling reception of signals 20 dB below the noise floor for exceptional range
  • Spreading Factor (SF7-SF12) controls the range/rate tradeoff: higher SF = longer range but slower data rate and more power consumption
  • Star-of-stars architecture with transparent gateways simplifies deployment—devices don't need routing logic or mesh capabilities
  • Three device classes (A, B, C) offer different latency/power tradeoffs: Class A for ultra-low power, Class C for low latency
  • OTAA activation is strongly preferred over ABP for security reasons—session keys refresh on each join
  • Two-layer encryption (NwkSKey + AppSKey) ensures network operators cannot read application payloads
  • Adaptive Data Rate (ADR) automatically optimizes SF and TX power, dramatically extending battery life and improving network capacity

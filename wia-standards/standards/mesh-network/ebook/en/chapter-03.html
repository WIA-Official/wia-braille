Chapter 3

Routing Protocols

Comprehensive exploration of AODV, OLSR, and BATMAN routing protocols for dynamic path discovery and maintenance in mesh networks.

Routing Protocol Fundamentals

Routing protocols are the intelligence layer of mesh networks, responsible for discovering optimal paths, maintaining routing tables, and adapting to topology changes. The WIA-COMM-017 standard recognizes three primary routing protocol families, each with distinct characteristics suited to different scenarios.

Protocol Type Best For Scalability
AODV Reactive (On-demand) Mobile, dynamic networks Medium (100-500 nodes)
OLSR Proactive (Table-driven) Stable, predictable networks High (1000+ nodes)
BATMAN Proactive (Metric-based) Community mesh, WiFi High (1000+ nodes)

AODV: Ad hoc On-Demand Distance Vector

AODV is a reactive routing protocol that creates routes only when needed, minimizing routing overhead in networks with sporadic communication patterns. It's particularly effective in mobile mesh networks where topology changes frequently.

AODV Route Discovery Process

When a source node needs to communicate with a destination for which it has no route, AODV initiates a route discovery sequence: 

Time T0: Source S needs route to Destination D

S broadcasts RREQ (Route Request)
    ↓
[RREQ: Src=S, Dest=D, Seq=101, HopCount=0]
    ↓
Neighbors A, B, C receive and forward
    ↓
[A: HopCount=1] → [E: HopCount=2] → [D: HopCount=3]
[B: HopCount=1] → [F: HopCount=2]
[C: HopCount=1]
    ↓
D receives RREQ, sends RREP (Route Reply)
    ↓
[RREP: Src=D, Dest=S, HopCount=3] ← unicast back to S
    ↓
S receives RREP, route established
Path: S → A → E → D (3 hops)

AODV Packet Formats

The WIA-COMM-017 standard specifies three AODV message types: 

RREQ (Route Request):
  [Type | Flags | Hop Count | RREQ ID | Dest Addr | Dest Seq | Src Addr | Src Seq]

  - Type: 1 (RREQ)
  - Flags: J (Join), R (Repair), G (Gratuitous RREP), D (Dest Only)
  - Hop Count: Incremented at each hop
  - RREQ ID: Unique request identifier
  - Dest/Src Seq: Sequence numbers for freshness

RREP (Route Reply):
  [Type | Flags | Prefix Size | Hop Count | Dest Addr | Dest Seq | Src Addr | Lifetime]

  - Type: 2 (RREP)
  - Lifetime: Route validity period (milliseconds)
  - Hop Count: Distance to destination

RERR (Route Error):
  [Type | Flags | Dest Count | Unreachable Dest List]

  - Type: 3 (RERR)
  - Dest Count: Number of unreachable destinations
  - List: [(Dest Addr, Dest Seq), ...]

AODV Routing Table Management

Each AODV node maintains a routing table with entries for known destinations: 

{
  destination: "192.168.1.50",
  next_hop: "192.168.1.23",
  hop_count: 3,
  sequence_number: 142,
  lifetime: 3000,  // milliseconds
  precursor_list: ["192.168.1.15", "192.168.1.22"],
  flags: ["valid", "active"]
}

AODV Sequence Numbers

Sequence numbers ensure route freshness and prevent routing loops:

  • Higher sequence number = fresher route: Nodes always prefer routes with higher sequence numbers
  • Same sequence number: Prefer route with lower hop count
  • Loop prevention: Nodes reject RREQ with sequence numbers ≤ previously seen
Route Selection Logic:
if (new_route.seq > old_route.seq):
    accept_new_route()
elif (new_route.seq == old_route.seq) AND (new_route.hops < old_route.hops):
    accept_new_route()
else:
    reject_new_route()

AODV Route Maintenance

AODV maintains active routes through periodic HELLO messages and monitors link failures: 

HELLO Message Protocol:
  Interval: 1000 ms (configurable)
  Purpose: Neighbor discovery and link monitoring

  if (no HELLO received from neighbor for 3 × interval):
      declare_link_failed()
      send_RERR_to_precursors()
      invalidate_affected_routes()

Local Route Repair:
  When link fails and route still needed:
  1. Upstream node initiates local RREQ
  2. Search within k hops (typically k=2)
  3. If alternative found: send RREP to source
  4. If not found: send RERR to source, global repair needed

OLSR: Optimized Link State Routing

OLSR is a proactive protocol that maintains routes to all destinations at all times. It optimizes link state flooding through Multipoint Relays (MPRs), significantly reducing routing overhead in dense networks.

Multipoint Relay Selection

The key innovation in OLSR is the MPR mechanism. Each node selects a minimal subset of neighbors (MPRs) that cover all 2-hop neighbors. Only MPRs forward topology control messages, reducing broadcast overhead. 

Node N selecting MPRs:

2-hop neighbors: {H, I, J, K, L}
1-hop neighbors: {A, B, C, D}

Coverage analysis:
  A covers: {H, I}
  B covers: {I, J, K}
  C covers: {K, L}
  D covers: {L}

Optimal MPR set: {B, C}  (covers all 2-hop neighbors)

Broadcast reduction:
  Without MPR: All 4 neighbors forward → 16 transmissions (4²)
  With MPR: Only 2 MPRs forward → 8 transmissions (4×2)
  Reduction: 50%

OLSR Message Types

OLSR uses two primary message types to build and maintain topology knowledge: 

HELLO Message (Local Link Discovery):
{
  message_type: "HELLO",
  validity_time: 6000,  // ms
  willingness: 7,  // 0-7, willingness to be MPR
  neighbor_list: [
    {
      address: "10.0.0.5",
      link_type: "SYMMETRIC",  // ASYMMETRIC, SYMMETRIC, MPR, NOT_MPR
      neighbor_type: "NEIGHBOR"  // NEIGHBOR, MPR_NEIGHBOR
    },
    // ... more neighbors
  ]
}

Broadcast interval: 2000 ms (default)

TC Message (Topology Control):
{
  message_type: "TC",
  validity_time: 15000,  // ms
  advertised_neighbor_seq: 250,
  neighbor_list: [
    "10.0.0.12",
    "10.0.0.19",
    "10.0.0.27"
  ]
}

Broadcast interval: 5000 ms (default)
Only MPRs broadcast TC messages

OLSR Routing Table Computation

OLSR uses Dijkstra's shortest path algorithm to compute routes from topology information: 

Routing Table Computation:

1. Build Topology Graph from TC Messages
   graph = build_graph_from_tc_messages()

2. Run Dijkstra's Algorithm
   for each destination d:
       shortest_path[d] = dijkstra(local_node, d, graph)

3. Extract Next Hop from Shortest Path
   routing_table[d] = {
       destination: d,
       next_hop: shortest_path[d][1],  // second node in path
       distance: len(shortest_path[d]) - 1
   }

4. Recompute on Topology Change
   when TC message received with new info:
       if topology_changed():
           recompute_routing_table()

BATMAN: Better Approach To Mobile Adhoc Networking

BATMAN takes a radically different approach: instead of calculating complete paths, each node only determines the best next hop for each destination. This distributed approach scales well and adapts quickly to topology changes.

BATMAN Originator Messages (OGM)

BATMAN nodes periodically broadcast OGMs containing the originator's identity and a transmit quality (TQ) value: 

OGM Structure:
{
  originator: "AA:BB:CC:DD:EE:FF",  // MAC address
  sequence_number: 1024,
  ttl: 50,  // Time To Live (hop limit)
  tq: 255,  // Transmit Quality (0-255, 255=perfect)
  flags: 0x00
}

OGM Broadcast Interval: 1000 ms (configurable: 100-5000 ms)

Transmit Quality (TQ) Metric

TQ measures bidirectional link quality by tracking OGM reception rates. The WIA-COMM-017 standard defines the TQ calculation: 

TQ Calculation Algorithm:

1. Initialize
   window_size = 64  // Track last 64 OGMs
   received_ogms = 0
   expected_ogms = window_size

2. Update on OGM Reception
   if ogm_received:
       received_ogms++

3. Calculate Local Link Quality
   local_link_quality = (received_ogms / expected_ogms) × 255

4. Update TQ for Forwarding
   TQ_new = TQ_received × (local_link_quality / 255)

Example:
  Node A sends OGM with TQ=255
  Node B receives 60 of last 64 OGMs (93.75% reception)
  B's local_link_quality = (60/64) × 255 = 239
  B forwards OGM with TQ = 255 × (239/255) = 239

  Node C receives 56 of 64 from B (87.5%)
  C's local_link_quality = (56/64) × 255 = 223
  C forwards with TQ = 239 × (223/255) = 208

Path TQ (A→B→C) = 208 (lower is worse)

BATMAN Route Selection

BATMAN nodes maintain a table of potential next hops for each destination, selecting the one with highest TQ: 

Best Route Selection:

neighbor_table = {
  "originator_1": [
    {next_hop: "neighbor_A", tq: 245, last_seen: timestamp},
    {next_hop: "neighbor_B", tq: 212, last_seen: timestamp},
    {next_hop: "neighbor_C", tq: 189, last_seen: timestamp}
  ],
  "originator_2": [
    {next_hop: "neighbor_B", tq: 233, last_seen: timestamp},
    {next_hop: "neighbor_D", tq: 198, last_seen: timestamp}
  ]
}

best_next_hop(originator) = argmax(neighbor_table[originator], key=tq)

Hysteresis to Prevent Flapping:
  switch_threshold = 1.20  // 20% improvement required

  if TQ_new > TQ_current × switch_threshold:
      switch_to_new_route()
  else:
      maintain_current_route()  // Avoid frequent switching

Protocol Comparison and Selection

Choosing the right routing protocol depends on network characteristics and application requirements:

Criterion AODV OLSR BATMAN
Overhead (Low Traffic) Very Low High Medium
Overhead (High Traffic) Medium Medium Medium
Convergence Time Slow (on-demand) Fast (proactive) Fast (proactive)
Route Optimality Good (hop count) Excellent (Dijkstra) Good (TQ metric)
Mobility Handling Excellent Good Excellent
Scalability Medium High (MPR optimization) Very High
Implementation Complexity Medium High Low

Selection Guidelines

  • Choose AODV if: Network has sporadic communication, high mobility, or limited routing overhead tolerance
  • Choose OLSR if: Network is stable, requires optimal paths, and can afford proactive overhead
  • Choose BATMAN if: Network is large, dynamic, requires simple implementation, or existing BATMAN infrastructure

Hybrid Approaches

The WIA-COMM-017 standard also recognizes hybrid protocols that combine reactive and proactive elements:

HWMP (Hybrid Wireless Mesh Protocol)

Used in IEEE 802.11s WiFi mesh, HWMP combines both modes: 

Proactive Mode (Tree-Based):
  - Root node periodically broadcasts PREQ
  - Nodes build paths to root
  - Suitable for infrastructure (Internet gateway)

Reactive Mode (On-Demand):
  - Similar to AODV
  - Source broadcasts PREQ when needed
  - Destination sends PREP
  - Used for peer-to-peer communication

Combined Operation:
  if destination_is_root_or_has_proactive_path:
      use_proactive_path()
  else:
      initiate_reactive_discovery()

Key Takeaways

  • AODV is reactive, discovering routes on-demand using RREQ/RREP flooding with sequence numbers preventing loops
  • OLSR is proactive, using Multipoint Relays (MPRs) to optimize link state flooding in dense networks
  • BATMAN uses distributed route selection based on Transmit Quality (TQ) metrics, offering simplicity and scalability
  • Protocol selection depends on traffic patterns (sporadic vs. continuous), mobility, and network size
  • Hybrid protocols like HWMP combine reactive and proactive modes for different traffic types
  • Route maintenance mechanisms (HELLO messages, RERR, TQ updates) ensure routes adapt to topology changes

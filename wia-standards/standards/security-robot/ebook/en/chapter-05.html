5.1 API Architecture Overview

Phase 2 of the WIA Security Robot Standard defines comprehensive RESTful API interfaces enabling remote control, configuration, monitoring, and data retrieval from security robots. These APIs build upon Phase 1 data formats, providing programmatic access to all robot capabilities through standardized HTTP endpoints.

The API architecture follows REST principles with resource-based URLs, standard HTTP methods (GET, POST, PUT, PATCH, DELETE), stateless operations, and JSON request/response bodies. This familiar pattern reduces learning curves for developers and enables integration with standard web development frameworks and tools.

All APIs support versioning through URL paths (e.g., /v1/robots/) to maintain backward compatibility as the standard evolves. Deprecated API versions remain accessible for transition periods allowing gradual migration to newer versions without breaking existing integrations.

Base URL Structure

API endpoints follow a consistent hierarchical structure:

https://{robot_address}/api/v1/{resource}/{id}/{action}

Examples:
https://robot-001.local/api/v1/robots/ROB-SEC-001/status
https://robot-001.local/api/v1/patrol/routes
https://robot-001.local/api/v1/sensors/cam_front_01/snapshot
https://robot-001.local/api/v1/commands/navigate

Authentication Methods

Phase 2 supports multiple authentication schemes to accommodate diverse security requirements and deployment scenarios.

Method Use Case Security Level Complexity
API Key (Bearer Token) Internal networks, simple integrations Medium Low
OAuth 2.0 Enterprise SSO integration High Medium
mTLS (Mutual TLS) High-security environments Very High High
JWT (JSON Web Tokens) Microservices, distributed systems High Medium

5.2 Robot Control APIs

Control APIs enable operators and automated systems to command robot actions, modify operational parameters, and manage patrol routes.

Start/Stop Operations

Basic operational control includes starting and stopping patrol operations, returning robots to charging bases, and emergency stops.

POST /api/v1/robots/{robot_id}/commands/start_patrol
Authorization: Bearer {api_key}
Content-Type: application/json

{
  "route_id": "route_alpha_1",
  "priority": "normal",
  "duration_minutes": 240,
  "start_immediately": true
}

Response (200 OK):
{
  "command_id": "cmd_20251226_103045",
  "status": "accepted",
  "estimated_start": "2025-12-26T10:30:50Z",
  "estimated_completion": "2025-12-26T14:30:50Z"
}

Navigation Commands

Direct navigation control allows operators to send robots to specific locations for investigation or response to incidents.

POST /api/v1/robots/{robot_id}/commands/navigate
Authorization: Bearer {api_key}
Content-Type: application/json

{
  "destination": {
    "type": "geographic",
    "latitude": 37.7749,
    "longitude": -122.4194
  },
  "speed": "normal",
  "avoid_crowds": true,
  "arrival_action": "patrol_area"
}

Response (202 Accepted):
{
  "command_id": "cmd_20251226_103101",
  "status": "executing",
  "eta_seconds": 127,
  "route": {
    "distance_meters": 245,
    "waypoints": 8
  }
}

Emergency Stop

Emergency stop commands have highest priority and override all other operations. Robots receiving emergency stops immediately halt motion and await further instructions.

POST /api/v1/robots/{robot_id}/commands/emergency_stop
Authorization: Bearer {api_key}
Content-Type: application/json

{
  "reason": "safety_concern",
  "operator_id": "operator_jane_doe"
}

Response (200 OK):
{
  "command_id": "cmd_20251226_103115",
  "status": "executed",
  "stopped_at": "2025-12-26T10:31:15.234Z",
  "location": {
    "latitude": 37.7750,
    "longitude": -122.4195
  }
}

5.3 Configuration Management APIs

Configuration APIs enable administrators to adjust robot operational parameters, update patrol routes, configure sensors, and manage alert thresholds.

Patrol Route Configuration

Security operations define patrol routes specifying waypoints, dwell times, and actions to perform at each location. Routes can include randomization elements to prevent predictability.

PUT /api/v1/patrol/routes/{route_id}
Authorization: Bearer {api_key}
Content-Type: application/json

{
  "route_id": "route_alpha_1",
  "name": "Building A Perimeter - Standard",
  "enabled": true,
  "schedule": {
    "days": ["monday", "tuesday", "wednesday", "thursday", "friday"],
    "start_time": "18:00",
    "end_time": "06:00"
  },
  "waypoints": [
    {
      "id": "wp_001",
      "location": {"latitude": 37.7749, "longitude": -122.4194},
      "dwell_seconds": 30,
      "actions": ["360_scan", "thermal_check"],
      "alert_zones": ["perimeter_fence_north"]
    },
    {
      "id": "wp_002",
      "location": {"latitude": 37.7751, "longitude": -122.4196},
      "dwell_seconds": 45,
      "actions": ["door_check", "access_log_review"],
      "alert_zones": ["entrance_gate_b"]
    }
  ],
  "options": {
    "randomize_waypoint_order": false,
    "add_random_waypoints": true,
    "max_random_waypoints": 2,
    "speed": "normal"
  }
}

Response (200 OK):
{
  "route_id": "route_alpha_1",
  "status": "updated",
  "validation": "passed",
  "estimated_duration_minutes": 185
}

Sensor Configuration

Sensor parameters can be adjusted to optimize performance for specific environments or operational requirements. Camera settings include resolution, frame rate, exposure, and white balance. LIDAR sensitivity and range can be tuned. Alert thresholds determine when events trigger notifications.

PATCH /api/v1/sensors/{sensor_id}/config
Authorization: Bearer {api_key}
Content-Type: application/json

{
  "resolution": "1920x1080",
  "fps": 30,
  "exposure": "auto",
  "night_mode": {
    "enabled": true,
    "activation_lux": 10,
    "ir_illumination": true
  },
  "motion_detection": {
    "enabled": true,
    "sensitivity": 0.7,
    "min_object_size": 100,
    "ignore_zones": [
      {"x": 0, "y": 0, "width": 100, "height": 50}
    ]
  }
}

Response (200 OK):
{
  "sensor_id": "cam_front_01",
  "status": "configured",
  "restart_required": false
}

5.4 Status Monitoring and Data Retrieval

Monitoring APIs provide real-time and historical data about robot operations, health, and detected events.

Real-time Status Query

Status endpoints return current robot state using Phase 1 data formats. These queries support operational dashboards and automated monitoring systems.

GET /api/v1/robots/{robot_id}/status
Authorization: Bearer {api_key}

Response (200 OK):
{
  "$schema": "https://wiastandards.com/schemas/security-robot/v1.0.0/status.json",
  "version": "1.0.0",
  "timestamp": "2025-12-26T10:31:30.123Z",
  "robot_id": "ROB-SEC-001",
  "status": {
    "operational_state": "patrolling",
    "location": {...},
    "battery": {...},
    "health": {...}
  },
  "sensors": {...},
  "patrol": {...}
}

Historical Data Retrieval

Historical APIs enable retrieval of past patrol routes, sensor readings, alerts, and events for analysis, auditing, and compliance reporting.

Alert History and Search

Alert APIs support querying past security events with filtering by type, severity, location, and time range. Advanced search capabilities enable incident investigation and pattern analysis.

5.5 Error Handling and Response Codes

Consistent error handling enables robust client implementations and clear debugging. Phase 2 defines standard HTTP status codes and error response formats.

Status Code Meaning Common Scenarios
200 OK Request succeeded Successful GET, PUT operations
201 Created Resource created POST creating new routes, configurations
202 Accepted Request accepted, processing asynchronously Long-running commands like navigation
400 Bad Request Invalid request format or parameters Malformed JSON, validation failures
401 Unauthorized Authentication required or failed Missing or invalid API key
403 Forbidden Insufficient permissions Attempting restricted operations
404 Not Found Resource doesn't exist Invalid robot ID, route not found
409 Conflict Request conflicts with current state Robot already executing command
429 Too Many Requests Rate limit exceeded Too many API calls in time window
500 Internal Server Error Server-side error Unexpected system failures
503 Service Unavailable Temporary unavailability Maintenance mode, system overload

Error Response Format

Error responses follow standardized JSON structure providing error codes, messages, and context for debugging.

{
  "error": {
    "code": "INVALID_ROUTE",
    "message": "Patrol route contains unreachable waypoint",
    "details": {
      "waypoint_id": "wp_007",
      "issue": "Location outside mapped area",
      "suggested_action": "Update waypoint coordinates or expand mapped area"
    },
    "request_id": "req_20251226_103045",
    "timestamp": "2025-12-26T10:30:45.123Z"
  }
}

5.6 Rate Limiting and Throttling

To prevent API abuse and ensure fair resource allocation across multiple clients, Phase 2 implements rate limiting using token bucket algorithms.

Different endpoint categories have different rate limits reflecting their resource intensity and typical usage patterns. Status queries support high request rates (60 per minute). Control commands have moderate limits (20 per minute). Configuration changes are more restricted (5 per minute).

Rate limit information appears in response headers, allowing clients to implement adaptive throttling:

X-RateLimit-Limit: 60
X-RateLimit-Remaining: 42
X-RateLimit-Reset: 1735212000

When rate limits are exceeded, APIs return 429 status with retry-after header indicating when requests can resume.

Key Takeaways

  • Phase 2 defines comprehensive RESTful APIs for robot control, configuration, and monitoring using standard HTTP methods and JSON payloads
  • Multiple authentication methods (API keys, OAuth 2.0, mTLS, JWT) support diverse security requirements from simple integrations to high-security deployments
  • Control APIs enable remote operation including start/stop, navigation commands, emergency stops, and patrol route management
  • Configuration APIs allow adjustment of sensors, alert thresholds, and operational parameters without requiring physical access to robots
  • Standardized error handling with consistent HTTP status codes and structured error responses enables robust client implementations and clear debugging

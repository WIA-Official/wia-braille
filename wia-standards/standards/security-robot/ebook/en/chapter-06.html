6.1 Overview of Phase 3 Communication Protocols

Phase 3 of the WIA Security Robot Standard addresses real-time communication requirements that request-response APIs cannot adequately serve. Security operations demand continuous bidirectional data flows: live video streaming from robot cameras, real-time sensor telemetry for situational awareness, immediate alert delivery requiring sub-second latency, and dynamic command execution with instant feedback. Phase 2 APIs excel at configuration and status queries, but streaming applications need different architectural patterns.

The standard supports multiple protocol options, each optimized for specific communication patterns and requirements. MQTT (Message Queuing Telemetry Transport) provides lightweight publish-subscribe messaging ideal for sensor telemetry and alert distribution across distributed systems. WebSocket enables full-duplex communication over single TCP connections, perfect for control interfaces requiring low-latency bidirectional exchanges. RTSP (Real-Time Streaming Protocol) and RTP (Real-Time Protocol) deliver time-sensitive media streams including live video from robot cameras compatible with existing video management systems.

Protocol selection depends on use case requirements. Control applications prioritizing responsiveness favor WebSocket. Sensor data aggregation from multiple robots benefits from MQTT's efficient pub-sub model. Video surveillance integration leverages RTSP for compatibility with enterprise VMS platforms. Organizations often deploy multiple protocols simultaneously, each serving its optimal use case within comprehensive security architectures.

Quality of Service Requirements

Different message types demand different reliability guarantees. Critical alert notifications require guaranteed delivery with acknowledgment - missing a security breach notification is unacceptable. Sensor telemetry tolerates occasional packet loss since subsequent readings supersede earlier values. Video streams prioritize low latency over perfect reliability - dropping occasional frames maintains real-time viewing while retransmitting dropped packets introduces unacceptable delays.

Phase 3 defines QoS levels aligned with message importance. Level 0 (at most once delivery) suits high-frequency sensor readings where latest value matters most. Level 1 (at least once delivery) ensures messages reach recipients though duplicates may occur, appropriate for alerts where processing duplicates is acceptable but missing notifications is not. Level 2 (exactly once delivery) guarantees single delivery without duplicates, critical for command execution and billing/audit events where duplicates cause problems.

6.2 MQTT for Sensor Telemetry and Alerts

MQTT excels at distributing sensor data and alerts across security operations centers, analytics platforms, and integrated systems. The publish-subscribe model decouples message producers (robots) from consumers (monitoring systems, databases, analytics engines), enabling flexible architectures that scale gracefully.

Topic Structure and Naming Conventions

MQTT organizes messages into hierarchical topics. The standard defines topic naming conventions ensuring consistency across implementations and preventing collisions in multi-vendor deployments.

wia/rob-012/{facility_id}/{robot_id}/{message_type}/{detail}

Examples:
wia/rob-012/campus-north/ROB-SEC-001/status/battery
wia/rob-012/campus-north/ROB-SEC-001/alerts/intrusion
wia/rob-012/campus-north/ROB-SEC-001/sensors/lidar/obstacles
wia/rob-012/campus-north/ROB-SEC-001/location/current

Wildcard subscriptions enable flexible monitoring. Security operations centers can subscribe to all alerts across facilities using wia/rob-012/+/+/alerts/# or monitor specific robot types using wia/rob-012/campus-north/+/status/health. This flexibility supports diverse operational patterns without requiring point-to-point configuration.

Message Payloads

MQTT message payloads use Phase 1 JSON formats, ensuring consistency with REST API data structures. This unified data model simplifies integration - systems processing REST API responses also parse MQTT messages without format translation.

Topic: wia/rob-012/campus-north/ROB-SEC-001/alerts/intrusion
QoS: 1 (at least once)
Payload:
{
  "$schema": "https://wiastandards.com/schemas/security-robot/v1.0.0/alert.json",
  "version": "1.0.0",
  "alert_id": "alert_20251226_103045_001",
  "timestamp": "2025-12-26T10:30:45.123Z",
  "robot_id": "ROB-SEC-001",
  "alert_type": "intrusion_detected",
  "severity": "high",

  "location": {
    "type": "geographic",
    "latitude": 37.7749,

Retained Messages and Last Known State

MQTT supports retained messages where brokers store the last message published to a topic and deliver it immediately when new clients subscribe. This enables new monitoring systems to discover current robot states without waiting for next status update. Robots publish status updates with retain flag set, ensuring dashboards display current fleet status immediately upon connection.

6.3 WebSocket for Real-time Control

WebSocket protocol provides full-duplex communication channels over single TCP connections, enabling low-latency bidirectional exchanges between security operations centers and robots. Unlike HTTP request-response patterns, WebSocket maintains persistent connections where both parties can send messages asynchronously.

Connection Establishment

WebSocket connections begin with HTTP upgrade handshake, then transition to WebSocket framing protocol. The standard defines connection URLs and authentication patterns:

wss://robot-001.local/api/v1/ws/control
Authorization: Bearer {api_key}

Connection upgrade:
GET /api/v1/ws/control HTTP/1.1
Host: robot-001.local
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13
Authorization: Bearer {api_key}

Response:
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=

Message Format

WebSocket messages carry JSON payloads with message type indicators and sequence numbers enabling reliable communication over unreliable networks.

{
  "message_type": "command",
  "sequence": 12847,
  "timestamp": "2025-12-26T10:31:15.234Z",
  "command": {
    "type": "navigate",
    "destination": {
      "latitude": 37.7749,
      "longitude": -122.4194
    },
    "priority": "high"
  }
}

Response:
{
  "message_type": "command_ack",
  "sequence": 12847,
  "timestamp": "2025-12-26T10:31:15.456Z",
  "status": "accepted",
  "command_id": "cmd_20251226_103115",
  "eta_seconds": 127
}

Heartbeat and Connection Management

WebSocket connections may traverse NAT gateways and firewalls that timeout idle connections. The standard mandates periodic ping/pong messages maintaining connection liveness. Clients send ping frames every 30 seconds; servers respond with pong frames within 5 seconds. Missing pong responses indicate connection failure triggering reconnection attempts with exponential backoff.

6.4 RTSP/RTP for Video Streaming

Security robots equipped with cameras stream live video to video management systems and security operations centers. The standard leverages existing RTSP (Real-Time Streaming Protocol) and RTP (Real-Time Transport Protocol) specifications ensuring compatibility with enterprise VMS platforms while defining security robot-specific extensions.

Stream URLs and Camera Identification

Each robot camera exposes RTSP streams through standardized URLs incorporating robot and camera identifiers:

rtsp://robot-001.local:554/wia/rob-012/{robot_id}/{camera_id}/{stream_profile}

Examples:
rtsp://robot-001.local:554/wia/rob-012/ROB-SEC-001/cam_front_01/main
rtsp://robot-001.local:554/wia/rob-012/ROB-SEC-001/cam_front_01/sub
rtsp://robot-001.local:554/wia/rob-012/ROB-SEC-001/cam_thermal_01/main

Multiple stream profiles support different bandwidth and quality requirements. Main streams deliver full resolution and frame rate for detailed viewing and recording. Sub streams provide lower resolution for bandwidth-constrained scenarios and multi-camera monitoring displays. Mobile streams optimize for cellular connections with aggressive compression.

Codec Standards

The standard mandates support for common video codecs ensuring broad compatibility:

Codec Profile Use Case Bandwidth
H.264 (AVC) High Profile Primary stream, recording 2-8 Mbps
H.265 (HEVC) Main Profile Bandwidth optimization 1-4 Mbps
MJPEG - Compatibility, snapshots 4-12 Mbps

Metadata Embedding

Video streams embed metadata using SEI (Supplemental Enhancement Information) messages in H.264/H.265 streams. Metadata includes timestamp synchronization (correlating video frames with sensor readings and alerts), location data (GPS coordinates or local position), sensor parameters (exposure, gain, focus distance), and alert context (when video captured during alert investigation).

This embedded metadata enables advanced analytics. Video management systems can geolocate recorded footage automatically, search historical video by location, and correlate video with sensor data timelines. Forensic analysis benefits from precise timestamp synchronization ensuring video evidence aligns with other data sources.

6.5 Security and Encryption

Communication security is paramount for security robot deployments. Phase 3 mandates encryption for all network communications protecting against eavesdropping, tampering, and man-in-the-middle attacks.

Transport Layer Security

All protocols use TLS encryption. MQTT connections use MQTT over TLS (MQTTS) on port 8883. WebSocket connections use secure WebSocket (wss://) URLs. RTSP streams support RTSPS with SRTP (Secure Real-time Transport Protocol) for encrypted media.

TLS 1.2 is minimum required version; TLS 1.3 is recommended for enhanced security and performance. Cipher suites must provide forward secrecy using ECDHE key exchange. Weak ciphers including RC4, DES, and export-grade encryption are prohibited.

Certificate Management

Robots present X.509 certificates during TLS handshakes for authentication. Certificates can be issued by organization private CAs or public certificate authorities depending on deployment architecture and network topology.

Certificate validation prevents impersonation attacks. Clients verify server certificates match expected robot identity through CN (Common Name) or SAN (Subject Alternative Name) fields. Certificate revocation checking using OCSP (Online Certificate Status Protocol) or CRL (Certificate Revocation Lists) detects compromised certificates.

Automated certificate renewal using ACME protocol or similar mechanisms prevents expiration-related outages. Robots request new certificates 30 days before expiration, allowing time for manual intervention if automated renewal fails.

Key Takeaways

  • Comprehensive standardization enables interoperability and reduces integration complexity across diverse security robot platforms and systems
  • Open standards accelerate innovation by providing stable foundations while preserving competitive differentiation opportunities for manufacturers
  • Real-world deployment validation ensures specifications address practical operational needs rather than theoretical ideals
  • WIA certification provides third-party validation building trust and enabling objective platform comparison for procurement decisions
  • The four-phase architecture enables progressive adoption allowing organizations to gain value incrementally while working toward full compliance

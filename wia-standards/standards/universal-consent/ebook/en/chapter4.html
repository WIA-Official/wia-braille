CHAPTER 04 · PHASE 1

Consent Data Format

Deep dive into standardized consent data structures, JSON schemas, validation rules, and universal formats that form the foundation of WIA-CORE-002.

The Foundation: Why Data Format Matters

Phase 1 of WIA-CORE-002 establishes the fundamental data format for consent records. This may seem like a purely technical concern, but the choice of data format has profound implications for interoperability, auditability, compliance, and user rights. A well-designed data format ensures that consent records are complete, consistent, verifiable, and machine-readable across all systems and organizations.

The goals of Phase 1 are ambitious yet practical:

  • Define a comprehensive consent record structure that captures all legally required information
  • Ensure human readability and machine processability
  • Support multiple jurisdictions and regulatory frameworks simultaneously
  • Enable extensibility for future requirements without breaking compatibility
  • Provide validation mechanisms to ensure data quality and completeness
  • Support the full consent lifecycle from creation through revocation and expiration

Core Consent Record Structure

Every WIA-CORE-002 consent record follows a standardized JSON structure with required and optional fields. The complete schema is available in the technical specification, but here we'll explore the key components.

Required Fields

These fields MUST be present in every valid consent record:

Field Type Description
consentId string (UUID) Globally unique identifier for this consent record
userId string Identifier for the user who provided consent
version string WIA-CORE-002 version (e.g., "1.0")
timestamp ISO 8601 datetime When consent was granted
status enum Current status: pending, active, revoked, expired
purposes array List of purposes for which consent is granted
legalBasis enum Legal basis for processing: consent, contract, legal-obligation, legitimate-interest
jurisdiction string Applicable jurisdiction (ISO 3166-1 alpha-2 code or special codes like "EU")

Purpose Specification

The "purposes" array is the heart of granular consent management. Each purpose represents a specific reason for processing personal data, and users can grant or deny consent for each purpose independently.

Purpose Object Structure

Field Required Description
purposeId Yes Unique identifier for this purpose (kebab-case recommended)
purposeName Yes Human-readable name for the purpose
description Yes Clear, plain-language description of what this purpose entails
granted Yes Boolean indicating whether consent is granted for this purpose
categories No Array of category tags for classification (e.g., "marketing", "analytics")
dataCategories Yes Types of personal data processed for this purpose
retentionPeriod Yes How long data will be retained (ISO 8601 duration format)
thirdParties Yes Array of third parties who will receive data for this purpose

Standard Purpose Categories

WIA-CORE-002 defines standard purpose categories to promote consistency across implementations:

  • marketing: Marketing communications and promotional activities
  • analytics: Usage analytics and performance monitoring
  • personalization: Customizing user experience and content
  • advertising: Targeted advertising and ad delivery
  • social-media: Social media integration and sharing
  • research: Product research and development
  • security: Security and fraud prevention
  • support: Customer support and service delivery
  • legal: Legal compliance and obligations
  • contract: Contract fulfillment and service delivery

Legal Basis and Jurisdiction

Different regulations recognize different legal bases for processing personal data. WIA-CORE-002 supports all major legal bases:

Legal Basis Description When Used
consent User has given explicit consent Marketing, optional analytics, data sharing
contract Processing necessary to fulfill a contract Service delivery, payment processing
legal-obligation Required by law Tax records, regulatory reporting
legitimate-interest Organization's legitimate interests (with balancing test) Fraud prevention, security measures
vital-interest Necessary to protect life or health Medical emergencies, safety threats
public-interest Performing tasks in the public interest Government services, public health

Jurisdiction Codes

The jurisdiction field uses ISO 3166-1 alpha-2 codes (e.g., "US", "GB", "DE") or special codes for regulatory regions:

  • EU: European Union (GDPR applies)
  • EEA: European Economic Area
  • US-CA: California, USA (CCPA/CPRA applies)
  • US-VA: Virginia, USA (VCDPA applies)
  • US-CO: Colorado, USA (CPA applies)
  • GLOBAL: Multi-jurisdictional (uses most restrictive requirements)

Consent Lifecycle States

Consent records progress through a defined lifecycle, with state transitions tracked in the audit trail:

State Definitions

  • pending: Consent has been requested but not yet confirmed (e.g., awaiting email verification or parental approval)
  • active: Consent is valid and in effect
  • revoked: User has withdrawn consent
  • expired: Consent has passed its expiration date
  • suspended: Temporarily suspended (e.g., during investigation)
  • superseded: Replaced by a newer consent record

State Transition Example

"auditTrail": [ { "timestamp": "2025-01-15T10:30:00Z", "action": "created", "actor": "system", "previousState": null, "newState": "pending", "reason": "User signup initiated" }, { "timestamp": "2025-01-15T10:35:00Z", "action": "verified", "actor": "user-789012", "previousState": "pending", "newState": "active", "reason": "Email verified via confirmation link" }, { "timestamp": "2025-06-20T14:22:00Z", "action": "updated", "actor": "user-789012", "previousState": "active", "newState": "active", "changes": { "purposes.marketing-email.granted": { "old": true, "new": false } }, "reason": "User updated preferences via preference center" }, { "timestamp": "2025-12-01T09:15:00Z", "action": "revoked", "actor": "user-789012", "previousState": "active", "newState": "revoked", "reason": "User requested account deletion" } ]

Metadata and Context

The metadata object captures contextual information that may be critical for proving valid consent or investigating disputes:

  • source: Where consent was obtained (e.g., "web-signup", "mobile-app", "in-person")
  • sourceUrl: Specific page or screen where consent was obtained
  • ipAddress: IP address of the user at time of consent (for audit purposes)
  • userAgent: Browser/app information
  • consentFormVersion: Version of the consent form presented to the user
  • privacyPolicyVersion: Version of privacy policy in effect
  • privacyPolicyUrl: URL to archived version of privacy policy
  • language: Language in which consent was presented
  • customFields: Organization-specific metadata (extensible)

This metadata is crucial for demonstrating that consent was informed and freely given—the user saw a specific version of your privacy policy, in their language, with clear explanations.

Data Categories

WIA-CORE-002 provides a standardized taxonomy of data categories to ensure consistency across organizations:

Category Examples Sensitivity
contact-info Email, phone, address Standard
identification Name, date of birth, government ID Standard
financial Credit card, bank account, transaction history Sensitive
health Medical records, health conditions Sensitive
biometric Fingerprints, facial recognition, DNA Sensitive
location GPS coordinates, IP address, address Standard
behavioral Browsing history, purchase history, app usage Standard

communications Emails, messages, call records Standard
employment Job title, employer, work history Standard

Retention Periods

Retention periods use ISO 8601 duration format for precision and internationalization:

  • P1Y: 1 year
  • P2Y: 2 years
  • P6M: 6 months
  • P90D: 90 days
  • P7Y: 7 years (common for financial records)
  • INDEFINITE: No expiration (must be justified under legal basis)

Child Consent Handling

For users identified as minors, additional fields are required:

"userInfo": { "age": 14, "isMinor": true, "parentalConsent": { "required": true, "obtained": true, "parentId": "parent-456789", "parentEmail": "parent@example.com", "verificationMethod": "credit-card-check", "verifiedAt": "2025-01-15T10:40:00Z" }, "ageVerificationMethod": "self-reported", "jurisdiction": "US" }

Validation Rules

WIA-CORE-002 includes comprehensive validation rules to ensure data quality:

  • consentId must be a valid UUID
  • timestamp must be ISO 8601 format and not in the future
  • expiresAt (if present) must be after timestamp
  • status must be one of the defined enum values
  • purposes array must contain at least one purpose
  • Each purpose must have purposeId, purposeName, description, granted, and dataCategories
  • jurisdiction must be a valid ISO 3166 code or special code
  • For minors, parental consent information must be present if required by jurisdiction
  • auditTrail must have at least one entry (creation event)

Extensibility

Organizations can extend the standard with custom fields in a "custom" namespace:

"custom": { "organizationId": "org-123", "department": "marketing", "campaignId": "summer-2025", "internalReferenceId": "ref-xyz-789", "complianceOfficerApproval": { "approved": true, "approver": "jane.doe@example.com", "approvedAt": "2025-01-14T15:00:00Z" } }

Custom fields do not affect validation and are ignored by systems that don't recognize them, ensuring forward compatibility.

Multi-Language Support

For organizations operating globally, purpose descriptions can be provided in multiple languages:

"purposes": [ { "purposeId": "marketing-email", "purposeName": { "en": "Email Marketing Communications", "es": "Comunicaciones de Marketing por Correo Electrónico", "de": "E-Mail-Marketing-Kommunikation", "fr": "Communications Marketing par E-mail" }, "description": { "en": "Receive promotional emails about our products", "es": "Recibir correos promocionales sobre nuestros productos", "de": "Werbe-E-Mails über unsere Produkte erhalten", "fr": "Recevoir des e-mails promotionnels sur nos produits" }, "granted": true, ... } ]

Implementation Checklist

To implement Phase 1 compliance, organizations should:

  1. Review existing consent data structures and identify gaps
  2. Map existing fields to WIA-CORE-002 required fields
  3. Implement JSON schema validation for new consent records
  4. Create migration scripts for legacy consent data
  5. Update consent capture forms to collect all required metadata
  6. Implement audit trail tracking for all consent operations
  7. Test validation rules with sample data
  8. Document any custom extensions in the "custom" namespace
  9. Train teams on the new data format
  10. Set up monitoring for validation failures

Chapter Summary

Phase 1 establishes the data foundation for universal consent management. By standardizing consent record formats, WIA-CORE-002 enables interoperability, auditability, and compliance across systems and organizations. The comprehensive structure captures all legally required information while remaining extensible for future needs.

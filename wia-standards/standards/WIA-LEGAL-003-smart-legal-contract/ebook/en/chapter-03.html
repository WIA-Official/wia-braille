Chapter 3

Smart Contract Architecture and Standards

Smart contracts are self-executing programs deployed on blockchain networks that automatically enforce agreement terms through code. This chapter explores the architectural foundations of smart contracts, focusing on Solidity development for Ethereum, execution models, oracle integration, and the WIA-LEGAL-003 standard for legal smart contracts that bridge traditional law and blockchain technology.

Smart Contract Fundamentals

Nick Szabo first proposed smart contracts in 1994 as "computerized transaction protocols that execute the terms of a contract." Blockchain technology made this vision practical by providing:

  • Immutability: Once deployed, contract code cannot be altered (without explicit upgrade mechanisms)
  • Transparency: All parties can inspect contract code and verify execution logic
  • Trustless execution: No intermediary required; blockchain network enforces execution
  • Atomic transactions: Contract operations either complete fully or revert entirely
  • Determinism: Same inputs always produce same outputs, regardless of who executes

Ethereum Smart Contract Model

Ethereum pioneered general-purpose smart contracts through the Ethereum Virtual Machine (EVM), a Turing-complete execution environment. Contracts are written in high-level languages (primarily Solidity or Vyper), compiled to EVM bytecode, and deployed to blockchain addresses. Once deployed, anyone can invoke contract functions by sending transactions containing function calls and required payment (in ETH or tokens).

Smart Contract Execution Flow

Step Actor Action Cost
1. Development Developer Write Solidity contract, compile to bytecode Free (local)
2. Testing Developer Deploy to testnet (Goerli, Sepolia), verify behavior Free (test ETH)
3. Deployment Developer Deploy bytecode to mainnet via transaction 200K-2M gas (~$50-$500)
4. Invocation User Send transaction calling contract function 21K-500K gas (~$5-$125)
5. Execution EVM (all nodes) Execute bytecode, update state, emit events Included in step 4
6. Verification Network Miners/validators verify execution, include in block Included in step 4

Gas costs vary with network congestion. Amounts shown assume 50 Gwei gas price and $2,500 ETH.

Solidity Smart Contract Development

Solidity is a statically-typed, contract-oriented language designed for Ethereum. It features inheritance, libraries, and complex user-defined types. Here's a complete example of a legal purchase agreement implemented as a smart contract: 

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

/**
 * @title PurchaseAgreement
 * @dev WIA-LEGAL-003 compliant smart legal contract for goods purchase
 * @notice This contract implements a legally binding purchase agreement with:
 *   - Escrow payment holding
 *   - Delivery confirmation mechanism
 *   - Automated dispute resolution with arbiter
 *   - Refund protection for buyer
 *   - Payment guarantee for seller
 */
contract PurchaseAgreement {
    // Contract parties
    address payable public buyer;
    address payable public seller;
    address public arbiter;

    // Contract terms
    uint256 public purchasePrice;
    string public itemDescription;
    uint256 public deliveryDeadline;

    // Contract state
    enum State { Created, Funded, Delivered, Disputed, Completed, Refunded }
    State public currentState;

    // Events for legal audit trail
    event ContractCreated(address buyer, address seller, uint256 price, uint256 deadline);
    event FundsDeposited(address buyer, uint256 amount, uint256 timestamp);
    event ItemShipped(address seller, string trackingNumber, uint256 timestamp);
    event DeliveryConfirmed(address buyer, uint256 timestamp);
    event DisputeRaised(address initiator, string reason, uint256 timestamp);
    event DisputeResolved(address arbiter, address winner, uint256 timestamp);
    event PaymentReleased(address seller, uint256 amount, uint256 timestamp);
    event RefundIssued(address buyer, uint256 amount, uint256 timestamp);

    // Tracking information
    string public trackingNumber;
    uint256 public shippedTimestamp;
    string public disputeReason;

    // Modifiers for access control
    modifier onlyBuyer() {
        require(msg.sender == buyer, "Only buyer can call this function");
        _;
    }

    modifier onlySeller() {
        require(msg.sender == seller, "Only seller can call this function");
        _;
    }

    modifier onlyArbiter() {
        require(msg.sender == arbiter, "Only arbiter can call this function");
        _;
    }

    modifier inState(State expectedState) {
        require(currentState == expectedState, "Invalid state for this operation");
        _;
    }

    /**
     * @dev Constructor creates purchase agreement contract
     * @param _seller Address of the seller
     * @param _arbiter Address of neutral third-party arbiter
     * @param _itemDescription Description of item being purchased
     * @param _deliveryDeadline Unix timestamp for delivery deadline
     */
    constructor(
        address payable _seller,
        address _arbiter,
        string memory _itemDescription,
        uint256 _deliveryDeadline
    ) payable {
        require(_seller != address(0), "Seller address cannot be zero");
        require(_arbiter != address(0), "Arbiter address cannot be zero");
        require(_deliveryDeadline > block.timestamp, "Deadline must be in future");
        require(msg.value > 0, "Purchase price must be greater than zero");

        buyer = payable(msg.sender);
        seller = _seller;
        arbiter = _arbiter;
        itemDescription = _itemDescription;
        deliveryDeadline = _deliveryDeadline;
        purchasePrice = msg.value;
        currentState = State.Funded;

        emit ContractCreated(buyer, seller, purchasePrice, deliveryDeadline);
        emit FundsDeposited(buyer, msg.value, block.timestamp);
    }

    /**
     * @dev Seller confirms item shipped and provides tracking
     * @param _trackingNumber Shipping tracking number for verification
     */
    function confirmShipment(string memory _trackingNumber)
        external
        onlySeller
        inState(State.Funded)
    {
        require(bytes(_trackingNumber).length > 0, "Tracking number required");
        require(block.timestamp < deliveryDeadline, "Delivery deadline passed");

        trackingNumber = _trackingNumber;
        shippedTimestamp = block.timestamp;

        emit ItemShipped(seller, _trackingNumber, block.timestamp);
    }

    /**
     * @dev Buyer confirms receipt and releases payment to seller
     */
    function confirmDelivery()
        external
        onlyBuyer
        inState(State.Funded)
    {
        require(bytes(trackingNumber).length > 0, "Item not yet shipped");

        currentState = State.Completed;
        uint256 payment = purchasePrice;

        emit DeliveryConfirmed(buyer, block.timestamp);
        emit PaymentReleased(seller, payment, block.timestamp);

        // Transfer funds to seller
        seller.transfer(payment);
    }

    /**
     * @dev Either party can raise dispute if issues arise
     * @param reason Explanation of why dispute is being raised
     */
    function raiseDispute(string memory reason)
        external
        inState(State.Funded)
    {
        require(
            msg.sender == buyer || msg.sender == seller,
            "Only contract parties can raise dispute"
        );
        require(bytes(reason).length > 0, "Dispute reason required");

        currentState = State.Disputed;
        disputeReason = reason;

        emit DisputeRaised(msg.sender, reason, block.timestamp);
    }

    /**
     * @dev Arbiter resolves dispute by awarding funds to one party
     * @param favorBuyer If true, refund buyer; if false, pay seller
     */
    function resolveDispute(bool favorBuyer)
        external
        onlyArbiter
        inState(State.Disputed)
    {
        address payable winner = favorBuyer ? buyer : seller;
        State finalState = favorBuyer ? State.Refunded : State.Completed;
        uint256 amount = purchasePrice;

        currentState = finalState;

        emit DisputeResolved(arbiter, winner, block.timestamp);

        if (favorBuyer) {
            emit RefundIssued(buyer, amount, block.timestamp);
        } else {
            emit PaymentReleased(seller, amount, block.timestamp);
        }

        // Transfer funds to winner
        winner.transfer(amount);
    }

    /**
     * @dev Buyer can claim refund if seller misses delivery deadline
     */
    function claimRefundAfterDeadline()
        external
        onlyBuyer
        inState(State.Funded)
    {
        require(block.timestamp > deliveryDeadline, "Deadline not yet passed");
        require(currentState != State.Delivered, "Item already delivered");

        currentState = State.Refunded;
        uint256 refund = purchasePrice;

        emit RefundIssued(buyer, refund, block.timestamp);

        // Return funds to buyer
        buyer.transfer(refund);
    }

    /**
     * @dev Get complete contract status for legal review
     * @return All relevant contract data as structured object
     */
    function getContractStatus()
        external
        view
        returns (
            address buyerAddr,
            address sellerAddr,
            uint256 price,
            string memory description,
            State state,
            uint256 deadline,
            string memory tracking,
            uint256 shipped
        )
    {
        return (
            buyer,
            seller,
            purchasePrice,
            itemDescription,
            currentState,
            deliveryDeadline,
            trackingNumber,
            shippedTimestamp
        );
    }
}

Contract Design Patterns

The above contract demonstrates several critical smart contract patterns for legal agreements:

Legal Smart Contract Patterns

Pattern Purpose Implementation Legal Benefit
State Machine Track contract lifecycle enum State with modifiers Clear contract progression
Escrow Hold funds until conditions met payable constructor, conditional release Payment security for both parties
Event Logging Create immutable audit trail emit events for all state changes Legal evidence of all actions
Access Control Restrict function calls by role onlyBuyer, onlySeller modifiers Enforce party-specific rights
Dispute Resolution Handle contract breaches Arbiter role with dispute functions Alternative to litigation
Deadline Enforcement Time-based obligations require(block.timestamp < deadline) Automatic deadline compliance

Oracle Integration for Real-World Data

Smart contracts are deterministic and cannot directly access external data (APIs, databases, real-world events). Oracles solve this by providing trusted data feeds to blockchain. Legal contracts often require external data: exchange rates, weather conditions, shipment tracking, court decisions, or regulatory updates.

Chainlink Oracle Integration

Chainlink is the leading decentralized oracle network, providing reliable external data to smart contracts. Here's how to integrate price feeds for international contracts with automatic currency conversion: 

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

import "@chainlink/contracts/src/v0.8/interfaces/AggregatorV3Interface.sol";

/**
 * @title InternationalPurchaseAgreement
 * @dev Purchase contract with automatic currency conversion using Chainlink oracles
 */
contract InternationalPurchaseAgreement {
    AggregatorV3Interface internal ethUsdPriceFeed;
    AggregatorV3Interface internal eurUsdPriceFeed;

    address payable public buyer;
    address payable public seller;
    uint256 public priceInUSD; // Price in USD cents (e.g., 100000 = $1,000.00)
    uint256 public priceInEUR; // Price in EUR cents

    /**
     * @dev Constructor with Chainlink price feed addresses
     * Mainnet ETH/USD: 0x5f4eC3Df9cbd43714FE2740f5E3616155c5b8419
     * Mainnet EUR/USD: 0xb49f677943BC038e9857d61E7d053CaA2C1734C1
     */
    constructor(
        address payable _seller,
        uint256 _priceInUSD,
        address _ethUsdFeed,
        address _eurUsdFeed
    ) {
        buyer = payable(msg.sender);
        seller = _seller;
        priceInUSD = _priceInUSD;

        ethUsdPriceFeed = AggregatorV3Interface(_ethUsdFeed);
        eurUsdPriceFeed = AggregatorV3Interface(_eurUsdFeed);
    }

    /**
     * @dev Get latest ETH price in USD from Chainlink oracle
     * @return price ETH/USD price with 8 decimal places
     */
    function getLatestEthPrice() public view returns (int) {
        (
            /* uint80 roundID */,
            int price,
            /* uint startedAt */,
            /* uint timeStamp */,
            /* uint80 answeredInRound */
        ) = ethUsdPriceFeed.latestRoundData();
        return price; // Returns price like 250000000000 for $2,500.00
    }

    /**
     * @dev Calculate required ETH payment based on USD price
     * @return Required ETH amount in wei
     */
    function calculateEthPayment() public view returns (uint256) {
        int ethPriceUsd = getLatestEthPrice(); // 8 decimals
        require(ethPriceUsd > 0, "Invalid ETH price from oracle");

        // priceInUSD has 2 decimals (cents), ethPriceUsd has 8 decimals
        // Result should be in wei (18 decimals)
        // Formula: (priceInUSD * 10^18) / (ethPriceUsd * 10^6)
        uint256 requiredWei = (priceInUSD * 1e18) / (uint256(ethPriceUsd) * 1e6);
        return requiredWei;
    }

    /**
     * @dev Buyer deposits payment, automatically converted from USD price
     */
    function depositPayment() external payable {
        uint256 requiredPayment = calculateEthPayment();
        require(msg.value >= requiredPayment, "Insufficient payment");

        // Refund excess payment
        if (msg.value > requiredPayment) {
            payable(msg.sender).transfer(msg.value - requiredPayment);
        }
    }

    /**
     * @dev Get EUR equivalent of contract price
     * @return Price in EUR cents
     */
    function getPriceInEUR() public view returns (uint256) {
        (
            /* uint80 roundID */,
            int eurUsdPrice,
            /* uint startedAt */,
            /* uint timeStamp */,
            /* uint80 answeredInRound */
        ) = eurUsdPriceFeed.latestRoundData();
        require(eurUsdPrice > 0, "Invalid EUR price from oracle");

        // Convert USD to EUR: priceInUSD / (EUR/USD rate)
        // eurUsdPrice has 8 decimals, represents EUR per USD
        uint256 priceInEurCents = (priceInUSD * 1e8) / uint256(eurUsdPrice);
        return priceInEurCents;
    }
}

Common Oracle Use Cases for Legal Contracts

  • Price Feeds: Currency exchange rates, commodity prices, stock prices for financial contracts
  • Weather Data: Temperature, precipitation, natural disasters for insurance and agriculture contracts
  • Shipping Data: Package delivery confirmation, customs clearance for logistics contracts
  • Identity Verification: KYC/AML checks, accredited investor status for securities contracts

  • Off-chain Computation: Complex calculations, AI model outputs for algorithmic contracts

WIA-LEGAL-003 Standard Specification

The WIA-LEGAL-003 standard defines requirements for legal smart contracts to ensure enforceability, auditability, and compliance with traditional legal frameworks. All compliant contracts must implement these interfaces and behaviors:

Core Interface Requirements

// SPDX-License-Identifier: CC-BY-SA-4.0
pragma solidity ^0.8.20;

/**
 * @title IWIALEGAL003
 * @dev Interface for WIA-LEGAL-003 compliant smart legal contracts
 */
interface IWIALEGAL003 {
    // Required events for legal audit trail
    event ContractCreated(address indexed creator, bytes32 indexed contractHash, uint256 timestamp);
    event PartyAdded(address indexed party, string role, uint256 timestamp);
    event StateChanged(uint8 indexed oldState, uint8 indexed newState, address indexed initiator);
    event TermsAccepted(address indexed party, bytes32 termsHash, uint256 timestamp);
    event ObligationFulfilled(bytes32 indexed obligationId, address indexed fulfiller, uint256 timestamp);
    event DisputeInitiated(address indexed initiator, string reason, uint256 timestamp);
    event DisputeResolved(address indexed resolver, bytes32 resolution, uint256 timestamp);

    // Required metadata functions
    function getContractHash() external view returns (bytes32);
    function getParties() external view returns (address[] memory);
    function getCurrentState() external view returns (uint8);
    function getCreationTimestamp() external view returns (uint256);
    function getLegalJurisdiction() external view returns (string memory);

    // Required operational functions
    function acceptTerms(bytes32 termsHash) external;
    function fulfillObligation(bytes32 obligationId) external;
    function initiateDispute(string calldata reason) external;

    // Required compliance functions
    function getAuditLog() external view returns (bytes memory);
    function isCompliant() external view returns (bool);
}

struct LegalMetadata {

    string contractTitle;           // "Purchase Agreement for Widget Model X"

    string[] regulatoryFrameworks;   // ["SEC Rule 10b-5", "GDPR Article 6"]

    // Amendment
    bool isAmendable;                // Whether contract can be amended
    address amendmentAuthority;      // Who can propose amendments
    uint256 amendmentThreshold;      // Required votes for amendment (basis points)
}

struct Party {

    string legalName;                // "Acme Corporation"
    string role;                     // "Buyer", "Seller", "Guarantor"
    bytes32 identityHash;            // Hash of KYC/identity verification
    bool hasAccepted;                // Whether party accepted terms
    uint256 acceptanceTimestamp;     // When party accepted
}

Gas Optimization for Legal Contracts

Legal contracts often involve complex logic and extensive state storage, making gas optimization critical for practical deployment. Key optimization strategies include:

Gas Optimization Techniques

Technique Description Gas Savings Example
Use uint256 EVM operates on 256-bit words 10-20% uint256 instead of uint8, uint16
Pack structs Combine variables into single storage slots 20-40% Group uint128 + address (both 128-bit)
Use events Store data in logs instead of state 80-90% emit FullText(text) vs storing string
Short-circuit logic Order conditions by likelihood 5-15% require(cheap) before require(expensive)
Immutable variables Use immutable for constants set in constructor 15-25% address immutable seller;
Custom errors Use custom errors instead of require strings 30-50% error Unauthorized(); revert Unauthorized();

Optimized Contract Example

// Gas-optimized version with custom errors and struct packing
contract OptimizedPurchaseAgreement {
    // Custom errors (saves 30-50% vs require strings)
    error Unauthorized();
    error InvalidState();
    error DeadlinePassed();
    error InsufficientPayment();

    // Packed struct (fits in 2 storage slots instead of 4)
    struct CompactParty {
        address payable wallet;      // 20 bytes
        uint88 contribution;         // 11 bytes (enough for 3.09e26 wei)
        bool hasAccepted;            // 1 byte
        // Total: 32 bytes = 1 slot
    }

    // Immutable variables (cheaper than storage)
    address public immutable arbiter;
    uint256 public immutable deliveryDeadline;
    uint256 public immutable purchasePrice;

    // Packed state variables
    CompactParty public buyer;
    CompactParty public seller;
    uint8 public state;

    constructor(
        address payable _seller,
        address _arbiter,
        uint256 _deadline
    ) payable {
        if (msg.value == 0) revert InsufficientPayment();
        if (_deadline <= block.timestamp) revert DeadlinePassed();

        buyer = CompactParty(payable(msg.sender), uint88(msg.value), true);
        seller = CompactParty(_seller, 0, false);
        arbiter = _arbiter;
        deliveryDeadline = _deadline;
        purchasePrice = msg.value;
        state = 1; // Funded
    }

    function confirmDelivery() external {
        if (msg.sender != buyer.wallet) revert Unauthorized();
        if (state != 1) revert InvalidState();

        state = 3; // Completed
        seller.wallet.transfer(purchasePrice);
    }
}

Testing and Verification

Legal smart contracts require rigorous testing beyond typical software QA. Bugs can result in permanent loss of funds or unenforceable agreements. A comprehensive testing strategy includes:

  • Unit tests: Test each function in isolation using Hardhat or Foundry frameworks
  • Integration tests: Test complete contract workflows and party interactions
  • Fuzzing: Use property-based testing to find edge cases (Echidna, Foundry fuzz)
  • Formal verification: Mathematically prove contract correctness (Certora, K Framework)
  • Security audits: Professional auditors review for vulnerabilities (OpenZeppelin, Trail of Bits)
  • Economic simulation: Model game-theoretic attack scenarios and incentives
  • Legal review: Attorneys verify blockchain execution matches legal intent

Common Smart Contract Vulnerabilities

  • Reentrancy: External calls allowing recursive exploitation (use checks-effects-interactions pattern)
  • Integer overflow/underflow: Arithmetic errors (Solidity 0.8+ has built-in protection)
  • Access control bugs: Missing or incorrect permission checks (use OpenZeppelin AccessControl)
  • Front-running: Miners/bots exploiting transaction order (use commit-reveal schemes)
  • Timestamp manipulation: Miners slightly adjusting block.timestamp (allow 15-minute tolerance)
  • Denial of service: Gas limits or failed transfers preventing operations (pull over push payments)
  • Oracle manipulation: Exploiting price feed data (use multiple oracles, time-weighted averages)

Deployment and Lifecycle Management

Deploying legal smart contracts to mainnet requires careful planning. Once deployed, contracts are immutable (unless explicitly designed otherwise), so errors cannot be easily corrected. Best practices include:

Deployment Checklist

  1. Complete development and unit testing on local blockchain (Hardhat, Anvil)
  2. Deploy to public testnet (Sepolia, Goerli) and conduct integration testing
  3. Perform security audit by qualified firm (budget $15K-$100K depending on complexity)
  4. Implement audit recommendations and retest
  5. Conduct legal review to verify code matches intended legal agreement
  6. Prepare deployment transaction with accurate constructor parameters
  7. Deploy to mainnet during low gas price period (typically weekends)
  8. Verify contract source code on Etherscan for transparency
  9. Document contract address and ABI for party interaction
  10. Monitor contract execution and events through blockchain explorers

Upgradeability Strategies

While immutability provides certainty, legal contracts sometimes need amendments. Three approaches enable upgrades:

  • Proxy pattern: Separate storage (proxy) from logic (implementation), allowing logic upgrades while preserving state
  • Migration contract: Deploy new version and migrate state/funds through administrative function
  • Amendment registry: Original contract remains but points to amendment contracts for modified terms

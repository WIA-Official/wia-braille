Chapter 3

Communication Protocol Stack

Understanding the five-layer architecture for reliable data transmission in HMI systems

3.1 The OSI-Inspired Architecture

WIA-AUG-014 defines a five-layer protocol stack inspired by the classic OSI networking model, adapted specifically for human-machine interface requirements. This layered approach provides separation of concerns, enabling independent optimization and evolution of each layer while maintaining interoperability. 

┌─────────────────────────────────────┐
│ Layer 5: Application Layer          │  Intent interpretation, command generation
│ - Intent interpretation             │  User state management
│ - Command generation                │
│ - User state management             │
├─────────────────────────────────────┤
│ Layer 4: Session Layer              │  Connection management, calibration
│ - Connection management             │  Session synchronization
│ - Calibration state                 │
│ - Session synchronization           │
├─────────────────────────────────────┤
│ Layer 3: Transport Layer            │  Reliable delivery, flow control
│ - Reliable delivery (optional)      │  Multiplexing
│ - Flow control                      │
│ - Multiplexing                      │
├─────────────────────────────────────┤
│ Layer 2: Data Link Layer            │  Framing, error detection
│ - Framing                           │  Addressing
│ - Error detection/correction        │
│ - Addressing                        │
├─────────────────────────────────────┤
│ Layer 1: Physical Layer             │  Wired: USB, SPI, I2C
│ - Wired: USB, SPI, I2C              │  Wireless: BLE, WiFi, proprietary
│ - Wireless: BLE, WiFi, proprietary  │
└─────────────────────────────────────┘

3.2 Layer 1: Physical Layer

The physical layer defines the electrical, mechanical, and procedural interface to the transmission medium. HMI systems employ diverse physical media optimized for different scenarios, from ultra-low-power neural implants to high-bandwidth external prosthetics.

Wired Interfaces

Medium Bandwidth Range Power Latency Use Case
USB 3.0 5 Gbps 3m Low <1ms External devices, high bandwidth
SPI 100 Mbps 0.3m Very Low <0.1ms Implant-to-hub, ultra-low latency
I2C 3.4 Mbps 1m Ultra Low <1ms Sensor networks, low data rate
Neural Link 10 Mbps 0.01m Ultra Low <0.5ms Implant internal communication

Wireless Interfaces

Medium Bandwidth Range Power Latency Use Case
BLE 5.0 2 Mbps 50m Very Low 7.5ms Wearables, long battery life
WiFi 6 9.6 Gbps 100m High 2ms High bandwidth, multi-channel recording
60 GHz mmWave 7 Gbps 10m Medium <1ms Short-range, very high bandwidth
Medical ISM 1 Mbps 2m Ultra Low 5ms Implants, regulatory compliance

Interface Selection Criteria

For Tier 1 applications (<10ms): Prefer wired (USB, SPI) or 60 GHz mmWave wireless. BLE latency (7.5ms baseline) leaves minimal budget for higher layers.

For implants: Power consumption dominates. Medical ISM or custom ultra-low-power protocols. Accept higher latency if medically acceptable.

For research systems: WiFi 6 or USB 3.0 for maximum bandwidth. Can stream hundreds of neural channels simultaneously.

3.3 Layer 2: Data Link Layer

The data link layer organizes raw bits into frames, detects/corrects errors, and manages point-to-point or multipoint communication. WIA-AUG-014 defines a standard frame format compatible across all physical layer options.

Frame Format

┌────────┬────────┬──────────┬─────────┬──────────┬────────┐
│ Sync   │ Header │ Address  │ Length  │ Payload  │ CRC    │
│ 2 bytes│ 1 byte │ 4 bytes  │ 2 bytes │ Variable │ 4 bytes│
└────────┴────────┴──────────┴─────────┴──────────┴────────┘

Sync (0xAA55):     Frame synchronization pattern
Header:            Frame type, priority, flags
Address:           Source (16b) + Destination (16b)
Length:            Payload length in bytes
Payload:           0-65535 bytes
CRC-32:            Polynomial 0x04C11DB7 (Ethernet compatible)

Error Detection and Correction

Biological signals are often small and sensitive to noise. The data link layer employs multiple error handling strategies depending on application requirements:

  • CRC-32 Error Detection: All frames include CRC checksum. Detection rate: 99.9999% of errors. Frames with errors are discarded.
  • Forward Error Correction (FEC): Optional Reed-Solomon coding for wireless links. Corrects up to 8 symbol errors per 255-symbol block.
  • Automatic Repeat Request (ARQ): Optional for Tier 3/4 applications. Retransmit corrupted frames. Incompatible with Tier 1/2 latency requirements.
  • Packet Loss Concealment: For real-time signals, interpolate from adjacent samples rather than requesting retransmission.

3.4 Layer 3: Transport Layer

The transport layer provides end-to-end communication services including reliability, flow control, and multiplexing multiple signal streams over a single physical connection. 

interface TransportPacket {
  sequenceNumber: number;           // 32-bit sequence
  acknowledgmentNumber: number;     // Last successfully received packet

  flags: {
    SYN: boolean;                   // Connection initiation
    ACK: boolean;                   // Acknowledgment
    FIN: boolean;                   // Connection termination
    RST: boolean;                   // Reset connection
    PRI: boolean;                   // Priority data
    REL: boolean;                   // Reliable delivery required
  };

  window: number;                   // Flow control window (bytes)
  checksum: number;                 // 16-bit checksum
  urgentPointer: number;            // Priority data pointer
  payload: Uint8Array;
}

Reliable vs. Unreliable Transport

Unlike traditional networks where reliability is always desired, HMI systems make explicit tradeoffs between reliability and latency:

Application Reliability Mode Rationale
Motor commands (Tier 1) Unreliable Stale commands worse than missing commands; new data arrives quickly
Sensory feedback (Tier 2) Unreliable Human perception tolerates dropouts; latency more critical
Configuration updates Reliable Must arrive correctly; latency acceptable
Calibration data Reliable Errors would corrupt calibration; latency acceptable
Device state Semi-reliable Retry once; if fails, send with next update

Flow Control Mechanisms

HMI systems generate data at widely varying rates, from sparse event-driven commands to continuous high-rate neural recordings. Flow control prevents buffer overflow and manages congestion.

Sliding Window Protocol

The sender maintains a window of unacknowledged packets. Receiver advertises window size based on available buffer space. When window fills, sender pauses until acknowledgments arrive, freeing window space.

Window Size Tuning:

  • Small windows (4-8 packets): Low latency, less buffering, suitable for Tier 1/2
  • Large windows (32-128 packets): Higher throughput, more buffering, Tier 3/4
  • Dynamic adjustment: Increase window when network performs well, decrease on congestion

3.5 Layer 4: Session Layer

The session layer manages long-lived connections between users and augmentation devices, maintaining calibration state, handling reconnection after temporary disconnects, and synchronizing multiple devices.

Calibration State Management

Sessions maintain calibration parameters that personalize signal interpretation. When a session disconnects and reconnects (e.g., device power cycled), previously-loaded calibration is restored automatically. 

interface SessionState {
  sessionId: string;
  userId: string;
  deviceId: string;
  startTime: Date;

  calibration: {
    profileId: string;
    loadedAt: Date;
    models: Map<string, CalibrationModel>;
    signalBaselines: Map<string, number[]>;
  };

  synchronization: {
    clockOffset: number;          // Microseconds
    lastSync: Date;
    driftRate: number;            // PPM
  };

  quality: {
    packetLoss: number;           // 0-1
    averageLatency: number;       // ms
    signalQuality: number;        // 0-100
  };
}

3.6 Layer 5: Application Layer

The application layer implements domain-specific logic: decoding user intent from biological signals, generating device commands, providing sensory feedback, and managing user-facing features.

Intent Decoding Pipeline

Raw Signals → Preprocessing → Feature Extraction → Classification → Intent
                    ↓               ↓                    ↓              ↓
                Filtering      Time/Frequency        ML Model       Action
                Artifact       Features              (trained       + Parameters
                Removal        Statistical           per user)      + Confidence

Command Generation

Decoded intents are translated into device-specific motor commands with appropriate safety constraints and control policies: 

interface MotorCommand {
  deviceId: string;
  timestamp: bigint;                // Intended execution time
  commandType: 'position' | 'velocity' | 'force' | 'impedance';

  joints: {
    jointId: number;
    target: number;
    limits: {
      min: number;
      max: number;
      maxVelocity: number;
      maxAcceleration: number;
      maxForce: number;
    };
    compliance: number;             // 0 = rigid, 1 = compliant
  }[];

  safetyOverride: boolean;          // Require explicit confirmation
  priority: number;                 // 0-255, higher = more urgent
}

Key Takeaways

  • WIA-AUG-014 defines a five-layer protocol stack separating physical, data link, transport, session, and application concerns
  • Physical layer options range from ultra-low-power wireless implants to high-bandwidth wired interfaces
  • Data link layer provides framing, error detection (CRC-32), and optional forward error correction
  • Transport layer offers both reliable and unreliable modes, with reliability traded for latency in real-time applications
  • Session layer manages long-lived connections, calibration state, and multi-device synchronization
  • Application layer implements intent decoding, command generation, and domain-specific logic
  • Each layer can evolve independently while maintaining backward compatibility through versioning

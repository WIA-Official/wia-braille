6.1 Time-Series Databases

Industrial IoT generates massive volumes of time-stamped data. Traditional relational databases struggle with high write throughput (10K-1M points/sec) and time-based queries. Time-Series Databases (TSDBs) optimize for temporal data with specialized indexing, compression, and query engines.

6.1.2 InfluxDB Schema Design

// InfluxDB Line Protocol
measurement,tag1=value1,tag2=value2 field1=value1,field2=value2 timestamp

// Example: Sensor data
sensor_data,sensor_id=temp-001,location=line-A,equipment=furnace temperature=850.5,pressure=1.2 1609459200000000000

// Schema components:
// - Measurement: sensor_data (table name)
// - Tags: sensor_id, location, equipment (indexed, for filtering)
// - Fields: temperature, pressure (values, for aggregation)
// - Timestamp: nanosecond precision

// Best practices:
// 1. Tags: Low-medium cardinality (<100K unique values)
// 2. Fields: High cardinality, numeric values
// 3. Avoid: High-cardinality tags (UUID, timestamp strings)
// Node.js InfluxDB Client
const { InfluxDB, Point } = require('@influxdata/influxdb-client');

const influx = new InfluxDB({
  url: 'http://localhost:8086',
  token: 'my-secret-token'
});

const writeApi = influx.getWriteApi('factory', 'sensor_bucket');

// Write single point
const point = new Point('sensor_data')
  .tag('sensor_id', 'temp-001')
  .tag('location', 'line-A')
  .tag('equipment', 'furnace')
  .floatField('temperature', 850.5)
  .floatField('pressure', 1.2);

writeApi.writePoint(point);

// Batch write (more efficient)
const points = [];
for (let i = 0; i < 1000; i++) {
  points.push(
    new Point('sensor_data')
      .tag('sensor_id', `temp-${i.toString().padStart(3, '0')}`)
      .tag('location', 'line-A')
      .floatField('temperature', 45 + Math.random() * 10)
      .timestamp(new Date())
  );
}

writeApi.writePoints(points);
await writeApi.close(); // Flush buffer

// Query with Flux
const queryApi = influx.getQueryApi('factory');
const flux = `
  from(bucket: "sensor_bucket")
    |> range(start: -1h)
    |> filter(fn: (r) => r._measurement == "sensor_data")
    |> filter(fn: (r) => r.sensor_id == "temp-001")
    |> aggregateWindow(every: 5m, fn: mean)
`;

for await (const {values, tableMeta} of queryApi.iterateRows(flux)) {
  console.log(`${values._time}: ${values._value}°C`);
}

6.2 OEE Calculation

Overall Equipment Effectiveness (OEE) is the gold standard for measuring manufacturing productivity:

6.2.1 OEE Formula

ComponentFormulaWorld-Class TargetData Sources
Availability(Operating Time / Planned Production Time) × 100%>90%PLC status, downtime logs
Performance(Actual Output / Target Output) × 100%>95%Production counters, cycle time
Quality(Good Units / Total Units) × 100%>99%Quality inspection, reject counts
OEEAvailability × Performance × Quality>85%Combined metrics
// Real-time OEE Calculator
class OEECalculator {
  async calculate(machineId: string, startTime: Date, endTime: Date) {
    // 1. Availability: (Operating Time / Planned Time)
    const plannedTime = (endTime.getTime() - startTime.getTime()) / 1000 / 60; // minutes
    const downtime = await this.getDowntime(machineId, startTime, endTime);
    const operatingTime = plannedTime - downtime;
    const availability = operatingTime / plannedTime;

    // 2. Performance: (Actual Output / Target Output)
    const actualOutput = await this.getProductionCount(machineId, startTime, endTime);
    const targetCycleTime = await this.getTargetCycleTime(machineId); // minutes per unit
    const targetOutput = operatingTime / targetCycleTime;
    const performance = actualOutput / targetOutput;

    // 3. Quality: (Good Units / Total Units)
    const rejectCount = await this.getRejectCount(machineId, startTime, endTime);
    const goodUnits = actualOutput - rejectCount;
    const quality = goodUnits / actualOutput;

    // OEE = A × P × Q
    const oee = availability * performance * quality;

    return {
      availability: (availability * 100).toFixed(1) + '%',
      performance: (performance * 100).toFixed(1) + '%',
      quality: (quality * 100).toFixed(1) + '%',
      oee: (oee * 100).toFixed(1) + '%',
      metrics: {
        plannedTime,
        operatingTime,
        downtime,
        actualOutput,
        targetOutput,
        goodUnits,
        rejectCount
      }
    };
  }

  private async getDowntime(machineId: string, start: Date, end: Date): Promise {
    const flux = `
      from(bucket: "production")
        |> range(start: ${start.toISOString()}, stop: ${end.toISOString()})
        |> filter(fn: (r) => r.machine_id == "${machineId}")
        |> filter(fn: (r) => r.status == "stopped")
        |> sum(column: "duration_minutes")
    `;
    return await influx.query(flux);
  }

  // ... similar methods for production count, reject count
}

// Usage
const calculator = new OEECalculator();
const result = await calculator.calculate('machine-001', 
  new Date('2025-01-01T06:00:00Z'),
  new Date('2025-01-01T14:00:00Z')
);

console.log(result);
// {
//   availability: '90.6%',
//   performance: '92.0%',
//   quality: '95.0%',
//   oee: '79.2%'
// }

Key Takeaways

  • TSDB Selection: InfluxDB (1M points/sec, 10-30x compression), TimescaleDB (SQL compatibility, 20x compression), QuestDB (4M rows/sec, highest throughput)
  • Schema Design: Use tags for indexed dimensions (sensor_id, location), fields for numeric values (temperature, pressure), avoid high-cardinality tags
  • OEE Formula: Availability × Performance × Quality, world-class target >85%, requires PLC status, production counters, quality data
  • Real-Time Monitoring: Grafana dashboards with 5-second refresh, threshold-based color coding (red <60%, yellow 60-85%, green >85%)
  • Alert Strategy: Multi-channel notifications (Email/SMS/Slack) based on severity, escalation for critical issues (machine down, quality)
  • Data Retention: Hot storage (7-30 days raw data), warm storage (90 days 1-min aggregates), cold storage (2+ years 1-hour aggregates)

6.4 Data Retention Policies

Industrial time-series data grows rapidly. A factory with 1000 sensors at 1Hz generates 86.4 million points daily. Intelligent retention policies balance storage costs against analytical value.

6.4.1 Tiered Storage Strategy

TierDurationResolutionUse CasesStorage Cost
Hot (Raw)7-30 daysOriginal (1Hz)Real-time monitoring, troubleshootingHigh (SSD)
Warm (1-min)90 days1-minute aggregatesShort-term trending, shift reportsMedium (SSD/HDD)
Cold (1-hour)2+ years1-hour aggregatesLong-term analysis, complianceLow (HDD/Object storage)
Archive7+ yearsDaily summariesRegulatory compliance, auditsVery low (Tape/Glacier)
// InfluxDB Retention Policies
// CLI commands to create retention policies

// Raw data: 7 days
influx -execute 'CREATE RETENTION POLICY "raw_7d" ON "factory_db" DURATION 7d REPLICATION 1 DEFAULT'

// 1-minute aggregates: 90 days
influx -execute 'CREATE RETENTION POLICY "agg_1m_90d" ON "factory_db" DURATION 90d REPLICATION 1'

// 1-hour aggregates: 2 years
influx -execute 'CREATE RETENTION POLICY "agg_1h_2y" ON "factory_db" DURATION 104w REPLICATION 1'

// Continuous Query for downsampling
influx -execute '
CREATE CONTINUOUS QUERY "cq_1m_agg" ON "factory_db"
BEGIN
  SELECT mean("temperature") AS "temperature",
         mean("pressure") AS "pressure",
         max("temperature") AS "temperature_max",
         min("temperature") AS "temperature_min"
  INTO "factory_db"."agg_1m_90d"."sensor_data_1m"
  FROM "factory_db"."raw_7d"."sensor_data"
  GROUP BY time(1m), *
END'

// Storage savings calculation:
// Raw: 1000 sensors × 86400 points/day × 7 days × 8 bytes = 4.8 GB
// 1-min: 1000 × 1440 points/day × 90 days × 8 bytes = 1.0 GB  
// 1-hour: 1000 × 24 points/day × 730 days × 8 bytes = 140 MB
// Total: 5.94 GB vs 175 GB (30 days raw) = 97% reduction

6.4.2 Advanced Query Patterns

// Complex Flux queries for industrial analytics

// 1. Downtime analysis - Group by reason code
from(bucket: "production")
  |> range(start: -30d)
  |> filter(fn: (r) => r._measurement == "downtime_events")
  |> filter(fn: (r) => r.machine_id == "machine-001")
  |> group(columns: ["reason_code"])
  |> sum(column: "duration_minutes")
  |> sort(desc: true)

// 2. Production efficiency by shift
from(bucket: "production")
  |> range(start: -7d)
  |> filter(fn: (r) => r._measurement == "production_count")
  |> window(every: 8h) // 8-hour shifts
  |> sum()
  |> duplicate(column: "_stop", as: "shift_end")

// 3. Anomaly detection with statistical functions
from(bucket: "sensors")
  |> range(start: -24h)
  |> filter(fn: (r) => r.sensor_id == "temp-001")
  |> aggregateWindow(every: 5m, fn: mean)
  |> movingAverage(n: 12) // 1-hour window
  |> derivative(nonNegative: true)
  |> filter(fn: (r) => r._value > 5.0) // Sudden spikes > 5°C/5min

// 4. Cross-sensor correlation
temp = from(bucket: "sensors")
  |> range(start: -1h)
  |> filter(fn: (r) => r.sensor_id == "temp-001")
  |> keep(columns: ["_time", "_value"])

pressure = from(bucket: "sensors")
  |> range(start: -1h)
  |> filter(fn: (r) => r.sensor_id == "pressure-001")
  |> keep(columns: ["_time", "_value"])

join(tables: {temp: temp, pressure: pressure}, on: ["_time"])
  |> map(fn: (r) => ({
      _time: r._time,
      temp: r._value_temp,
      pressure: r._value_pressure,
      ratio: r._value_temp / r._value_pressure
    }))

6.5 Performance Optimization

6.5.1 Write Performance Tuning

TechniqueImpactImplementationTradeoff
Batch Writes10-100x throughputBuffer 100-1000 pointsSlight latency increase
Tag Caching50% reduction in index sizeLimit tag cardinality <100KSchema design constraint
Write Ahead Log99.99% durabilityEnable WAL in config+10-20% disk usage
Compression10-30x storage reductionSnappy/GZIP/LZ4+5-15% CPU usage
// Optimized batch writer with backpressure handling
class OptimizedInfluxWriter {
  private buffer: Point[] = [];
  private maxBatchSize = 1000;
  private maxBatchInterval = 1000; // ms
  private lastFlush = Date.now();

  constructor(private writeApi: WriteApi) {
    // Auto-flush on interval
    setInterval(() => this.flush(), this.maxBatchInterval);
  }

  write(point: Point) {
    this.buffer.push(point);

    if (this.buffer.length >= this.maxBatchSize) {
      this.flush();
    }
  }

  private flush() {
    if (this.buffer.length === 0) return;

    const points = this.buffer.splice(0, this.maxBatchSize);
    this.writeApi.writePoints(points);
    this.lastFlush = Date.now();

    console.log(`Flushed ${points.length} points`);
  }

  async close() {
    this.flush();
    await this.writeApi.close();
  }
}

// Usage achieves ~100x better throughput than individual writes
const writer = new OptimizedInfluxWriter(influx.getWriteApi('factory', 'sensors'));

for (let i = 0; i < 100000; i++) {
  writer.write(
    new Point('sensor_data')
      .tag('sensor_id', `temp-${i % 1000}`)
      .floatField('temperature', 45 + Math.random() * 10)
  );
}

await writer.close();

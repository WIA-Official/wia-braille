CHAPTER 7

Best Practices and Patterns

7.1 Error Handling Principles

  1. Fail Fast, Recover Smart: Detect errors immediately, but have intelligent recovery
  2. Never Swallow Errors: Always log, always propagate with context
  3. Be Specific: Use precise error codes, not generic catch-alls
  4. Think User First: Error messages should guide users, not confuse them
  5. Automate Recovery: Let recovery strategies handle retries, not manual code
  6. Monitor Everything: Every error is a learning opportunity
  7. Test Failure Paths: Error handling code must be tested as thoroughly as happy paths
  8. Document Error Contracts: APIs must document which errors they throw

7.2 Common Anti-Patterns to Avoid

// ❌ ANTI-PATTERN: Swallowing errors
try {
  await riskyOperation();
} catch (error) {
  // Silently ignoring - terrible!
}

// ✅ CORRECT: Log and handle
try {
  await riskyOperation();
} catch (error) {
  logger.error('Operation failed', { error, context });
  throw new WIAError({
    code: 'WIA-API-INTERNAL-001',
    message: 'Operation failed',
    severity: 'ERROR',
    recovery: 'RETRY_WITH_BACKOFF',
    context: { operation: 'riskyOperation' },
    causedBy: error
  });
}

// ❌ ANTI-PATTERN: Generic error codes
throw new Error('Something went wrong'); // Useless!

// ✅ CORRECT: Specific WIA code
throw new WIAError({
  code: 'WIA-DB-CONNECTION-001',  // Specific!
  message: 'Failed to connect to PostgreSQL',
  severity: 'CRITICAL',
  recovery: 'RETRY_WITH_BACKOFF'
});

// ❌ ANTI-PATTERN: Retry without backoff
for (let i = 0; i < 100; i++) {
  try {
    return await api.call();
  } catch (e) {
    // Hammering the failing service!
  }
}

// ✅ CORRECT: Exponential backoff
return await retryWithBackoff(
  () => api.call(),
  { maxAttempts: 5, baseDelay: 1000 }
);

// ❌ ANTI-PATTERN: Losing error context
try {
  await serviceA.call();
} catch (error) {
  throw new Error('ServiceA failed'); // Lost original error!
}

// ✅ CORRECT: Preserve original error
try {
  await serviceA.call();
} catch (error) {
  throw new WIAError({
    code: 'WIA-API-INTERNAL-001',
    message: 'ServiceA failed',
    severity: 'ERROR',
    recovery: 'RETRY_WITH_BACKOFF',
    causedBy: error  // Preserved!
  });
}

7.3 Production-Ready Error Handling

class ProductionErrorHandler {
  async handleRequest(req, res) {
    const correlationId = req.headers['x-correlation-id'] || generateUUID();

    try {
      const result = await this.processRequest(req, correlationId);
      res.json(result);
    } catch (error) {
      const wiaError = this.toWIAError(error, correlationId);

      // 1. Log with full context
      logger.error('Request failed', {
        error: wiaError.toJSON(),
        request: {
          method: req.method,
          path: req.path,
          query: req.query,
          userId: req.user?.id
        }
      });

      // 2. Track metrics
      metrics.increment('errors_total', {
        code: wiaError.code,
        severity: wiaError.severity
      });

      // 3. Alert if critical
      if (wiaError.severity === 'CRITICAL') {
        await alerting.page({
          title: `Critical error: ${wiaError.code}`,
          error: wiaError,
          runbook: this.getRunbook(wiaError.code)
        });
      }

      // 4. Apply recovery strategy
      if (wiaError.recovery === 'RETRY_WITH_BACKOFF') {
        // Queue for retry
        await retryQueue.add(req, { delay: 2000 });
      }

      // 5. Return user-friendly response
      res.status(this.toHTTPStatus(wiaError)).json({
        error: {
          code: wiaError.code,
          message: this.toUserMessage(wiaError),
          correlationId: wiaError.correlationId,
          // Include recovery hint
          retryable: wiaError.recovery === 'RETRY_WITH_BACKOFF'
        }
      });
    }
  }
}

7.4 Testing Error Handling

describe('Error Handling', () => {
  it('should retry on timeout with backoff', async () => {
    const mockAPI = jest.fn()
      .mockRejectedValueOnce(new WIAError({
        code: 'WIA-NET-TIMEOUT-015',
        message: 'Timeout',
        severity: 'ERROR',
        recovery: 'RETRY_WITH_BACKOFF'
      }))
      .mockRejectedValueOnce(new WIAError({
        code: 'WIA-NET-TIMEOUT-015',
        message: 'Timeout',
        severity: 'ERROR',
        recovery: 'RETRY_WITH_BACKOFF'
      }))
      .mockResolvedValueOnce({ data: 'success' });

    const result = await retryWithBackoff(mockAPI, { maxAttempts: 3 });

    expect(result).toEqual({ data: 'success' });
    expect(mockAPI).toHaveBeenCalledTimes(3);
  });

  it('should use fallback when primary fails', async () => {
    const primary = jest.fn().mockRejectedValue(new Error('Primary down'));
    const fallback = jest.fn().mockResolvedValue({ data: 'fallback' });

    const result = await withFallback(primary, fallback);

    expect(result).toEqual({ data: 'fallback' });
    expect(fallback).toHaveBeenCalled();
  });

  it('should open circuit breaker after threshold', async () => {
    const breaker = new CircuitBreaker({ failureThreshold: 3 });
    const failing = jest.fn().mockRejectedValue(new Error('Failed'));

    // First 3 failures should be attempted
    for (let i = 0; i < 3; i++) {
      await expect(breaker.execute(failing)).rejects.toThrow();
    }

    // Circuit should now be open
    await expect(breaker.execute(failing)).rejects.toThrow('Circuit breaker is OPEN');

    // Should not have called the 4th time
    expect(failing).toHaveBeenCalledTimes(3);
  });
});

7.5 Monitoring and Observability

Error Monitoring Dashboard Checklist

  • Error rate by severity (CRITICAL, ERROR, WARNING)
  • Top 10 error codes by frequency
  • Error distribution by service
  • Mean time to resolution (MTTR) by error type
  • Recovery strategy success rates
  • Error trends over time (hourly, daily, weekly)
  • Correlation between errors and deployments
  • User impact metrics (affected users, failed requests)

7.6 Documentation Standards

Every API endpoint should document potential errors:

/**
 * Process user payment
 *

7.7 Incident Response Runbooks

Create runbooks for each CRITICAL and common ERROR codes:

# Runbook: WIA-DB-CONNECTION-001

## Severity: CRITICAL

## Description
Unable to establish connection to primary database.

## Impact
All write operations will fail. Read operations may fail if read replica is also down.

## Immediate Actions
1. Check database server status: `pg_isready -h db-primary.example.com`
2. Check network connectivity: `ping db-primary.example.com`
3. Check connection pool: `SELECT count(*) FROM pg_stat_activity;`
4. Check recent deployments (possible config change)

## Recovery Steps
1. If connection pool exhausted: Restart application servers
2. If database unresponsive: Failover to read replica
3. If network issue: Update DNS to point to backup region
4. If credentials invalid: Rotate database credentials

## Escalation
If not resolved in 15 minutes:
1. Page Database SRE team
2. Notify VP Engineering
3. Prepare customer communication

## Post-Incident
1. Update capacity planning
2. Review connection pool settings
3. Implement additional monitoring
4. Document lessons learned

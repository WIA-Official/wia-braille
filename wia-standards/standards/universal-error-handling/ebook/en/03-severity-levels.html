CHAPTER 3

Severity Levels and Classification

3.1 The Four Severity Levels

Every WIA error is classified into one of four severity levels. This classification determines how urgently the error must be addressed, what automated responses should be triggered, and how it's presented to users and operators.

🔴 CRITICAL

System Failure - Immediate Action Required

Critical errors indicate complete system failure or data loss scenarios. These require immediate human intervention and typically trigger incident response procedures.

Examples:

  • Database server completely unavailable
  • Data corruption detected
  • Security breach in progress
  • Payment processing system offline
  • Critical service dependency failure

Response Time: Immediate (< 5 minutes)

Notification: Page on-call engineer, executive escalation

User Impact: Service completely unavailable

🟠 ERROR

Operation Failed - User Impact

Error level indicates that a specific operation failed but the overall system remains functional. Users are impacted but the service is still available for other operations.

Examples:

  • Failed authentication attempt
  • Database query timeout
  • Invalid user input
  • External API call failed
  • File upload failure

Response Time: Within 1 hour

Notification: Alert team, create ticket

User Impact: Specific feature unavailable, clear error message shown

🟡 WARNING

Potential Issue - Degraded Performance

Warning level indicates potential problems that haven't caused failures yet but might lead to issues. System continues operating but performance may be degraded.

Examples:

  • High database connection pool usage
  • Approaching rate limits
  • Cache miss rate increasing
  • Slow query performance
  • Deprecated API usage

Response Time: Within 24 hours

Notification: Daily digest, team dashboard

User Impact: No immediate impact, may experience slower performance

🔵 INFO

Informational - No Action Needed

Info level provides operational visibility into expected conditions. These aren't errors in the traditional sense but important state changes or conditions worth logging.

Examples:

  • Cache miss (expected behavior)
  • Resource not found (valid query result)
  • Graceful service degradation triggered
  • Fallback mechanism activated successfully
  • Configuration change applied

Response Time: Review during retrospectives

Notification: Logged only, aggregated in metrics

User Impact: None

3.2 Severity Classification Guidelines

3.2.1 Decision Matrix

Use this decision matrix to classify error severity correctly:

Question CRITICAL ERROR WARNING INFO
Can users complete their tasks? No - service down No - this task fails Yes - slower/degraded Yes - normal
Is data at risk? Yes - loss/corruption Possibly - transaction failed No No
How many users impacted? All users Individual users Potentially many None
Can system auto-recover? No - manual intervention Maybe - retry possible Yes - fallback active N/A
Business impact? Severe - revenue loss Moderate - UX degraded Minor - performance None

3.2.2 Common Classification Mistakes

Mistake #1: Over-escalation

❌ WRONG: Classify cache miss as ERROR
Cache misses are expected behavior when cache is cold or data expires.
✅ CORRECT: Classify as INFO

❌ WRONG: Classify rate limit as CRITICAL
Individual users hitting rate limits doesn't mean system failure.
✅ CORRECT: Classify as WARNING or ERROR depending on frequency

Mistake #2: Under-escalation

❌ WRONG: Classify database down as ERROR
If database is completely unavailable, entire service fails.
✅ CORRECT: Classify as CRITICAL

❌ WRONG: Classify payment processing failure as WARNING
Failed payments directly impact revenue and user trust.
✅ CORRECT: Classify as ERROR or CRITICAL depending on scope

Mistake #3: Severity Inflation

Teams sometimes inflate severity to ensure errors get attention. This leads to alert fatigue and actual critical errors being missed. Instead:

  • Use WARNING for potential issues and monitor trends
  • Aggregate INFO-level events for pattern detection
  • Reserve CRITICAL only for true emergencies
  • Tune alert thresholds rather than inflating severity

3.3 Severity in Different Contexts

3.3.1 Context-Dependent Severity

The same error code can have different severity levels depending on context:

// Database timeout during read operation
WIA-DB-TIMEOUT-015 (Severity: ERROR)
- User sees error message
- Can retry or use cached data
- Service continues for other users

// Database timeout during write operation (payment processing)
WIA-DB-TIMEOUT-015 (Severity: CRITICAL)
- Money movement may be in inconsistent state
- Requires manual reconciliation
- Could affect many transactions

WIA-CORE-010 allows severity override based on context:

// Default severity
throw new WIAError({
  code: 'WIA-DB-TIMEOUT-015',
  message: 'Query timeout',
  // severity defaults to ERROR per standard
});

// Context-specific override
throw new WIAError({
  code: 'WIA-DB-TIMEOUT-015',
  message: 'Payment processing timeout',
  severity: 'CRITICAL',  // Override for critical operation
  context: {
    operation: 'payment_processing',
    amount: 1000.00,
    transactionId: 'txn_123'
  }
});

3.3.2 Severity Escalation

Errors can be escalated based on frequency or pattern:

  • Single occurrence: WIA-NET-TIMEOUT-015 = ERROR
  • 10 occurrences in 1 minute: Escalate to WARNING (pattern emerging)
  • 100 occurrences in 1 minute: Escalate to CRITICAL (cascading failure)
// Automatic severity escalation
class ErrorEscalator {
  track(error) {
    const count = this.countRecent(error.code, '1m');

    if (count > 100) {
      return { ...error, severity: 'CRITICAL' };
    } else if (count > 10) {
      return { ...error, severity: 'WARNING' };
    }

    return error;
  }
}

3.4 Severity and Observability

3.4.1 Alert Configuration

Severity levels drive alert routing and escalation policies:

Severity Alert Channel Escalation Auto-Remediation
CRITICAL PagerDuty, Phone, SMS, Slack Immediate, escalate to VP after 15min Trigger failover, scale resources
ERROR Slack, Email, Ticket 1 hour SLA, escalate to manager Retry, circuit breaker
WARNING Daily digest, Dashboard 24 hour review, team discussion Scale preventively, clear cache
INFO Logs only, Metrics Weekly retrospective None - informational only

3.4.2 Dashboard Design

Organize monitoring dashboards by severity:

Dashboard: Error Overview
├── CRITICAL Errors (count, last occurrence, MTTR)
├── ERROR Rate (trend, top errors, affected users)
├── WARNING Trends (patterns, predictions, thresholds)
└── INFO Events (volume, distribution, anomalies)

Each severity level has different visualization needs:
- CRITICAL: Red alerts, require acknowledgment
- ERROR: Orange counters, filterable by service
- WARNING: Yellow trends, show historical patterns
- INFO: Blue metrics, aggregate statistics

3.5 Severity Best Practices

  1. Start Conservative: When in doubt, use a lower severity. You can always escalate based on monitoring.
  2. Review Regularly: Audit error severity quarterly. Business priorities change.
  3. Use Context: Same error code can have different severity in different contexts.
  4. Monitor Patterns: Single errors may be low severity, but patterns indicate bigger issues.
  5. Document Decisions: Record why specific errors have specific severities.
  6. Align with SLOs: Severity should map to your service level objectives.
  7. Train Teams: Ensure everyone understands severity classification criteria.
  8. Avoid Inflation: Too many CRITICAL alerts leads to alert fatigue.

CHAPTER 5

Error Propagation in Distributed Systems

5.1 The Challenge of Error Propagation

In distributed systems, errors don't stay local - they propagate across service boundaries, through message queues, over HTTP APIs, and between different programming languages. Without standardized error handling, critical context is lost at each hop.

Consider a typical request flow: Frontend → API Gateway → Auth Service → Payment Service → Database. An error in the database needs to propagate all the way back to the frontend with complete context, through multiple services written in different languages.

5.2 Correlation IDs and Distributed Tracing

Every WIA error includes a correlation ID that links related errors across the entire request chain:

// Service A (JavaScript)
const correlationId = generateUUID();

try {
  await callServiceB({ data, correlationId });
} catch (error) {
  throw new WIAError({
    code: 'WIA-API-INTERNAL-001',
    message: 'Service B call failed',
    severity: 'ERROR',
    recovery: 'RETRY_WITH_BACKOFF',
    correlationId,  // Preserve correlation ID
    context: {
      service: 'ServiceA',
      operation: 'processOrder',
      causedBy: error  // Nest original error
    }
  });
}

// Service B (Python)
def process_request(data, correlation_id):
    try:
        db.execute(query)
    except Exception as e:
        raise WIAError(
            code="WIA-DB-TIMEOUT-015",
            message="Database timeout",
            severity="ERROR",
            recovery="RETRY_WITH_BACKOFF",
            correlation_id=correlation_id,  // Same ID
            context={
                "service": "ServiceB",
                "query": query[:100]
            }
        )

// All errors share the same correlation ID for full trace

5.4 Cross-Language Error Handling

WIA-CORE-010 enables seamless error propagation across different programming languages:

// Frontend (TypeScript) → API (Go) → Service (Python) → Database

// TypeScript Frontend
try {
  const result = await api.post('/orders', orderData);
} catch (error) {
  if (error.code === 'WIA-DB-TIMEOUT-015') {
    // Show user-friendly message
    toast.error('Order processing delayed. Please wait...');
    // Automatic retry from recovery strategy
    setTimeout(() => retry(), 2000);
  }
}

// Go API Gateway
func handleOrder(w http.ResponseWriter, r *http.Request) {
    result, err := paymentService.Process(orderData)
    if err != nil {
        if wiaErr, ok := err.(*wia.Error); ok {
            // Preserve WIA error across language boundary
            http.Error(w, wiaErr.ToJSON(), wiaErr.HTTPStatus())
            return
        }
    }
}

// Python Payment Service
def process_payment(order_data):
    try:
        db.execute("INSERT INTO payments ...")
    except TimeoutError:
        raise WIAError(
            code="WIA-DB-TIMEOUT-015",
            message="Payment database timeout",
            severity="ERROR",
            recovery="RETRY_WITH_BACKOFF"
        )

// Same error code flows seamlessly through all three languages

5.5 HTTP Error Mapping

WIA errors map to HTTP status codes for REST APIs:

WIA Error Code                 → HTTP Status
WIA-AUTH-INVALID-*            → 401 Unauthorized
WIA-AUTH-PERMISSION-*         → 403 Forbidden
WIA-*-NOTFOUND-*              → 404 Not Found
WIA-VALIDATE-INVALID-*        → 400 Bad Request
WIA-*-CONFLICT-*              → 409 Conflict
WIA-API-RATE_LIMIT-*          → 429 Too Many Requests
WIA-*-TIMEOUT-*               → 504 Gateway Timeout
WIA-*-INTERNAL-*              → 500 Internal Server Error
WIA-*-*                       → 503 Service Unavailable (if CRITICAL)

// Implementation
function toHTTPStatus(wiaError) {
  const codeMap = {
    'WIA-AUTH-INVALID': 401,
    'WIA-AUTH-PERMISSION': 403,
    'WIA-NOTFOUND': 404,
    'WIA-VALIDATE-INVALID': 400,
    'WIA-CONFLICT': 409,
    'WIA-RATE_LIMIT': 429,
    'WIA-TIMEOUT': 504
  };

  for (const [pattern, status] of Object.entries(codeMap)) {
    if (wiaError.code.includes(pattern)) {
      return status;
    }
  }

  return wiaError.severity === 'CRITICAL' ? 503 : 500;
}

5.6 Message Queue Error Handling

Errors in async message processing require special handling:

class MessageProcessor {
  async process(message) {
    try {
      await this.handleMessage(message);
      await this.queue.ack(message);
    } catch (error) {
      const wiaError = this.toWIAError(error, message);

      // Recovery strategy from error
      switch (wiaError.recovery) {
        case 'RETRY_WITH_BACKOFF':
          // Re-queue with delay
          await this.queue.nack(message, {
            delay: this.calculateBackoff(message.retryCount),
            maxRetries: 5
          });
          break;

        case 'FAIL_FAST':
          // Move to dead letter queue
          await this.deadLetterQueue.send(message, wiaError);
          await this.queue.ack(message);
          break;

        case 'MANUAL':
          // Alert ops team, keep in queue
          await this.alerting.notify(wiaError);
          await this.queue.nack(message, { delay: 300000 }); // 5 min
          break;

        default:
          // Unknown recovery, move to DLQ
          await this.deadLetterQueue.send(message, wiaError);
          await this.queue.ack(message);
      }

      // Log with full context
      logger.error('Message processing failed', {
        error: wiaError,
        messageId: message.id,
        retryCount: message.retryCount
      });
    }
  }
}

5.7 Error Aggregation and Analysis

Centralized error tracking becomes powerful with standardized error codes:

// Error Aggregation Pipeline
class ErrorAggregator {
  async track(error) {
    // Store in time-series database
    await this.influx.write({
      measurement: 'errors',
      tags: {
        code: error.code,
        domain: this.extractDomain(error.code),
        category: this.extractCategory(error.code),
        severity: error.severity,
        service: error.context.service,
        recovery: error.recovery
      },
      fields: {
        message: error.message,
        correlationId: error.correlationId,
        count: 1
      },
      timestamp: error.timestamp
    });

    // Update real-time metrics
    this.prometheus.increment('errors_total', {
      code: error.code,
      severity: error.severity
    });

    // Check for patterns
    await this.detectAnomalies(error);
  }

  async detectAnomalies(error) {
    // Get error rate for this code in last 5 minutes
    const recentCount = await this.getRecentCount(error.code, '5m');

    // Get baseline for this code
    const baseline = await this.getBaseline(error.code);

    // Alert if 10x baseline
    if (recentCount > baseline * 10) {
      await this.alerting.send({
        title: `Error spike detected: ${error.code}`,
        severity: 'WARNING',
        current: recentCount,
        baseline,
        errors: await this.getRecentErrors(error.code, '5m')
      });
    }
  }
}

5.8 Error Transformation at Boundaries

Transform internal errors to user-friendly messages at system boundaries:

const errorMessages = {
  'WIA-AUTH-INVALID-001': {
    user: 'Invalid username or password. Please try again.',
    internal: 'Authentication failed: credential mismatch',
    httpStatus: 401
  },
  'WIA-DB-TIMEOUT-015': {
    user: 'Service temporarily unavailable. Please try again in a moment.',
    internal: 'Database query timeout after 30s',
    httpStatus: 504
  },
  'WIA-API-RATE_LIMIT-007': {
    user: 'Too many requests. Please wait a moment before trying again.',
    internal: 'Rate limit exceeded: 100 req/min',
    httpStatus: 429
  }
};

class ErrorTransformer {
  toUserMessage(wiaError) {
    const mapping = errorMessages[wiaError.code];
    if (!mapping) {
      return 'An error occurred. Please contact support.';
    }
    return mapping.user;
  }

  toAPIResponse(wiaError, includeInternals = false) {
    const mapping = errorMessages[wiaError.code];

    return {
      error: {
        code: wiaError.code,
        message: includeInternals ? mapping.internal : mapping.user,
        severity: wiaError.severity,
        correlationId: wiaError.correlationId,
        // Include recovery hint for API clients
        recovery: wiaError.recovery,
        // Only include context in dev/staging
        ...(includeInternals && { context: wiaError.context })
      }
    };
  }
}

5.9 Propagation Best Practices

  1. Always Include Correlation ID: Generate at entry point, propagate everywhere
  2. Preserve Original Error: Wrap, don't replace. Keep causedBy chain
  3. Enrich at Each Layer: Add service name, operation, local context
  4. Log Before Propagating: Each service logs errors before re-throwing
  5. Transform at Boundaries: Internal details → user messages at API edge
  6. Use Structured Logging: JSON format for machine parsing
  7. Implement Timeouts: Don't let errors propagate indefinitely
  8. Monitor Propagation Depth: Alert on excessively deep error chains

Chapter 4: Phase 1 - Data Format Specification

Phase 1 of WIA-LEGAL-001 implementation establishes the foundation for all digital court operations: standardized data formats. This chapter provides comprehensive technical specifications for representing legal information in machine-readable, interoperable formats that work across jurisdictions and systems.

4.1 JSON Schema Overview

WIA-LEGAL-001 uses JSON Schema (Draft 2020-12) as the primary mechanism for defining and validating data structures. JSON Schema provides machine-readable specifications that enable:

  • Automatic Validation: Tools can automatically verify data conforms to specifications
  • Documentation Generation: Human-readable docs auto-generated from schemas
  • Code Generation: Type-safe classes and interfaces generated for multiple languages
  • Interoperability: Universal format understood across platforms and ecosystems
Why JSON? JSON is human-readable, widely supported, and has excellent tooling support across all major programming languages. Its simplicity makes it accessible while remaining powerful enough for complex legal data.

4.8 Validation Rules

4.8.1 Business Logic Validation

Beyond schema validation, WIA-LEGAL-001 enforces business rules:

  • Chronological Consistency: Filing dates cannot be in the future; events must occur after case filing
  • Party Validation: At least two distinct parties required for most case types
  • Status Transitions: Cases can only transition between valid status pairs (e.g., "filed" → "pending", not "filed" → "decided")
  • Document Requirements: Certain case types require specific documents (e.g., criminal cases require charging documents)
  • Jurisdiction Authority: Judges can only be assigned to cases in their jurisdictions
  • Confidentiality Rules: Sealed documents cannot have public access enabled

4.8.2 Cross-Field Validation

Example validation rules implemented in application code: 

// Validation: Case filing date must be before first hearing date
function validateCaseDates(caseData, hearings) {
  const filingDate = new Date(caseData.filingDate);
  for (const hearing of hearings) {
    const hearingDate = new Date(hearing.scheduledDateTime);
    if (hearingDate < filingDate) {
      throw new ValidationError(
        `Hearing ${hearing.hearingId} scheduled before case filing date`
      );
    }
  }
  return true;
}

// Validation: Attorney must be authorized in case jurisdiction
function validateAttorneyJurisdiction(attorney, jurisdiction) {
  const hasAdmission = attorney.barAdmissions.some(admission => 
    admission.jurisdiction === jurisdiction.region &&
    admission.status === 'active'
  );
  if (!hasAdmission) {
    throw new ValidationError(
      `Attorney ${attorney.name} not admitted in ${jurisdiction.region}`
    );
  }
  return true;
}

4.9 Data Migration

4.9.1 Legacy Data Conversion

Courts with existing systems must migrate data to WIA-LEGAL-001 formats. The standard provides transformation guidelines:

Legacy Format Transformation Approach Data Quality
Structured Database Direct field mapping with data cleansing High (90-95%)
Semi-structured (XML/CSV) Parser with validation and correction Medium (70-85%)
Scanned Documents OCR + AI extraction + manual review Low-Medium (50-70%)
Paper Records Digitization + OCR + data entry + QA Variable (40-80%)

4.9.2 Migration Best Practices

  1. Pilot Migration: Start with 100-1000 recent cases to test processes
  2. Data Cleansing: Correct inconsistencies before migration
  3. Dual Operation: Run legacy and new systems in parallel for 3-6 months
  4. Validation Testing: Automated comparison of legacy vs. migrated data
  5. Rollback Plan: Maintain ability to revert to legacy system if needed
  6. Incremental Migration: Migrate in phases by case type or date range

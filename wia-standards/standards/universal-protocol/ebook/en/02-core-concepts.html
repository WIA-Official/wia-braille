2.1 Message Types

The Universal Protocol defines four fundamental message types that cover all communication patterns. Understanding these types is essential to effectively using the protocol.

2.1.1 Request Messages

Request messages initiate a communication exchange. They expect a response and are used in RPC (Remote Procedure Call) patterns.

{
  "id": "req_1234567890",
  "type": "request",
  "method": "users.getProfile",
  "payload": {
    "userId": "user_abc123",
    "fields": ["name", "email", "avatar", "preferences"]
  },
  "metadata": {
    "timestamp": "2025-12-27T10:30:00.000Z",
    "version": "1.0",
    "timeout": 5000,
    "retryPolicy": {
      "maxRetries": 3,
      "backoff": "exponential"
    }
  }
}

Key characteristics of request messages:

  • Must have a unique id to correlate with responses
  • Require a method that identifies what operation to perform
  • May include a timeout to prevent indefinite waiting
  • Can specify retry policies for handling failures
  • Always expect exactly one response message

2.1.2 Response Messages

Response messages are sent in reply to request messages. They contain either the result of the operation or error information.

// Success Response
{
  "id": "req_1234567890",
  "type": "response",
  "payload": {
    "userId": "user_abc123",
    "name": "Jane Doe",
    "email": "jane@example.com",
    "avatar": "https://cdn.example.com/avatars/jane.jpg",
    "preferences": {
      "theme": "dark",
      "language": "en",
      "notifications": true
    }
  },
  "metadata": {
    "timestamp": "2025-12-27T10:30:00.150Z",
    "processingTime": 45,
    "cacheHit": false
  }
}

// Error Response
{
  "id": "req_1234567890",
  "type": "response",
  "error": {
    "code": "USER_NOT_FOUND",
    "message": "User with ID 'user_abc123' does not exist",
    "details": {
      "requestedId": "user_abc123",
      "suggestions": ["Check user ID format", "Verify user exists"]
    }
  },
  "metadata": {
    "timestamp": "2025-12-27T10:30:00.050Z",
    "processingTime": 15
  }
}

2.1.3 Stream Messages

Stream messages represent a continuous flow of data. They can flow in one direction (client-to-server or server-to-client) or bidirectionally.

{
  "id": "stream_sensor_data",
  "type": "stream",
  "sequence": 42,
  "payload": {
    "sensorId": "temp_sensor_01",
    "temperature": 23.5,
    "humidity": 65.2,
    "pressure": 1013.25,
    "timestamp": "2025-12-27T10:30:00.500Z"
  },
  "metadata": {
    "streamId": "stream_sensor_data",
    "isComplete": false,
    "totalMessages": null
  }
}

Stream characteristics:

  • Include a sequence number for ordering
  • May be infinite or have a defined end
  • Support backpressure mechanisms
  • Can be paused, resumed, or cancelled
  • Maintain ordering guarantees (configurable)

2.1.4 Event Messages

Event messages are fire-and-forget notifications. They don't expect responses and are used in pub/sub patterns.

{
  "id": "evt_order_placed_7890",
  "type": "event",
  "topic": "orders.placed",
  "payload": {
    "orderId": "order_xyz789",
    "customerId": "user_abc123",
    "totalAmount": 149.99,
    "items": [
      {
        "productId": "prod_001",
        "quantity": 2,
        "price": 49.99
      },
      {
        "productId": "prod_045",
        "quantity": 1,
        "price": 49.99
      }
    ]
  },
  "metadata": {
    "timestamp": "2025-12-27T10:30:00.000Z",
    "source": "order-service",
    "priority": "normal"
  }
}

2.2 Communication Patterns

2.2.1 Request-Response (RPC)

The most common pattern where a client sends a request and waits for a response. This is analogous to function calls in programming.

// Client code
const result = await protocol.call('calculateTax', {
  amount: 100.00,
  country: 'US',
  state: 'CA'
});

console.log('Tax:', result.tax); // Tax: 8.25

// Server handler
protocol.handle('calculateTax', async (params) => {
  const taxRate = await getTaxRate(params.country, params.state);
  return {
    amount: params.amount,
    taxRate: taxRate,
    tax: params.amount * taxRate
  };
});

2.2.2 Server Streaming

The server sends multiple messages in response to a single client request. Useful for large result sets or real-time updates.

// Client code
for await (const transaction of protocol.stream('getTransactionHistory', { userId: 'user123' })) {
  console.log('Transaction:', transaction);
  updateUI(transaction);
}

// Server handler
protocol.streamHandler('getTransactionHistory', async function* (params) {
  const transactions = await database.streamTransactions(params.userId);

  for await (const tx of transactions) {
    yield {
      id: tx.id,
      amount: tx.amount,
      date: tx.date,
      description: tx.description
    };
  }
});

2.2.3 Client Streaming

The client sends multiple messages and receives a single response. Ideal for uploading large datasets or batch operations.

// Client code
const uploadStream = protocol.createClientStream('uploadSensorData');

// Send multiple readings
for (let i = 0; i < 1000; i++) {
  await uploadStream.send({
    timestamp: new Date(),
    temperature: 20 + Math.random() * 10,
    humidity: 50 + Math.random() * 20
  });
}

// Complete and get summary
const summary = await uploadStream.complete();
console.log('Uploaded:', summary.count, 'readings');

2.2.4 Bidirectional Streaming

Both client and server can send multiple messages. Perfect for real-time collaborative applications or gaming.

// Client code
const chatStream = protocol.createBidirectionalStream('chat.room123');

// Send messages
chatStream.send({ message: 'Hello everyone!' });

// Receive messages
chatStream.on('message', (data) => {
  console.log(data.user + ':', data.message);
  displayMessage(data);
});

// Server handler
protocol.bidirectionalHandler('chat.room123', async (stream) => {
  const room = await joinChatRoom('room123');

  // Forward client messages to room
  stream.on('message', (data) => {
    room.broadcast(data);
  });

  // Send room messages to client
  room.on('message', (data) => {
    stream.send(data);
  });
});

2.2.5 Publish-Subscribe

Decoupled event-driven communication where publishers don't know about subscribers.

// Publisher
protocol.publish('user.login', {
  userId: 'user123',
  timestamp: new Date(),
  ipAddress: '192.168.1.100'
});

// Subscriber 1: Analytics Service
protocol.subscribe('user.login', (event) => {
  analytics.track('user_login', event);
});

// Subscriber 2: Email Service
protocol.subscribe('user.login', (event) => {
  sendWelcomeEmail(event.userId);
});

// Subscriber 3: Security Service
protocol.subscribe('user.login', (event) => {
  checkForSuspiciousActivity(event);
});

2.3 Protocol Lifecycle

2.3.1 Connection Lifecycle

const protocol = new UniversalProtocol(config);

// Lifecycle hooks
protocol.on('connecting', () => {
  console.log('Establishing connection...');
});

protocol.on('connected', () => {
  console.log('Connected successfully');
  initializeApp();
});

protocol.on('disconnected', (reason) => {
  console.log('Disconnected:', reason);
  showOfflineUI();
});

protocol.on('reconnecting', (attempt) => {
  console.log('Reconnection attempt:', attempt);
});

protocol.on('error', (error) => {
  console.error('Protocol error:', error);
  handleError(error);
});

// Connect
await protocol.connect();

2.3.2 Message Lifecycle

Every message goes through several stages from creation to completion:

  1. Creation: Message is created with unique ID and metadata
  2. Serialization: Payload is encoded using chosen format (JSON, Protobuf, etc.)
  3. Transmission: Encoded message is sent over transport layer
  4. Reception: Message is received on the other end
  5. Deserialization: Message is decoded back to original format
  6. Processing: Application handler processes the message
  7. Response/Acknowledgment: Response is sent back (if applicable)

2.4 Error Handling

2.4.1 Error Categories

Category Description Example Codes
Transport Errors Issues with underlying connection CONNECTION_FAILED, TIMEOUT, NETWORK_ERROR
Protocol Errors Malformed messages or violations INVALID_MESSAGE, UNSUPPORTED_VERSION, ENCODING_ERROR
Application Errors Business logic failures VALIDATION_FAILED, NOT_FOUND, PERMISSION_DENIED
System Errors Infrastructure or resource issues OUT_OF_MEMORY, RATE_LIMIT_EXCEEDED, SERVICE_UNAVAILABLE

2.4.2 Error Handling Strategies

// Automatic retry with exponential backoff
const result = await protocol.call('unreliableService', params, {
  retry: {
    maxAttempts: 5,
    backoff: 'exponential',
    maxBackoff: 30000,
    retryableErrors: ['TIMEOUT', 'SERVICE_UNAVAILABLE']
  }
});

// Circuit breaker pattern
const circuitBreaker = new CircuitBreaker({
  failureThreshold: 5,
  resetTimeout: 60000
});

try {
  const result = await circuitBreaker.execute(() =>
    protocol.call('externalAPI', params)
  );
} catch (error) {
  if (error.code === 'CIRCUIT_OPEN') {
    return cachedResult;
  }
  throw error;
}

// Fallback handling
try {
  return await protocol.call('primaryService', params);
} catch (error) {
  console.warn('Primary service failed, using fallback');
  return await protocol.call('fallbackService', params);
}

2.5 Metadata and Context

Metadata allows passing additional information without changing the core payload. This is crucial for cross-cutting concerns like authentication, tracing, and logging.

// Adding metadata to requests
const result = await protocol.call('securedEndpoint', payload, {
  metadata: {
    authorization: 'Bearer eyJ0eXAiOiJKV1QiLCJhbGc...',
    'x-request-id': 'req_xyz789',
    'x-user-id': 'user_abc123',
    'x-trace-id': 'trace_001',
    'x-client-version': '2.1.0'
  }
});

// Accessing metadata in handlers
protocol.handle('securedEndpoint', async (payload, context) => {
  const token = context.metadata.authorization;
  const userId = await validateToken(token);

  if (!userId) {
    throw new UnauthorizedError('Invalid token');
  }

  // Use trace ID for logging
  logger.info('Processing request', {
    traceId: context.metadata['x-trace-id'],
    userId: userId
  });

  return processRequest(payload, userId);
});

2.6 Versioning

The Universal Protocol supports multiple versioning strategies to enable smooth evolution of your APIs.

2.6.1 Protocol Version

The protocol itself has a version (currently 1.0). Different versions may have different message formats or capabilities.

2.6.2 API Version

Your application can support multiple API versions simultaneously:

// Version in method name
await protocol.call('users.v2.getProfile', params);

// Version in metadata
await protocol.call('users.getProfile', params, {
  metadata: { 'api-version': '2.0' }
});

// Version negotiation
protocol.handle('users.getProfile', async (params, context) => {
  const version = context.metadata['api-version'] || '1.0';

  switch (version) {
    case '1.0':
      return handleV1(params);
    case '2.0':
      return handleV2(params);
    default:
      throw new UnsupportedVersionError(version);
  }
});

2.7 Type Safety

The Universal Protocol provides strong typing support for TypeScript and other statically-typed languages:

// Define your message types
interface GetProfileRequest {
  userId: string;
  fields: ('name' | 'email' | 'avatar' | 'preferences')[];
}

interface GetProfileResponse {
  userId: string;
  name: string;
  email: string;
  avatar?: string;
  preferences?: UserPreferences;
}

// Type-safe RPC call
const result = await protocol.call<GetProfileRequest, GetProfileResponse>(
  'users.getProfile',
  {
    userId: 'user123',
    fields: ['name', 'email']
  }
);

// result is strongly typed as GetProfileResponse
console.log(result.name); // ✓ OK
console.log(result.invalidField); // ✗ Compile error

// Type-safe handler
protocol.handle<GetProfileRequest, GetProfileResponse>(
  'users.getProfile',
  async (params) => {
    // params is strongly typed as GetProfileRequest
    return {
      userId: params.userId,
      name: 'John Doe',
      email: 'john@example.com'
    };
  }
);

Key Takeaways

  • Four message types: Request, Response, Stream, Event
  • Five main patterns: RPC, Server Streaming, Client Streaming, Bidirectional Streaming, Pub/Sub
  • Robust error handling with retries, circuit breakers, and fallbacks
  • Rich metadata support for cross-cutting concerns
  • Flexible versioning strategies for API evolution
  • Strong type safety in supported languages

Chapter 4

Format Transformation Engines

At the heart of universal data exchange lies the transformation engine—the component responsible for converting data between formats while preserving semantics, structure, and metadata. This chapter explores how WIA-CORE-003's transformation engines work, from basic format conversion to advanced semantic mapping and AI-powered inference.

Codec Architecture

A codec (encoder/decoder) is a pair of functions that serialize data to a specific format and deserialize it back. WIA-CORE-003 maintains a registry of codecs for 99+ formats, each implementing a standard interface that enables composition and chaining.

// Codec Interface interface Codec<F: Format> { // Deserialize from format F to universal representation fn decode(input: &[u8], schema: &Schema) -> Result<UniversalData> // Serialize from universal representation to format F fn encode(data: &UniversalData, schema: &Schema) -> Result<Vec<u8>> // Validate that data conforms to format F's rules fn validate(input: &[u8], schema: &Schema) -> ValidationResult // Detect schema from sample data (optional) fn infer_schema(samples: &[&[u8]]) -> Option<Schema> } // Example: JSON Codec struct JsonCodec; impl Codec<JsonFormat> for JsonCodec { fn decode(input: &[u8], schema: &Schema) -> Result<UniversalData> { let json_value = serde_json::from_slice(input)?; convert_json_to_universal(json_value, schema) } fn encode(data: &UniversalData, schema: &Schema) -> Result<Vec<u8>> { let json_value = convert_universal_to_json(data, schema)?; Ok(serde_json::to_vec(&json_value)?) } fn validate(input: &[u8], schema: &Schema) -> ValidationResult { match serde_json::from_slice::<Value>(input) { Ok(value) => validate_against_schema(&value, schema), Err(e) => ValidationResult::Invalid(vec![format!("Invalid JSON: {}", e)]) } } }

Transformation Strategies

Direct Codec-to-Codec

For lossless conversions between similar formats (e.g., JSON to YAML), direct transformation bypasses the universal representation for performance. The transformation engine detects when this optimization is safe and automatically applies it.

Universal Representation Bridge

Most transformations use the universal representation as an intermediate: source format → universal → target format. This ensures semantic preservation and enables complex schema mappings.

Multi-Hop Transformation

Some conversions require multiple steps. For example, CSV to Protocol Buffers might go: CSV → universal → JSON schema inference → protobuf schema generation → protobuf encoding.

Type System Mapping

Different formats support different type systems. JSON has strings, numbers, booleans, arrays, and objects. Protocol Buffers adds enums, oneofs, and precise numeric types (int32, int64, float, double). XML has strings and attributes. The transformation engine maps between these type systems while preserving semantics.

// Type Mapping Examples // JSON number to various targets {"age": 25} → XML: <age>25</age> or <person age="25"/> → Protobuf: int32 age = 1; // value: 25 → Avro: {"name": "age", "type": "int"} // value: 25 → CSV: age\n25 // JSON array to various targets {"tags": ["new", "featured"]} → XML: <tags><tag>new</tag><tag>featured</tag></tags> → Protobuf: repeated string tags = 2; // values: ["new", "featured"] → Avro: {"name": "tags", "type": {"type": "array", "items": "string"}} → CSV: tags\n"new,featured" // Requires escaping // Complex nested structure { "user": { "name": "Alice", "contacts": [ {"type": "email", "value": "alice@example.com"}, {"type": "phone", "value": "+1-555-0123"} ] } } // Protocol Buffers representation message User { string name = 1; repeated Contact contacts = 2; } message Contact { string type = 1; string value = 2; }

Semantic Mapping

Structural transformation isn't enough when schemas differ. Semantic mapping handles field renaming, restructuring, value transformation, and business logic application during conversion.

// Mapping Definition Language (MDL) mapping OrderMapping { source: schema OrderV1 target: schema OrderV2 // Simple field mapping map order_id -> orderId // Type conversion map customer_id -> customerId { transform: string_to_int } // Restructuring map { first_name, last_name } -> customer.name { transform: (first, last) => { full_name: concat(first, " ", last), given_name: first, family_name: last } } // Conditional mapping map status -> orderStatus { transform: match value { "pending" | "new" => "PENDING", "shipped" => "IN_TRANSIT", "delivered" => "COMPLETED", "cancelled" => "CANCELLED", _ => "UNKNOWN" } } // Computed fields derive total_with_tax { compute: source.subtotal * (1 + source.tax_rate) } // Array transformation map items -> lineItems { transform: items.map(item => { productId: item.product_id, quantity: item.qty, unitPrice: { amount: item.price, currency: source.currency } }) } // Default values for missing fields map payment_method -> paymentInfo.method { default: "CREDIT_CARD" } // Validation rules validate { require: target.customerId > 0 require: target.lineItems.length > 0 require: target.total_with_tax >= 0 } }

Performance Optimization

Zero-Copy Techniques

For binary formats like Protocol Buffers and Avro, the engine uses zero-copy deserialization where possible, referencing data in place rather than copying it into new structures.

Streaming Processing

Large datasets are processed in streams rather than loading entirely into memory. The transformation engine supports streaming JSON, streaming CSV, and chunked processing for formats that don't naturally stream.

// Streaming Transformation API // Stream large JSON array let input_stream = File::open("large_dataset.json")?; let transformer = StreamingTransformer::new( JsonCodec::streaming(), ProtobufCodec::new() ); let output_stream = transformer.transform_stream( input_stream, source_schema, target_schema, mapping ); // Process chunks incrementally for chunk_result in output_stream { let chunk = chunk_result?; write_to_destination(chunk)?; }

Parallel Processing

Independent records can be transformed in parallel. The engine automatically detects when parallelization is safe and distributes work across CPU cores.

Error Handling and Recovery

Transformation errors are inevitable—malformed data, schema mismatches, validation failures. The engine provides comprehensive error handling with multiple recovery strategies:

  • Fail-fast: Stop on first error (default for critical pipelines)
  • Skip invalid: Log error and continue with next record
  • Best effort: Transform partial data, marking fields that couldn't be converted
  • Fallback values: Use default values for missing or invalid fields
  • Dead letter queue: Route failed transformations to separate stream for manual review
// Error Handling Configuration let transformer = Transformer::builder() .source_format(JsonFormat) .target_format(ProtobufFormat) .error_strategy(ErrorStrategy::SkipInvalid { max_errors: 100, // Stop after 100 errors log_samples: true, // Log first 10 failures dead_letter_queue: Some("errors.jsonl") }) .validation_mode(ValidationMode::Strict) .build()?; let results = transformer.transform_batch(records)?; println!("Successful: {}", results.success_count); println!("Failed: {}", results.error_count); println!("Error rate: {:.2}%", results.error_rate() * 100.0);

Format-Specific Considerations

JSON Peculiarities

JSON's limited type system requires semantic hints. Numbers might represent integers, floats, or decimals. Strings might represent dates, UUIDs, or binary data. The transformation engine uses schema annotations to preserve type information during conversion.

XML Challenges

XML conflates elements and attributes, supports mixed content (text with nested elements), and uses namespaces. The engine provides configurable strategies for mapping XML constructs to other formats.

Binary Format Efficiency

Protocol Buffers, Avro, and Parquet are binary formats optimized for compactness and speed. The engine leverages their native serialization libraries and avoids unnecessary conversions to text formats.

CSV Limitations

CSV is flat and positional, lacking type information and nested structure support. Converting from CSV requires schema hints. Converting to CSV often requires flattening nested structures.

Best Practices for Transformation

  • Always provide schemas—don't rely on inference for production
  • Test mappings with diverse data samples including edge cases
  • Monitor transformation metrics: throughput, latency, error rates
  • Version mappings alongside schemas
  • Use semantic types to preserve meaning across formats
  • Configure appropriate error handling for your use case
  • Validate output data against target schema
  • Document business logic in mapping definitions

Transformation engines are the workhorses of universal data exchange. Understanding their capabilities, limitations, and optimization strategies is key to building high-performance data pipelines.

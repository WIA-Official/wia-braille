Chapter 5

Cross-System Integration Patterns

Universal data exchange isn't just about format conversion—it's about connecting diverse systems that communicate through different protocols, operate on different timescales, and have different reliability guarantees. This chapter explores proven integration patterns and how WIA-CORE-003 implements them to enable seamless system-to-system communication.

Integration Pattern Catalog

Pattern 1: API Gateway with Format Negotiation

An API gateway sits at the system boundary, accepting requests in multiple formats and translating them to the internal format. Clients can send JSON, XML, Protocol Buffers, or any supported format, and receive responses in their preferred format.

// API Gateway with Content Negotiation // Client sends JSON, wants XML response POST /api/users Content-Type: application/json Accept: application/xml {"name": "Alice", "email": "alice@example.com"} // Gateway converts to internal format (e.g., Protobuf) // Processes request // Converts response to XML HTTP/1.1 201 Created Content-Type: application/xml <?xml version="1.0"?> <user> <id>12345</id> <name>Alice</name> <email>alice@example.com</email> </user>

Pattern 2: Message Transformation Middleware

Message queues and event streams often contain messages in heterogeneous formats. Transformation middleware sits between producers and consumers, converting messages to each consumer's preferred format.

// Kafka with Multi-Format Support // Producer publishes in JSON producer.send(topic="orders", value={ "order_id": "ORD-123", "amount": 99.99 }, format="json") // Middleware converts and republishes // Consumer A receives Avro consumer_a.subscribe(topic="orders", format="avro") // Consumer B receives Protobuf consumer_b.subscribe(topic="orders", format="protobuf") // Consumer C receives original JSON consumer_c.subscribe(topic="orders", format="json")

Pattern 3: Database Change Data Capture (CDC)

Capture changes from databases and stream them to other systems in their native formats. A PostgreSQL change can be transformed into a Kafka Avro message, an Elasticsearch JSON document, or a REST API call.

Pattern 4: Legacy System Adapter

Wrap legacy systems (mainframes, COBOL systems, EDI) with modern APIs that handle format translation bidirectionally, enabling gradual modernization without rewriting the core system.

Pattern 5: Schema-Based Routing

Route messages to different consumers based on schema version or structure. This enables A/B testing of new schema versions and gradual rollout of breaking changes.

Protocol Adapters

WIA-CORE-003 provides protocol adapters that abstract communication mechanisms, allowing format transformation to work across diverse transport layers.

HTTP/REST Adapter

// REST Adapter Configuration RestAdapter::new() .endpoint("https://api.example.com/v1/users") .method(HttpMethod::POST) .input_format(JsonFormat) // Accept JSON from client .output_format(XmlFormat) // Send XML to backend .response_format(JsonFormat) // Convert XML response to JSON .schema_mapping(user_mapping) .auth(BearerToken::from_env("API_TOKEN")) .timeout(Duration::seconds(30)) .retry_policy(ExponentialBackoff::new()) .build()

gRPC Adapter

gRPC uses Protocol Buffers natively, but the adapter can expose gRPC services that accept multiple formats, converting them to Protobuf internally.

Message Queue Adapters

Support for Kafka, RabbitMQ, AWS SQS, Azure Service Bus, and Google Pub/Sub. Messages are deserialized from their native format, transformed, and serialized to the target format before delivery.

Database Adapters

Connect to relational databases (PostgreSQL, MySQL, Oracle), NoSQL stores (MongoDB, Cassandra, DynamoDB), and data warehouses (Snowflake, BigQuery, Redshift). Query results are automatically converted to requested formats.

// Database Query with Format Conversion let db_adapter = PostgresAdapter::new(connection_string)?; // Execute SQL query let rows = db_adapter.query(" SELECT user_id, name, email, created_at FROM users WHERE status = 'active' ").await?; // Convert result to JSON let json_output = db_adapter .convert_to_format(rows, JsonFormat, user_schema)?; // Or convert to Parquet for data lake let parquet_output = db_adapter .convert_to_format(rows, ParquetFormat, user_schema)?; write_to_s3("s3://datalake/users.parquet", parquet_output)?;

Real-World Integration Scenarios

Scenario 1: E-Commerce Order Processing

An online retailer receives orders through multiple channels: web (JSON), mobile app (Protobuf), B2B partners (EDI X12), and call center (XML). All orders must be processed through the same fulfillment system.

// Order Integration Pipeline pipeline OrderIntegration { // Multiple input sources sources { web: HttpEndpoint("/api/orders", format=JSON) mobile: GrpcService("OrderService", format=Protobuf) b2b: FileWatcher("/incoming/edi/*.x12", format=EDI_X12) callcenter: SoapService("OrderSoapService", format=XML) } // Normalize all to canonical order schema transform { use schema CanonicalOrder@2.0 mapping { web -> CanonicalOrder: WebOrderMapping mobile -> CanonicalOrder: MobileOrderMapping b2b -> CanonicalOrder: EdiOrderMapping callcenter -> CanonicalOrder: XmlOrderMapping } } // Validate and enrich validate { schema: CanonicalOrder@2.0 business_rules: OrderValidationRules } enrich { customer_data: lookup_customer(order.customer_id) inventory_status: check_inventory(order.items) pricing: calculate_pricing(order.items, customer_data) } // Route to fulfillment system destination { kafka: KafkaTopic("orders.validated", format=Avro) database: PostgresTable("orders", format=SQL) warehouse: RestApi("https://wms.example.com/orders", format=JSON) } }

Scenario 2: Multi-Cloud Data Synchronization

A company runs workloads across AWS, Azure, and Google Cloud. Data must be synchronized between cloud providers, each using different native formats and APIs.

// Multi-Cloud Sync Configuration sync_job CloudDataSync { source { aws_s3: { bucket: "prod-data-lake", format: Parquet, schema: DataLakeSchema@3.1 } } destinations { azure_blob: { container: "analytics-data", format: Avro, schema: AnalyticsSchema@2.0, mapping: DataLakeToAnalytics } gcp_bigquery: { dataset: "enterprise_analytics", table: "fact_events", format: BigQueryJSON, schema: BigQueryEventSchema@1.5, mapping: DataLakeToAnalytics, partition_by: "event_date" } } schedule: "0 */4 * * *" // Every 4 hours incremental: true checkpoint: S3("s3://sync-state/checkpoints/") }

Scenario 3: Microservices Data Mesh

In a microservices architecture, each service owns its data and schema. Services need to exchange data without tight coupling or shared database dependencies.

// Service Mesh Data Exchange service UserService { publishes { event UserCreated { schema: User@1.0 formats: [Protobuf, JSON, Avro] topic: "users.created" } event UserUpdated { schema: UserUpdate@1.0 formats: [Protobuf, JSON] topic: "users.updated" } } consumes { event OrderPlaced from OrderService { schema: Order@2.0 preferred_format: Protobuf mapping: OrderToUserActivity } } } service NotificationService { consumes { event UserCreated from UserService { schema: User@1.0 preferred_format: JSON // Different from publisher! mapping: UserToNotificationContext } } // Transformation happens automatically in service mesh }

Error Handling and Resilience

Cross-system integration must handle failures gracefully. WIA-CORE-003 implements several resilience patterns:

Circuit Breaker Pattern

When a downstream system becomes unresponsive, the circuit breaker stops sending requests temporarily, preventing cascade failures and allowing time for recovery.

Retry with Exponential Backoff

Transient errors (network glitches, temporary unavailability) are retried automatically with increasing delays between attempts.

Dead Letter Queues

Messages that can't be processed after multiple retries are routed to a dead letter queue for manual investigation, preventing data loss.

Bulkhead Pattern

Integration points are isolated from each other using separate thread pools and resource limits, so one failing integration doesn't exhaust resources for others.

// Resilience Configuration adapter.configure_resilience( CircuitBreaker { failure_threshold: 5, timeout: Duration::seconds(60), half_open_after: Duration::minutes(5) }, RetryPolicy { max_attempts: 3, backoff: Exponential { initial: Duration::seconds(1), max: Duration::seconds(30), multiplier: 2.0 }, retryable_errors: [NetworkError, Timeout, ServiceUnavailable] }, DeadLetterQueue { queue: "dlq.failed_transformations", max_message_age: Duration::days(7) }, Bulkhead { max_concurrent_requests: 100, max_queue_size: 1000, thread_pool_size: 10 } )

Monitoring and Observability

Integration pipelines must be observable to detect issues, measure performance, and ensure SLAs are met.

Key Metrics

  • Throughput: Messages/records processed per second
  • Latency: Time from source to destination (p50, p95, p99)
  • Error Rate: Percentage of failed transformations
  • Format Distribution: Which formats are most commonly used
  • Schema Version Distribution: Track schema version adoption
  • Transformation Time: Time spent in format conversion

Integration Best Practices

  • Design for failure: assume downstream systems will be unavailable
  • Use idempotent operations: retries shouldn't cause duplicate side effects
  • Implement comprehensive logging: capture input, output, and transformation details
  • Set appropriate timeouts: balance responsiveness with completion rates
  • Monitor continuously: alert on error rates, latency spikes, and throughput degradation
  • Version APIs and schemas: enable gradual rollout of changes
  • Document integration contracts: clear schemas and SLAs for all interfaces
  • Test with production-like data volumes: integration issues often emerge at scale

Cross-system integration is where universal data exchange delivers its greatest value, enabling systems to communicate seamlessly despite differences in technology, format, and design philosophy.

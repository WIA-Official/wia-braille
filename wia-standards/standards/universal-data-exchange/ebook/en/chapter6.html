Chapter 6

Real-Time Streaming and Pipelines

Batch processing has its place, but modern applications increasingly demand real-time data processing. User analytics need to update dashboards immediately, fraud detection must flag suspicious transactions instantly, and IoT systems process millions of sensor readings per second. This chapter explores how WIA-CORE-003 enables real-time data transformation and streaming pipelines that operate at internet scale.

Streaming Fundamentals

Streaming systems process unbounded data—continuous flows that have no predetermined end. Unlike batch jobs that process a fixed dataset and terminate, streaming jobs run indefinitely, processing events as they arrive. This paradigm shift requires different architectural patterns and mindsets.

Key Streaming Concepts

  • Event Time vs Processing Time: When the event occurred vs when the system processes it. Critical for handling out-of-order events and late arrivals.
  • Windowing: Grouping infinite streams into finite chunks (tumbling windows, sliding windows, session windows) for aggregation and analysis.
  • Watermarks: Signals indicating that no events with timestamps earlier than the watermark will arrive, enabling timely window closure.
  • Backpressure: Mechanism for slow consumers to signal upstream producers to reduce rate, preventing system overload.
  • Exactly-Once Semantics: Guarantee that each event is processed exactly one time, despite failures and retries.

Streaming Transformation Architecture

// Streaming Pipeline Definition stream_pipeline RealTimeAnalytics { // Ingest from Kafka in JSON format source { kafka_stream( topic: "user_events", format: JSON, schema: UserEvent@1.0, consumer_group: "analytics_pipeline" ) } // Transform to internal representation transform { parse { format: JSON, schema: UserEvent@1.0, error_handling: DeadLetter("events.parse_errors") } validate { schema: UserEvent@1.0, business_rules: EventValidationRules } enrich { user_profile: async_lookup("redis://users/{user_id}"), geolocation: geo_ip_lookup(source_ip), device_info: parse_user_agent(user_agent) } map { source_schema: UserEvent@1.0, target_schema: EnrichedEvent@2.0, mapping: UserEventEnrichmentMapping } } // Window and aggregate window { type: TumblingWindow(duration: 5.minutes) key_by: user_id aggregate { event_count: count(), unique_pages: count_distinct(page_url), total_duration: sum(session_duration), last_activity: max(timestamp) } } // Output to multiple sinks in different formats sinks { // Real-time dashboard (WebSocket, JSON) websocket_sink( endpoint: "wss://dashboard.example.com/events", format: JSON, schema: AggregatedMetrics@1.0 ) // Data warehouse (Parquet to S3) s3_sink( bucket: "analytics-datalake", prefix: "events/date={date}/", format: Parquet, schema: EnrichedEvent@2.0, partition_by: date, flush_interval: 1.minute ) // Elasticsearch for search (JSON) elasticsearch_sink( index: "user_events", format: JSON, schema: EnrichedEvent@2.0, batch_size: 1000 ) } // Performance and reliability settings config { parallelism: 16, checkpoint_interval: 30.seconds, state_backend: RocksDB, exactly_once: true } }

Format-Aware Streaming

Different streaming platforms have different native formats. Kafka often uses Avro with a schema registry. AWS Kinesis typically uses JSON. Google Pub/Sub supports both. WIA-CORE-003's streaming layer abstracts these differences, allowing transparent format conversion in stream processing.

// Multi-Format Stream Processing // Producer publishes JSON to Kafka producer.send( topic: "orders", key: order_id, value: order_data, format: JSON, schema: Order@2.0 ) // Consumer A reads as Avro (automatic conversion) stream_a = kafka.consume( topic: "orders", format: Avro, // Convert JSON → Avro automatically schema: Order@2.0 ) // Consumer B reads as Protobuf (automatic conversion) stream_b = kafka.consume( topic: "orders", format: Protobuf, // Convert JSON → Protobuf automatically schema: Order@2.0 ) // Both consumers get the same data, different serialization stream_a.for_each(|order| process_avro(order)) stream_b.for_each(|order| process_protobuf(order))

Stateful Stream Processing

Many stream processing operations require maintaining state: aggregating metrics, joining streams, detecting patterns over time. WIA-CORE-003 provides stateful operators with automatic checkpointing and recovery.

Aggregation with State

// Stateful Aggregation Example stream .key_by(|event| event.user_id) .window(TumblingWindow::of(Minutes(5))) .aggregate(|key, events| { // State is maintained per key (user_id) // Automatically checkpointed for fault tolerance AggregatedMetrics { user_id: key, total_events: events.count(), total_revenue: events .filter(|e| e.event_type == "purchase") .map(|e| e.amount) .sum(), unique_products: events .map(|e| e.product_id) .collect::>() .len() } }) .output_to(metrics_sink)

Stream Joins

Joining two streams requires buffering events from both sides until matches are found. WIA-CORE-003 handles time-based joins with configurable windows and late event handling.

// Join Two Streams // Stream 1: User clicks (JSON) let clicks_stream = kafka.consume( topic: "clicks", format: JSON, schema: ClickEvent@1.0 ); // Stream 2: Ad impressions (Protobuf) let impressions_stream = kafka.consume( topic: "impressions", format: Protobuf, schema: ImpressionEvent@1.0 ); // Join streams within 10-minute window let joined = clicks_stream .join(impressions_stream) .where(|click| click.ad_id) .equal_to(|impression| impression.ad_id) .window(TimeWindow::of(Minutes(10))) .apply(|click, impression| { // Combine data from both events ClickAttribution { ad_id: click.ad_id, user_id: click.user_id, impression_timestamp: impression.timestamp, click_timestamp: click.timestamp, time_to_click: click.timestamp - impression.timestamp } }); // Output attribution data in Avro format joined.output_to( kafka_sink( topic: "attributions", format: Avro, schema: ClickAttribution@1.0 ) );

Exactly-Once Processing

In distributed systems, failures are inevitable. Exactly-once processing guarantees that despite failures, retries, and reprocessing, each event affects the system's state exactly one time. This is crucial for financial transactions, billing, and any scenario where duplicates or data loss are unacceptable.

// Exactly-Once Configuration pipeline.configure_exactly_once( // Checkpoint state periodically checkpoint_interval: Duration::seconds(30), // Use transactional sinks sinks: vec![ TransactionalKafkaSink { topic: "processed_events", transactional_id: "pipeline-001", enable_idempotence: true }, TransactionalDatabaseSink { connection: postgres_pool, table: "events", dedup_key: "event_id" // Detect duplicates } ], // Configure state backend for recovery state_backend: RocksDBStateBackend { checkpoint_path: "s3://checkpoints/pipeline-001/", incremental_checkpoints: true } )

Performance Optimization

Parallelization Strategies

Stream processing frameworks distribute work across multiple parallel instances. WIA-CORE-003 optimizes parallelism based on message keys, ensuring related events are processed by the same instance to maintain consistency.

// Parallelism Configuration pipeline .set_parallelism(32) // 32 parallel operators .key_by(|event| event.user_id) // Partition by user_id .rebalance() // Redistribute evenly across instances .transform(expensive_transformation) .set_parallelism(64) // Increase parallelism for expensive step

Format-Specific Optimizations

  • Avro: Uses object container files with block compression for efficient streaming
  • Protobuf: Leverages wire-format efficiency and optional field skipping
  • Parquet: Columnar format ideal for analytics sinks, with predicate pushdown
  • JSON: Optimized parsers with streaming SAX-style parsing for large documents

Monitoring and Debugging

Streaming pipelines are always-on systems that must be monitored continuously. WIA-CORE-003 provides comprehensive observability.

Key Streaming Metrics

  • Throughput: Events processed per second (input rate, output rate)
  • Latency: Time from event generation to processing (p50, p95, p99, p999)
  • Backlog: Number of unprocessed events (lag behind real-time)
  • Error Rate: Percentage of events that fail processing
  • Checkpoint Duration: Time to save state (affects recovery time)
  • State Size: Memory used by operator state
  • Watermark Lag: How far behind real-time the watermark is
// Metrics Export pipeline.enable_metrics( MetricsConfig { // Export to Prometheus prometheus_exporter: PrometheusExporter { port: 9090, path: "/metrics" }, // Custom metrics custom_metrics: vec![ Counter::new("events_processed_total"), Histogram::new("transformation_duration_ms"), Gauge::new("current_backlog_size"), Counter::new("format_conversion_errors") ], // Detailed logging sample_rate: 0.01, // Log 1% of events for debugging log_transformations: true } )

Backpressure Handling

When downstream systems can't keep up with upstream data rates, backpressure mechanisms prevent system overload by slowing down producers.

// Backpressure Configuration pipeline.configure_backpressure( // Buffer up to 10000 events buffer_size: 10_000, // Strategy when buffer fills overflow_strategy: OverflowStrategy::Block, // Alternatives: DropOldest, DropNewest, Fail // Slow down source if lag exceeds threshold dynamic_rate_limiting: DynamicRateLimiter { max_lag: 100_000, min_rate: 100, // Events per second max_rate: 100_000 } )

Streaming Best Practices

  • Design for event-time processing: use watermarks and handle late events
  • Keep state size bounded: use TTL and compaction strategies
  • Checkpoint frequently enough for acceptable recovery time
  • Monitor lag continuously: rising lag indicates capacity issues
  • Test failure scenarios: verify exactly-once semantics under failures
  • Use schemas for all events: enables validation and evolution
  • Set appropriate parallelism: balance resource usage and latency
  • Implement dead letter queues: capture unparseable events for investigation

Real-time streaming enables responsive applications that react to events as they happen. With WIA-CORE-003's format-agnostic streaming layer, you can build pipelines that transform data across formats while maintaining the low latency and high throughput required for modern applications.
